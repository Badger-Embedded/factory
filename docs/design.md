# Factory design

The factory turns feature requests into pull requests. You describe a change in a dashboard. Claude Code agents clarify it with you, write a spec and a plan for you to approve, implement it in an isolated container, and open a pull request. You review and merge on GitHub.

The factory is separate from the projects it works on. Its skills, agents, hooks and per-project configuration live in this repository and are never committed to a target repository. A target repository keeps only its own rules, which bind people too: `CLAUDE.md`, `CONTRIBUTING.md`, CI and its GitHub ruleset. [maestro](https://github.com/Badger-Embedded/maestro) is the first project.

These decisions were made on 2026-11-19 while brainstorming in the maestro repository.

## Decisions

| Topic | Decision |
| --- | --- |
| Agent runtime | The Claude Code CLI in rootless podman worker containers. Claude Managed Agents was considered and rejected in favor of local Claude Code on our own hardware. |
| Host | `moon.local` (`ssh moon@moon.local`): Ubuntu 26.04, x86_64, 8 cores, 7.2 GB RAM, 74 GB free disk, systemd linger on for user `moon`. Tailscale is up at `100.77.68.75`. |
| Factory process | A Rust binary in its own container, run as a Quadlet systemd user service. It starts worker containers through the user's `podman.socket`. |
| Factory stack | axum, SQLite, server-rendered pages with htmx, and server-sent events for live logs. No frontend build step. |
| Dashboard access | The factory listens on localhost. `tailscale serve` publishes it over HTTPS on the tailnet and passes the Tailscale login in request headers. No separate login. |
| GitHub identity | The bot account `moonthebot`, logged in with `gh` on moon (scope `repo`). It must be a **Write** collaborator on each target repository, not Admin, so a ruleset's Admin bypass does not apply to it. Onboarding a project checks the repository against this as the bot, through the `GitHubRepos` trait: `GhRepos` runs `gh api`, and tests pass a fake so none reaches the network. `check_repo` returns errors and warnings. An error blocks onboarding: a repo that is not `owner/name`, one that is missing or not visible to the bot, a base branch that does not exist, no push access for the bot, and squash merges turned off, which the factory relies on. A warning does not: the bot holds Admin, the base branch has no protection or ruleset, the repo has no Actions workflow, and merged branches are not auto-deleted. GitHub answers HTTP 403 for the rules of a branch in a private repository on a free plan. That check then becomes a warning that names GitHub's answer, because it cannot tell whether the branch is protected. A 403 from any other call still means the checks could not run. Nothing calls the checks yet; the onboarding wizard is a later change. |
| Credentials | Only the factory holds the GitHub token. Workers get no GitHub credentials. |
| Claude auth | The subscription token from `claude setup-token`, held in the factory's encrypted secret store, the same store MCP header values use. An operator sets or replaces it from the settings page, so changing it needs no login to moon. The settings page has a "Claude token" field in the global section, outside the per-project forms. It shows only whether a token is stored, never the value and not even in the input's `value` or the page source, the way an MCP header value's field does. A non-empty save replaces the token, after the factory trims surrounding whitespace and a trailing newline; an empty save keeps it; and a separate Clear button removes it. When the secret store is unavailable the field is disabled with a message and Clear still works, so a token stranded by a lost master key can still be removed. A saved token reaches the next worker run and plan usage refresh with no restart, because the `ClaudeToken` resolver reads it afresh. See "MCP secret storage" for the store. A `ClaudeToken` resolver reads the current token on each use: the stored token when the store is available, or `CLAUDE_CODE_OAUTH_TOKEN` from the environment when it is not, so a lost master key does not stop jobs while the old podman secret still passes the token in. At startup, when the store is available, holds no token, and the env var is set and not empty, the factory imports that value into the store and logs the import without the token, so the move off the podman secret needs no manual step on moon. Once a token is stored the env var is ignored. Workers get the resolved token to run Claude Code, and the factory process fetches plan usage for the board tile with it. Its usage limits are shared with interactive use. Switch to an API key if the factory hits them often. |
| MCP secret storage | Per-project header values for MCP servers are credentials, so the factory encrypts them at rest. Each value is sealed with XChaCha20-Poly1305 under a random per-value nonce, with the project, server and header name bound in as associated data, so a ciphertext copied into another row fails to decrypt. The ciphertext lives in the `secrets` table, keyed by project, server and header, separate from the server and per-project settings tables, so a later user system can add an owner column in a migration. The master key is 32 random bytes in the `factory-master-key` podman secret, held outside the database. `deploy/install.sh` generates it when it is missing, the same way it creates `gh-token`, so no step is manual, and it never regenerates the key on a later run. The Quadlet unit passes the key to the factory container alone. Workers never get it, so a stolen worker cannot read a credential, and a stolen database file or backup leaks nothing without the key. The key is excluded from database backups. Losing it makes every stored value unreadable, and each one must be entered again. When the key is missing or malformed the factory still starts and reports the secret store as unavailable, rather than refusing to run. Secret access goes through the `SecretStore` trait, with put, get and delete for MCP header values, and get, set and clear for the account-wide Claude token. The local encrypted backend is its only implementation now, and each row records its backend, so an external manager such as Vault can be added later without a schema change for existing rows. The Claude subscription token from `claude setup-token` is stored here too, sealed the same way but in one reserved row of the `secrets` table whose `server` is empty, which no MCP server name can be. So `delete from secrets where server = ?` for any MCP server, including one named `claude`, never touches it, and deleting or renaming such a server leaves the token in place. Its ciphertext binds a fixed domain tag rather than a project, server and header, so a ciphertext moved between the token row and an MCP header row fails to decrypt in either direction. |
| MCP server registry | An operator adds remote MCP servers on the settings page, in an "MCP servers" section with forms to add, edit and delete one. The `mcp_servers` table holds one row per server: a unique `name`, an `https` `url`, and a JSON list of `headers`. A name is 1 to 32 characters of `a-z`, `0-9` and `-`, unique, because it keys the run's MCP config and is part of the proxy path. The URL must parse, use `https` and have a host. Each header name is a header a project may fill with a value; it must be a valid HTTP token and not one the factory sets itself or the streamable-HTTP transport owns: `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Mcp-Session-Id`, `MCP-Protocol-Version` and `Last-Event-ID`. Two header names that differ only in case collapse to the first spelling. The transport is streamable HTTP. stdio servers and the older SSE-only transport are out of scope. Deleting a server deletes every project's `project_mcp` row and every stored secret for it in one transaction. An edit that changes the URL's origin, its scheme, host or port, deletes every stored secret value for the server, so no dashboard user can repoint a server at their own host and collect another project's keys, and the edit form says this before you save. An edit that changes only the path keeps the values. Removing a header name deletes the stored values for that name alone. A rename is a remove plus an add: the old name's stored values are gone and each project enters a value under the new name. context7 at `https://mcp.context7.com/mcp` is the first server, added by hand through the form. |
| MCP project settings | Each project's form on the settings page has a block per server: an enabled switch, a checkbox for each of the five stages, clarify, spec, plan, implement and review, the same five as the project models, and a write-only field for each header the server declares. The `project_mcp` table stores the enabled flag and the five stage flags, keyed by project and server. A project with no row reads off with no stage, so a newly added server and a newly onboarded project both start off. The save handler refuses an enabled server with no stage checked and returns a 400 that names the server. A header field shows only whether a value is stored, "set" or "not set", never the value and not even masked. An empty field leaves the stored value as it is, a typed value replaces it, and a "clear" checkbox deletes it. A header with no stored value is not sent, so a keyless server such as context7 needs none. The handler reads and checks every server's block before any write, so a rejected submit leaves every table as it was, and saving one project's settings leaves other projects alone. The scheduler reads the registry and the project's settings on every run, the way it reads the models, so a change reaches a job in flight at its next run. |
| MCP header-name editing | The settings page edits a server's header names in one text box per name, on the add form and each server's edit form, not a textarea of names. An "Add header" button appends an empty row and each row has a "Remove" button, both run by an inline script. The boxes post a repeated `header` field that the add and edit handlers trim, dropping an empty row, so the form works without JavaScript too: the add form starts with one empty box, an edit form shows one box per stored name plus one empty box, you add one name per save and clear a box to drop its name. Each box's `pattern` allows only the HTTP token characters `mcp::normalize_headers` accepts, so a pasted `Authorization: x` is refused in the browser before the server validates it again, see MCP server registry for the validation and the propagation of an add, remove, rename or URL origin change to every project's stored values. Only the name goes in the box; the value is per project and encrypted, which the hints state, see MCP secret storage. |
| MCP proxy | The factory runs an HTTP proxy for MCP traffic on its own listener, `FACTORY_PROXY_LISTEN`, which the Quadlet unit sets to `0.0.0.0:8081`, separate from the dashboard on `127.0.0.1:8080`. The factory container and its workers share the `factory` podman network, which `install.sh` creates, so a worker reaches the proxy by the factory's container name at `FACTORY_PROXY_URL` (`http://factory:8081`), while the dashboard port, published only to the host loopback, stays out of a worker's reach. For each agent run with at least one active server the scheduler issues a run token through `RunTokens`: 256 random bits held only in the factory's memory, scoped to the job and the servers active for the run's stage. The scheduler revokes the token when the worker exits, whether the run succeeded, failed or was cancelled, and a factory restart drops every token. The worker gets `claude --mcp-config` with one `http` entry per active server, each pointing at `http://factory:8081/mcp/<server>` and carrying `Authorization: Bearer <run token>` as its only header. A run with no active server gets no MCP flags, so its arguments are unchanged, and check runs and every non-agent container get no config and no token. The proxy answers 401 to a missing, unknown or revoked token and 403 to a server outside the token's scope. For an authorized request it drops the worker's `Authorization` header, adds the project's stored headers, and forwards the method, path suffix, query, body and the protocol headers, `Content-Type`, `Accept`, `Mcp-Session-Id`, `MCP-Protocol-Version` and `Last-Event-ID`, to the server's URL. It streams a `text/event-stream` response without buffering it and supports the POST, GET and DELETE that streamable HTTP uses. It follows no redirect, so a 3xx cannot carry the headers to another host and is returned to the worker as it is. It uses a 10-second connect timeout and no total timeout, so a streaming response may stay open for the length of the run. The credential stays out of the worker because the worker runs with `bypassPermissions`: it could otherwise read the value from its config, arguments or environment, and a prompt injection in a repository or an MCP response could make it print or send the key. The proxy keeps the value on the factory side, so the worker holds only a run token the proxy swaps for the real headers. |
| MCP unavailable servers | An enabled server that is unreachable when a run starts does not fail the run. The run goes on without the server's tools, as Claude Code does. Two paths report it. The runner reads the `mcp_servers` list in the stream-json `system`/`init` line and warns about each active server whose status is not `connected`. The proxy warns when it cannot reach the server, a connection times out, or the server answers 5xx. The scheduler also warns about a server it skipped because a stored header value would not decrypt, so a broken credential never lands in a worker's config. All three funnel through `McpWarnings`, which dedupes per run so a server is warned at most once, and writes the warning through `Store::record_mcp_unavailable`: a factory line to the job log that names the server and the reason, and an `mcp-unavailable` row in `job_events` with `<server>: <reason>` in its `detail`, written the way `add_cost` writes a cost row, so it changes neither the job's stage nor its turn. The reason names no credential. The job page timeline shows the row as a note under the step the run was in. |
| MCP connection check | Each server block in a project's settings has a "Check connection" button that tests the server with that project's saved header values. It posts to `POST /settings/projects/<project>/mcp/<server>/check` through htmx, which swaps the returned HTML fragment into a result area, so the page does not reload and unsaved input survives. The handler resolves the saved URL and the project's saved values through `StoreUpstreams`, the same resolver the proxy uses, so the check and a real run send the same headers. It ignores any form field posted with the request, so an unsaved value typed into the page is never sent, and the hint says to save first to check new ones. An unknown project or server gives 404. The check sends one JSON-RPC `initialize` POST with `Content-Type: application/json` and `Accept: application/json, text/event-stream` plus the project's values, follows no redirect like the proxy, uses the proxy's 10-second connect timeout, a 15-second total timeout, and reads at most 1 MiB of the body. Success is a 2xx reply, JSON or SSE, whose `result` carries a `protocolVersion`; the result names the server and version when the reply gives them. On success it sends a best-effort `DELETE` with any `Mcp-Session-Id` to end the session. The result messages cover a reachable MCP server, an unreachable host, a timeout, a 401 or 403 that points to the project's header values, another 3xx, 4xx or 5xx with a 3xx `Location`, and a 2xx that is not an MCP reply. A declared header with no stored value is named in the result, and the check runs without it. No header value reaches the fragment, a log line or an error. The result is not stored: reloading the page clears it. The HTTP part sits behind the `McpChecker` trait, held by the dashboard the way it holds `RepoChecker`, so a test uses a fake and the real `HttpMcpChecker` is tested against a local `http://` server. The "Add server" button runs no check, because the header values belong to projects and the add form has none; the per-project check is the one the requester chose. |
| Approval gates | Spec, plan and publish. Spec and plan are on by default. The settings page turns each on or off. A job copies the gates from the settings when it is created, so a later settings change does not touch existing jobs. Everything after the last gate runs without stopping, apart from questions the agent asks. The state machine stops at a gate only when the job has it. The settings page also has a publish gate, off by default. A job with it stops before the first push of each planned pull request and waits for approval. Later pushes to the same pull request, such as fixes for CI or review comments, are not gated. You merge on GitHub, unless the project's auto-merge setting is on: then the factory squash-merges a pull request once every check passed and no review comment waits for the agent. Auto-merge is per project, see Project settings. A pull request with no checks reported yet is not merged, so a push is never merged before GitHub starts its CI. |
| Notifications | The dashboard inbox only. |
| Job board | The index page is an inbox of the selected project's jobs in one column, sorted by what you must do. Each job's lane comes from one function that also decides its turn badge, from the same stage and turn rules, so they never disagree. The lanes are You, Agent, Factory, Failed and Done. A merged or cancelled job is in Done. A failed job is in Failed. A job that needs an answer or approval, or a review on GitHub, is in You. A job in review with auto-merge on is in Factory. The board shows four sections, top to bottom: Needs you for the You lane, Failed, Running for the Agent and Factory lanes together, and Done. Each section has a count and lists the newest job first. The new-request form above the sections is a one-line bar. It grows and shows the image picker once it has focus, text or a pasted image, using CSS `:focus-within` and `:has()` with no script. A section with no job does not render. When no job is live, the board says "Nothing needs you and no job is running." Done lists five jobs, and the older ones sit in a collapsed `<details>` element, so it works without JavaScript. Each job is a row: the id, the title, then a line with the turn badge, the steps, the detail, the requester and the cost. The title is the first line of the request, cut at 80 characters, with the full line in its `title` attribute. The steps are nine small segments for requested, clarifying, spec, plan, implementing, verifying, pr-open, ci-and-review and merged, marked done, current or to come. A job with several pull requests shows the steps of the one it is on. Only a live job shows them. The detail is the stage label for a live job, such as "implementing, PR 2 of 7", and the failure reason for a failed job. A merged or cancelled row has no detail, because its badge says so. The cost is the job total, formatted like the job page, and shows "–" when the job has none. `Store::costs` reads every job cost in one query. The row omits the project name, because the board shows one project. A row in Needs you that waits at the spec or plan gate has a "Read spec" or "Read plan" link to the job page and an Approve button. Approve posts to `POST /jobs/{id}/approve` with the selected project, and the handler redirects back to that project's board. The job page's own approve form sends no project, so it still redirects to the job page. Any other row in Needs you has an Open link to the job page, where the answer, publish and review controls are. A failed row shows a Retry button for a retryable job. It posts to `POST /jobs/{id}/retry` with the selected project, and the handler redirects back to the board the same way. Rows in Running and Done have no button. Below the sections, one line lists the project totals: total API cost, jobs created, jobs merged, merge rate and cost per merged job. A figure that is zero or would divide by zero shows a dash. The inbox replaced a five-column lane board with KPI tiles and a Live jobs by lane panel, because those showed the same counts three times and left empty lanes on the screen. |
| Project registry | The `projects` table in SQLite, one row per project: a unique name, a unique `owner/name` repo, the base branch, an optional checks command, and a created-at time. The `Projects` handle reads the table on each `lookup` or `list`, so a project onboarded while the service runs is visible at once, with no restart. `Store::create_project` adds a row and rejects a duplicate name or a duplicate repo, so the web onboarding wizard builds on it. A project's models and its auto-merge and LLM-review flags stay in `project_models` and `project_settings`, so a project read from the `projects` table carries those at their defaults. Before this, projects were `projects/<name>/project.toml` files in this repository and a new one was a pull request. `import_tomls` makes the move once: on the first start of a database with no projects, it reads each `project.toml` under the `FACTORY_IMPORT_PROJECTS` directory (default `projects`), writes the `repo`, `base` and `checks` into the `projects` table, writes a `[models]` into `project_models` only when set and `auto_merge` or `llm_review` into `project_settings` only when one is on, then deletes the files. It is a no-op once the table has a project, so a rerun duplicates no row and keeps a later edit. A file that sets neither flag writes no `project_settings` row, so `Store::migrate_global_auto_merge` still applies the old global auto-merge to an imported project exactly as it did to the file. |
| Project settings | A project has two per-project flags, auto-merge and LLM review, edited in each project's form on the settings page and stored together in one row of the `project_settings` table in SQLite. Auto-merge squash-merges a pull request once its checks pass. LLM review runs a reviewer before the merge, see Project models for the review model and the `ci-and-review` LLM review pass. Both default to off, so a project with no row does neither, the state a project onboarded without flags starts in. `save_project_settings` writes the whole row. The one-time toml import writes a `project_settings` row only when a file turned a flag on, see Project registry. The form that edits a project's models edits both flags too, so saving one project writes all three and leaves other projects alone. The scheduler reads both flags for a project on every watch, so a change to either reaches jobs already in flight. `llm_review` joined the row after auto-merge shipped, so the store adds an `llm_review` column to a `project_settings` table that predates it when it opens the database. Auto-merge was one global setting before. A one-time migration, `Store::migrate_global_auto_merge`, runs at startup: when the stored settings still carry the old global `auto_merge` and it was on, every known project inherits it, so those projects keep their earlier behaviour. The migration then drops the global field, so it runs only once and a project added later starts off. |
| Project models | Each project has a model for each of the clarify, spec, plan, implement and review stages. The settings page has a form per project to edit them, stored in the `project_models` table in SQLite. A project with no row runs every stage on the default model, the state a project onboarded without models starts in. Empty means no model. The one-time toml import writes a `project_models` row only when a file set a `[models]` table, see Project registry. The scheduler picks the model for a run from the stage it runs in: clarify and its answer runs use `clarify`, `WriteSpec` and spec revisions use `spec`, `WritePlan` and plan revisions use `plan`, `Implement`, check fixes, CI fixes, rebases and review-comment runs use `implement`, and the LLM review pass uses `review`. It reads the saved models on every run, so a change reaches jobs already in flight at their next run. The runner passes the model as `claude --model` and passes nothing when it is empty. `review` joined the stages after the table shipped, so the store adds a `review` column to a `project_models` table that predates it when it opens the database. |
| Agent effort | Each stage's agent run passes `claude --effort <level>`, so no run relies on Claude Code's own default. The level is `medium` unless a project sets another, across the same five stages as the models. The default and the allowed levels, `low`, `medium`, `high`, `xhigh` and `max`, the levels the installed `claude` CLI accepts, are constants in `factory-core`, so the server and the runner read one list and a default that cannot drift between them. The default lives in code, not a config file, so a project that saved no effort runs every stage at medium. The runner always adds `--effort` to the `claude` arguments and uses the default when a run request carries no effort, such as a request from an older server. A project's effort per stage lives in the `project_efforts` table in SQLite, one row per project with a column per stage. SQLite is the only store: effort is never read from `project.toml`. The table is created when a database that predates it opens, so an existing project has no row and reads medium for every stage, the way `review` was added to the models. The scheduler picks a run's effort from the same stage mapping as the model, so check fixes, CI fixes, rebases and review-comment runs use `implement`, and it reads the saved effort on every run, so a change reaches jobs already in flight at their next run. The store validates each saved level against the allowed list and rejects anything else without a write, so a bad value is never stored. Saving one project writes that project's row alone. The settings page edits a project's effort per stage with a selector beside each stage's model field. The selector offers only the allowed levels and preselects the effective one, medium when the project saved none. The save handler writes the models and the efforts together and saves the efforts first, so a level outside the allowed set returns an error and nothing is stored, the models included. The job page timeline shows the running step's effort after its model in the agent badge, such as `opus · medium`. |
| Request images | The New request form posts multipart. The handler accepts up to 5 images of at most 5 MiB each, and the request text may be at most 256 KiB. It checks each image by its first bytes, not by file name or declared type, and accepts PNG, JPEG, GIF and WebP. A request over a limit, or one with images and no text, gets a 400 that names the limit and creates no job. The factory saves each image as `<data_dir>/jobs/<id>/images/image-<n>.<ext>` under a name it generates, so an upload's file name never reaches the file system. The job row in SQLite records only the file names, in a `job_images` table. `factory-core`'s `Job` holds no image data, since it does no I/O. A small script, `static/paste-images.js`, attaches an image pasted into the request textarea to the file input, shows a thumbnail with a Remove button, and leaves the form working without the script. The job page shows the images next to the request, served from `GET /jobs/<id>/images/<name>`, which serves only a name the `job_images` table lists for that job. When a run starts a fresh session, the runner copies the images into the checkout under `.git/factory-images/`, which git does not track, so the checkout stays clean. It appends their paths to the prompt and tells the agent to look at them. The clarify run is the first such run. A run that resumes a session adds nothing, because the session already has the paths. |
| Job expiry | The job loop deletes a merged, failed or cancelled job once its `created_at` is more than 30 days old. The age counts from the request, not from the day the job finished. The factory deletes the job row, its rows in the other tables, and `<data_dir>/jobs/<id>`. A job that is not finished stays however old it is. When one job fails to delete, the loop logs it and goes on with the others, and the next pass tries it again. |
| Capacity | At most 2 worker containers at a time. Each worker gets `--memory 3g --cpus 4`. A job waiting for you holds no worker. The limit, image, memory and CPUs are settings stored in SQLite, read by the job loop on every pass, so a settings page can change them without a restart. The scheduler records which job holds which numbered slot, and since when, in a `WorkerSlots` handle it shares with the dashboard. A worker run takes the lowest free slot number when it starts and frees it when it ends or the job no longer wants it. Checks run in a worker and take a slot too. Factory steps such as a push or a pull request watch run in the factory process and take none. The board shows one tile per slot above the request bar, as many as the worker limit. A busy tile links to the job and shows its stage and how long it has held the slot. A job of another project shows that project's name, because the slots are shared by every project. An idle tile says idle. When the factory runs without podman workers, every tile is idle. |
| Job page timeline | The job page has two columns. The left one holds the status card, the request, the spec, the plan, the review passes and the log. The right one holds the timeline, which replaced the nine-step tracker under the title. Below 900px the columns stack, with the timeline between the status card and the request. The timeline reads the job history, see Job history. It lists the four planning steps, then a group for each planned pull request with its four steps, then merged. A pull request goes back through verifying, pr-open and ci-and-review after each fix, so each step adds up every visit: it shows the time the job first entered it, the time spent in it over all visits, and the API cost of the runs in it. Under a step, timed notes list what happened in it: questions and answers, requested changes, failed checks and CI, CI reruns, conflicts, review comments, LLM review verdicts, failures, retries and a cancel. The last 8 notes show and older ones collapse into one line. A gate shows `✓ approved` with its time once approved, and a `✋ approval` badge until then. The publish gate sits on verifying and applies only before a pull request's first push. The step the job is in shows who acts: the model of the agent run, from the project's models as the next run would use them, with what the agent is doing; `waiting for you`; or `factory`. A failed job marks the step it failed in and shows the reason. Each pull request group is a `<details>` element, so it works without JavaScript. It starts open while a step in it is running or failed, and its summary shows the number, the title and, once done, the total time and cost. A poll swap resets a group the reader opened or closed. A job from before the history has no times or costs: the steps before its current one show as done without them. A legacy failed job with no history shows its reason under the steps. |
| Job cost | Each job has a running total of the API cost of its agent runs, in USD. It lives in the `job_costs` table in SQLite, one row per job, so a job from before the table existed has no row and reads 0. `Scheduler::agent` adds the cost a run reports, and a run that reports none adds nothing. A cancelled or failed job keeps its total. `format_cost` formats it as `$1.23`, for the log and the job page. The job page shows the total as a pill badge on the title row, right-aligned and vertically centred with the heading, out of the meta line. A job with no recorded cost shows "–". The job board shows it on each card. The stats strip shows the project total, see Project totals. |
| Job history | The `job_events` table in SQLite keeps what happened to each job, one row per entry, oldest first by id. `Store::apply_in` writes a row in the same transaction as every event it applies, so the history and the stored job cannot disagree, and a rejected event writes nothing. A row has the time, the event name, and the stage, pull request index and turn the event left the job in. `Store::create` writes a `created` row, and `Store::add_cost` writes a `cost` row with the run's cost in USD against the stage the run ran in, because the scheduler adds the cost before it applies the run's event. A failed agent or reviewer run and a CI rerun keep their reason in the row. Watching that pull request finds the work left, or finds it merged and moves on to the next pull request. A legacy job with no pull request number is not retryable. ## Claude plan usage source

The board will show one account-wide tile with the Claude subscription limits left: the 5-hour window, the weekly window, and the Fable usage the plan reports. The feasibility gate ran on 2026-11-20 in a factory worker on `moon.local`, with the worker's `CLAUDE_CODE_OAUTH_TOKEN`, the `claude setup-token` secret from the "Claude auth" decision.

Two things were tried:

- `claude -p "/usage" --output-format json`. In print mode `/usage` resolves to the local session-cost command. The result line carries `local_command: "usage"` and prints this session's cost and duration, not the plan limits. The CLI does not report plan usage non-interactively, so the factory cannot shell out to it.
- `GET https://api.anthropic.com/api/oauth/usage?skip_spend=1`, the endpoint the interactive `/usage` panel calls. The headers are `Authorization: Bearer <token>` and `anthropic-beta: oauth-2025-04-20`. `skip_spend=1` asks for the windows without the spend figures.

The token is accepted. A request with an invalid token, and one with no auth header, both return HTTP 401 `authentication_error`. The factory's token returns HTTP 429 `rate_limit_error`, so it passes authentication and reaches the throttle. The endpoint rate-limits hard: every authenticated call during the spike returned 429 after a handful of requests, so a live 200 body was not captured. The fields below come from the response parser inside the CLI (version 2.1.329), which names them and their types.

The `?skip_spend=1` response holds:

- `five_hour`, `seven_day`, and `seven_day_overage_included`, each an object `{ utilization, resets_at, status? }`. `utilization` is a number, the fraction of the window used. `resets_at` is a Unix timestamp. `status`, when present, is one of `allowed`, `allowed_warning`, or `rejected`.
- `model_scoped`, an array of `{ display_name, utilization, resets_at }`, one entry per per-model weekly window. The server supplies `display_name`, for example `Fable`. Fable usage arrives through this array, not as a field of its own, so the parser in the next pull request reads it as an optional list. The array is absent when the server reports nothing about these windows.

Decision: the factory fetches `GET /api/oauth/usage?skip_spend=1` with its own token. It is the only source the requester accepted, and it returns the three windows and the Fable entry the tile needs.

Risk: the endpoint is undocumented and carries no stability promise. Its path, auth header, query flags, or response shape can change with no notice, and the heavy rate limiting means a single fetch can fail at any time. The factory polls on a long interval and serves the tile from a cache, so a 429 never reaches a page load, and it hides the tile on any error or stale cache rather than show a wrong number. If the endpoint breaks, the tile disappears and the rest of the board is unaffected.

### Refresh and cache

A background task fetches the endpoint every `PLAN_USAGE_REFRESH` (5 minutes) and writes the result into a `PlanUsageCache` the task shares with the dashboard. A page load reads the cache and never calls the endpoint, so a slow or rate-limited fetch cannot hold up a request. Each fetch resolves the current token through the `ClaudeToken` resolver, see "Claude auth", so a token saved on the settings page is used from the next refresh with no restart. With no token the fetch is skipped and the cache is left as it is, so the tile stays hidden. The fetch shells out to `curl` and passes the URL and the `Authorization` header through curl's stdin config, so the token stays out of the process arguments. A failed fetch, a non-200 status, or a body that does not parse is logged without the token and marks the cache as errored.

The cache keeps the last snapshot that parsed and the time it was fetched, plus whether the most recent fetch errored. The tile is hidden, meaning `visible` returns `None`, when the last fetch errored, when no fetch has ever parsed, or when the last success is older than `PLAN_USAGE_STALE_AFTER_SECS` (30 minutes). The refresh interval is shorter than the staleness cutoff, so one failed fetch does not blank the tile; five in a row do. The cutoff and the refresh interval are named constants, the first in `factory-core` next to the snapshot type and the second in `factory-server` next to the fetch.

## Architecture

```text
moon.local (rootless podman, user moon)
├─ factory container (Quadlet user service)
│    orchestrator + dashboard + SQLite
│    holds moonthebot's gh token
│    talks to podman through podman.socket
│    polls GitHub for CI status and review comments
│    holds the master key that decrypts per-project MCP header values
│    runs the MCP proxy on its own port, which adds a project's stored headers
└─ worker containers, one per job stage, started by the factory
     image: Claude Code, git, nix
     mounts: job workspace, shared /nix store volume, cargo cache per project, factory plugin (read-only)
     network: the shared factory podman network, to reach the MCP proxy but not the dashboard
     env: the Claude token the factory resolves, see Claude auth, and an MCP config pointing at the proxy with a per-run token when a server is active
```

GitHub cannot reach `moon.local`, so the factory polls GitHub with `gh api` about once a minute instead of receiving webhooks.

## Job flow

Each job moves through these states. Each ✋ is an approval gate. A job has the gates its settings turned on when it was created.

```text
requested → clarifying → spec ✋ → plan ✋ → implementing → verifying → publish ✋ → pr-open → ci-and-review → merged
```

- **clarifying.** The agent reads the repository and asks questions. A headless run cannot wait for answers, so the run ends with its questions as structured output. The dashboard shows them, and the next run resumes the same session with your answers.
- **spec.** The agent writes the goal, scope, what is out of scope, and acceptance criteria. The run starts a new session. Its prompt holds the request and the answers to the clarifying questions.
- **plan.** The agent splits the work into pull requests. A large refactor gets its own pull request first, as maestro's `CONTRIBUTING.md` requires. The run starts a new session. Its prompt holds the request, the answers and the approved spec.
- **implementing.** One worker session per pull request. The prompt holds the request, the answers, the approved spec, the titles of all planned pull requests and the summary of this one. The worker commits in the job workspace and stops when the commits are ready.
- **verifying.** The factory runs the project's checks in the worker. Failures go back to the session. The comment review once planned here is now part of the merge-time LLM review, see `ci-and-review, the LLM review pass`.
- **publish.** With the publish gate on, the job stays in verifying once the checks pass and the factory collects the branch's commits and diff stat from the checkout. The dashboard shows them with the pull request title and description. Approve moves the job to pr-open. Request changes sends your feedback to the pull request's session, then the checks run again and the job returns here. A revision does not count toward the 5 failed rounds. The factory pushes nothing before you approve.
- **pr-open.** The factory pushes the branch and opens the pull request as moonthebot. Before the push, it asks GitHub for a merged pull request from the branch. You can merge a pull request while the factory is between a CI fix and its push, and GitHub then deletes the branch. The push would fail on every retry, because `--force-with-lease` expects the deleted branch. So when the branch has a merged pull request, the factory pushes nothing, records that pull request's number and applies `Merged`, and the job moves to the next pull request.
- **ci-and-review.** The factory polls CI and review comments, and feeds failures and your comments back into a resumed session until CI is green and you merge. When the pull request no longer merges cleanly, the factory fetches the newest base branch into the checkout, since workers have no GitHub credentials, and the agent rebases onto it. A conflict counts toward the job's limit of 5 failed rounds per pull request, so an agent that cannot resolve one stops.
- **ci-and-review, the LLM review pass.** When CI is green and the project has LLM review on, a reviewer runs before the factory merges. The scheduler applies `StartReview`, which moves the job to a review turn: a worker run in a `review` session of its own, separate from the implement session, with no GitHub token. It reads the branch diff from the checkout and ends with `approve`, or `changes` with feedback. Each pass is kept as a numbered `ReviewPass` with its verdict and feedback, for the job page. `approve` records the approval and returns the job to watching the pull request, so the factory merges when auto-merge is on or waits for you when it is off. `changes` sends the feedback to the implement session as a review-fix run, the same path as a human review comment; after the push CI runs and the reviewer runs again. The review session resumes across passes, so a later pass sees only the commits since the last one and reviews those. A push clears the recorded approval, so the reviewer reads each head afresh. The review-fix runs count toward a review cap of 5, held in `review_rounds` and separate from the 5 failed check and CI rounds, so a job can spend both on one pull request. At the cap, or when a reviewer run crashes, times out or returns no valid result, the review fails closed through `ReviewFailed`: the job does not merge and waits for you with the reason. The state machine is pure, so it models the pass with no I/O; the scheduler runs the worker and decides the merge.
- **Rerun on request.** When the agent runs a `FixCi` task and finds nothing to commit, such as after a flaky failure, it returns `rerun_ci` with a reason. The job moves to a factory turn that runs `Command::RerunCi`, which carries the reason for the log. This counts a failed round through `fail_round`, so the limit of 5 still applies and the fifth round fails the job. The `CiRerun` event returns the job to watching the pull request. The result is rejected in any other turn. The scheduler logs the reason, then calls `Executor::rerun`, which runs `GitHub::rerun_failed` with the factory's token. The worker still gets no GitHub token. When `gh` fails, the job stays in the rerun turn and the scheduler tries again after `poll_seconds`. After a successful rerun the scheduler applies `CiRerun` and holds the next watch for `poll_seconds`. `rerun_failed` already waits until GitHub stops reporting the old failure, so the next watch does not count it as a second round. When the head has no failed Actions run, the scheduler logs that and applies `CiRerun` anyway. The next watch then sees the failure again and asks the agent again, which counts another round, so the limit of 5 ends the loop.
- **Retry a failed job.** A job that used up its 5 failed check or CI rounds ends in `failed` with a retry target: the `verifying` or `ci-and-review` stage of the pull request it failed on. A job whose agent run failed ends in `failed` with the stage and task of that run as its retry target. The failure card on the job page shows a Retry button, which posts to `POST /jobs/{id}/retry`. `Event::Retry` returns the job to that stage with a factory turn and resets the failed-round count, so the factory runs the checks or watches the pull request again and the agent gets 5 fresh rounds before it fails once more. For a failed agent run, `Event::Retry` runs the same task again in the same session and keeps the failed-round count. This covers a run stopped by the plan's usage limit, and a job whose project was not configured, which fails again if the project is still missing. `failed` is therefore no longer always terminal. `Job::can_retry` reports whether a retry would resume the job. A legacy job stored before the retry target existed carries none. The factory recognises it by its exact old reason, or by an agent failure reason that starts with "the agent run ended with", and resumes at `ci-and-review` of its highest-numbered pull request. A legacy job with no pull request number is not retryable. A job closed unmerged, and a cancelled or merged job, reject `Retry`, and their failure cards show no button. The retry leaves `created_at` alone, so the 30-day expiry is unchanged.
- **Rerun after an edit.** When `open_pr` edits an existing pull request whose checks had failed, the factory reruns the failed runs on the head commit, so they read the new description. `GitHub::rerun_failed` lists the runs on the head with `gh run list --commit`, and runs `gh run rerun <id> --failed` for each one that failed, timed out or was cancelled. It uses the factory's token, so workers still have none. The case it covers is an agent run that edits the description and adds no commit. The push does nothing, so the old failed run is still the head's result. The factory reads the checks before the edit, and reruns after it. The rerun counts no round, because the round for the failing CI was counted when the agent was asked to fix it. Passing, pending and missing checks cause no rerun, and neither does creating the pull request. When the head has no failed Actions run, such as a failed check from outside Actions, `rerun_failed` returns `NothingToRerun`, and `open_pr` logs an error. When the rerun fails, `open_pr` logs the error and returns the pull request number, because the edit worked. GitHub keeps reporting the old failure for a moment after a rerun, and a watch in that moment would report it again and count a second round. So `rerun_failed` reads the pull request after the reruns until no check is failed, up to `settle_polls` reads `settle_interval` apart (10 reads, 3 seconds). The watch reads the same data, so it sees the new state.

The state machine is pure logic with no I/O, so it can be tested without podman or GitHub. Every step must be safe to retry, because a container or the factory can die in the middle of one.

## Running Claude Code in a worker

- One `claude -p` run per stage, with `--output-format stream-json` for the live log. The factory picks the session's UUID and passes it with `--session-id` on the first run, so it knows the ID even if it dies during the run. Later runs pass `--resume <session-id>`.
- **Fresh sessions.** The clarify, spec, plan and implement runs each start their own session, one for clarifying, one for the spec, one for the plan and one per planned pull request. Each prompt is self-contained, because the session has seen none of the earlier stages. The job stores the request, the answers, the approved spec and the plan for this. Only a gate revision, a check fix, a CI fix, a review fix or a rebase resumes the session of its own stage. Each stage can then use its own model, because no resumed session switches models. A job created before this rule has no stored answers and keeps one planning session for clarifying, spec and plan, so its spec and plan runs resume it with the short prompts.
- Every run ends with `--json-schema` structured output: an `outcome` and the questions, spec or plan that go with it. Each stage allows `questions` and one outcome of its own: `clarified`, `spec`, `plan` or `commits_ready`. A `FixCi` run may also end with `rerun_ci` and a required non-empty `reason`. The factory runs the rerun itself, so the worker needs no GitHub token for it. Any other run that returns it fails the job. Claude Code puts the output in `structured_output` on the final `result` line. A run without it, or with an outcome its stage does not allow, fails the job.
- The worker is started with `--rm`, so each job gets a Claude Code config directory on the host, mounted at `CLAUDE_CONFIG_DIR`. It keeps the session files that `--resume` reads.
- The factory resolves the Claude token when the run starts, see "Claude auth", and sets it in the podman process environment. The worker gets it with `--env CLAUDE_CODE_OAUTH_TOKEN` and no value, so podman passes the token through from its own environment and it never appears in the `podman` arguments, the job log or an error message. A token saved on the settings page reaches the next run this way, with no restart, while a run already going keeps the token it started with. With no token the run fails before any container starts with "no Claude token is set", and the job page's Retry runs the task again once a token is saved.
- Every run gets `--settings` with `attribution` emptied. Claude Code otherwise adds a `Co-Authored-By` trailer to each commit, a skill's rules do not stop it, and GitHub copies the branch's co-author trailers into the squash commit on the base branch. Before the project's checks, the factory also fails a branch whose commits credit an AI tool, and the agent rewords them.
- The factory's rules come in through `--plugin-dir` (skills and agents) and `--settings` (hooks). A headless run in an untrusted folder ignores a repository's `extraKnownMarketplaces` without any message, so the factory must not depend on the target repository's plugin settings.
- The target repository's own `CLAUDE.md` and project skills still load. maestro has its own `no-comments` and `open-pr` skills, so the factory's plugin namespaces its versions as `factory:no-comments` and `factory:open-pr`.
- Claude Code hooks run under whatever shell the container has, without the nix devShell. Write hook scripts for plain bash and test them that way.

`open-pr` changes from maestro's version: the worker stops when its commits are ready, and the factory pushes and opens the pull request.

The `Title and description` job reads the title and body with `gh pr view`, not from the event payload. ## Lessons from building maestro's checks

- `grep -q` at the end of a pipeline under `set -o pipefail` can fail when it matches, because the writer gets SIGPIPE. Feed `grep -q` from a variable instead.
- macOS has bash 3.2 as `/bin/bash`. Hook scripts must work there.
- prek refuses to run when `prek.toml` is not staged.
- prek runs hooks without a `stages` setting at every stage, the `commit-msg` stage included. Set `default_stages` when adding hooks for other stages.
- A project setting in `.claude/settings.json` loads only when the session starts. A hook added mid-session does not fire until the next session.
