# Factory design

The factory turns feature requests into pull requests. You describe a change in a dashboard. Claude Code agents clarify it with you, write a spec and a plan for you to approve, implement it in an isolated container, and open a pull request. You review and merge on GitHub.

The factory is separate from the projects it works on. Its skills, agents, hooks and per-project configuration live in this repository and are never committed to a target repository. A target repository keeps only its own rules, which bind people too: `CLAUDE.md`, `CONTRIBUTING.md`, CI and its GitHub ruleset. [maestro](https://github.com/Badger-Embedded/maestro) is the first project.

These decisions were made on 2026-11-19 while brainstorming in the maestro repository.

## Decisions

| Topic | Decision |
| --- | --- |
| Agent runtime | Agents run in rootless podman worker containers. Everything agent-specific sits behind one agent interface in `factory-runner`, the `AgentBackend` trait: the command after the image, the credential and config-directory environment variable names, the session-resume check, and the parser that turns the agent's stdout into the generic items the worker consumes. `worker.rs` keeps the generic `podman run` flags and names no one agent. Claude Code is the first agent; see "Running Claude Code in a worker" for its implementation. Claude Managed Agents was considered and rejected in favor of local Claude Code on our own hardware. Codex is the second agent and runs on a ChatGPT Plus or Pro login; see "Running Codex in a worker". Copilot is the third agent and runs the GitHub Copilot CLI on a stored GitHub login; see "Running Copilot in a worker". |
| Salsa and GitLab | Salsa (salsa.debian.org) is the second forge kind, `salsa`. `GitLab` in `factory-runner` is generic over the host, and `Forges` builds it for Salsa with `salsa.debian.org`; the kinds are fixed in code. It runs `glab api` from `FACTORY_GLAB` (default `glab`) with the token in `GITLAB_TOKEN` and the host in `GITLAB_HOST` in the child's environment, never in arguments, and with a private empty `GLAB_CONFIG_DIR` so no ambient login leaks in. A repository is the full project path with two or more segments, and `ForgeKind::valid_repo` validates each kind's form. A merge request's number is its `iid`. Developer is Write, Maintainer and Owner are Admin, the higher of the project and group level counts, and Reporter, Guest or a public project the account is not a member of are Read. Whether the account may merge comes from the merge request's `user.can_merge`, because a protected branch can limit merging to Maintainers. Merge is a squash merge that deletes the source branch, and a Renovate merge is bound to the head by `sha`. CI checks are the jobs of the pipeline on the merge request's head; a pipeline whose sha is not the head, or no pipeline, reads as no checks, so it never merges. Only a pipeline with status `success` passes; `manual`, `running` and the like wait and `skipped` reads as no checks. The pipeline's jobs, retry and traces use the project that owns the pipeline, which is the fork for a fork's merge request. Merge requests of the branch are matched by source project as well as branch, and the diff is read from the merge request version whose head is the head under review, and refused unless that version is `collected` and holds as many files as its `real_size`. The Renovate watch polls again when the diff's head is not the head its CI was read for. Every call passes `--hostname`, runs outside any checkout with the inherited token, OAuth, TLS-skip, protocol and `GIT_*` variables removed and CI auto-login off, and resolves a relative `FACTORY_GLAB` first. A rerun retries the pipeline's failed jobs, and the failure report is the end of each failed job's trace. Review comments are the notes, with `file:line` for a note on the diff; system notes, bot notes and the logins to ignore are left out. The commit identity is the username with `<id>-<username>@users.noreply.salsa.debian.org`, and git authenticates with a Basic header for `oauth2:<token>`. GitLab has no fixed Renovate account, so `renovate_prs` takes the author and a Salsa project must name one. The onboarding checks for Salsa (`GlabRepos` in `factory-server`, built on the same `GitLab`) run as the onboarding login's token. Errors: a malformed path, a project that is missing or not visible, an account below Developer, a base branch that does not exist, and `squash_option` `never`. Warnings: Maintainer or Owner access, a base branch that is not protected, a base branch head with no pipeline on the base branch's ref and head sha (the "has CI" check, because Salsa CI is often set in the project settings with no `.gitlab-ci.yml`; a pipeline another ref ran on the same sha does not count), and protection whose `merge_access_levels` do not let the account merge, which means auto-merge will not work for it. The check reads every page of protected-branch rules until an empty one, takes those whose name or wildcard matches the base, and the most permissive wins, as in GitLab; a list it cannot read to the end is unverified, never a denial. A project whose `builds_access_level` is `disabled` warns that CI/CD is disabled and its pipelines are not listed. A 403 from the listing on any other project warns that CI could not be checked, which is not a confirmed absence. Access level `0` is "No one" and never a grant. A rule that names a user or a group, or no matching rule at all, gives no warning, because the result is unverified: the account's id and groups are not known there. There is no warning about branch deletion, because the factory asks for it on each merge. |
| Forge interface | Everything a job asks of a git forge sits behind the `Forge` trait in `factory-runner`: pull request lookup, open, status, rerun, merge, the Renovate reads and writes, ticking Renovate's rebase checkbox in a pull request description with the factory's account, file and compare reads, the failure report, the clone URL and the git authentication header. Its methods return boxed futures, so the trait is object safe with no macro crate, the same way `RepoChecker` is. Each call takes the `Account` it runs as, a token plus the login and commit identity, so the caller picks the account per operation and the forge holds no token. `GitHub`, which runs the `gh` CLI, and `GitLab`, which runs `glab`, are the implementations. `Git` takes the clone URL and the header from the forge through a `Remote`, so it names no `github.com` or `x-access-token`, and `PodmanExecutor` holds `Forges`, not one forge. `Forges` in `factory-server` maps a `ForgeKind` to the `Forge` and to the onboarding `RepoChecker`. Each scheduler request that reaches the forge carries its `ForgeKind` and the `Account` it runs as, and the executor calls `forges.forge(request.forge)` with that account. `Accounts` in `factory-server` builds the account when an operation starts and the logins whose comments are left out. `Forge::status` takes those logins, so the forge holds no bot login. `ForgeKind` has the variants `GitHub` and `Salsa`, with a display name, a host and builders for the repository and pull request links, so `pages.rs` builds no forge URL itself. Onboarding has no forge field yet, so it stores `github`. A project's `Project::forge` holds a `ProjectForge`, which is a known kind or the unknown name from the row. `Accounts::resolve` and the scheduler refuse a project whose forge is unknown, and the job fails with a message that names the forge. `Accounts` resolves the account of each operation from the stored tokens, see "Account resolution". There is no factory-wide account: `Account` has no default, and the factory reads no `FACTORY_GIT_NAME`, `FACTORY_GIT_EMAIL` or `moonthebot`. `Git::prepare` sets `user.name` and `user.email` from the `Remote` on every call, not only at clone, so an existing checkout takes the identity of the account that runs next. A further forge adds a variant, an implementation and an arm in `Forges`. `Forgejo` in `factory-runner` implements the trait over the Forgejo HTTP API with `reqwest`, so the factory image needs no further CLI. Its base URL is data, not a constant, because the factory registers any number of Forgejo servers. Nothing selects it yet. It sends the token only in an `Authorization: token` header, follows no redirect, reads no proxy or credential from the environment and accepts `https` only, so a token never reaches another origin. Git is safe the same way: git follows a redirect only on the first request, and sends the `extraHeader` of `git_auth_header`, which is scoped to the clone URL's host, to no other host. `forgejo::version` reads `/api/v1/version` and refuses an answer without the `+gitea-` suffix that Forgejo appends, because plain Gitea is not supported. A version below 16 has no job logs and below 17 has no rerun. `account` commits as `<login>@noreply.<host>`, with the host of the base URL and no port. The checks come from the combined commit status, which holds the latest status per context. `failure` or `error` on any context is a failed check, otherwise `pending` waits, otherwise one `success` or `warning` passes, and no status or only `skipped` is no checks. A `warning` does not block, because the server does not treat it as a failure. A target URL that is relative resolves against the base URL. A pull request that reports `mergeable` false is read again up to three times, `settle_interval` apart, before it counts as conflicting, because the server reports false while it works the merge state out. `rerun_failed` lists the workflow runs of the head, reruns each failed job and then waits as GitHub does, and a 404 or 405 from those endpoints reads as nothing to rerun and is logged. `failure_report` finds the failed job by the check's URL, which names the run index and job index, and keeps the last 30,000 bytes of its log. Every timestamp becomes UTC as `YYYY-MM-DD HH:MM:SS`, because the server answers with its own offset and the scheduler compares the text. The compare API lists no patch, so `compare_patch` reads the file at both refs and builds a unified diff with a small line diff in the crate, which adds no dependency. Comments of a review carry `path:position`, and `original_position` when the position is 0. `pushed_at` is the time of the latest `pull_push` timeline entry that names the head. |
| Forge tokens | A forge token is a credential for one forge account, sealed in the encrypted secret store, see "MCP secret storage". There are three kinds, named by `ForgeTokenOwner`. A user token belongs to a login and a forge, at row `project ""`, `server ""`, header `forge-user:<forge>:<login>`. A project token belongs to a project and an upstream token to a project's packaging upstream, at `project <name>`, `server ""`, headers `forge-project` and `forge-upstream`, so `Store::remove_project`, which deletes `secrets WHERE project = name`, removes them and a project onboarded later under the same name inherits none. The associated data is `factory:forge-token:v1` followed by the length-framed owner kind, key and forge. The account metadata is not secret and sits in plain tables, `user_forge_accounts (login, forge, account_login, account_id)` and `project_forge_accounts (project, kind, forge, account_login, account_id)`, so a page says whose token is stored without decrypting it, and `remove_project` deletes the second table's rows too. On save, `forge_tokens::save` calls `Forge::lookup_account` with the pasted token (`gh api user` for GitHub, the token in `GH_TOKEN` in the child's environment) and stores the token with the account's login and numeric id. HTTP 401 or 403 is `LookupError::Rejected` and any other failure is `LookupError::Failed`, whose text has the token removed. A rejected token is stored nowhere, and the page says so without echoing the input. `Forge::account` builds the commit identity from the lookup: the login as name and `<id>+<login>@users.noreply.github.com` as email. No page renders a token: the field has no value and the placeholder reads "set" or "not set". An empty save keeps the stored token, Clear removes the token and its account, and with the secret store unavailable the field is disabled, a save is refused and Clear still works. A forge page, `/settings/forges/<forge>`, is open to every login. The project token is saved on the Forge account card of the project's settings page, see "Project collaborators". `forge_tokens::save_for_repo` does the lookup and then `Forge::access`, which reads the account's access to the repository: for GitHub `gh api repos/<repo>` permissions, `admin` is Admin, `maintain` or `push` is Write, anything else is Read, and HTTP 404 is `Access::NotVisible`. Not visible stores nothing and the page names the account. Read and Admin store the token with a warning. Write stores it with none. A failed access read stores the token and the page says the access was not checked. The write is `SecretStore::put_project_forge_token`, which stores nothing when the project instance the save began with is gone or when the saving login is no longer a collaborator. `Store::project_with_instance` reads the project and its instance id, from the never reused `project_instances` autoincrement, in one transaction before the forge calls, and the write checks the id and the membership in the transaction that stores the token. Removing an unrelated project does not affect a save. A save that outlives its project cannot recreate the token for a project that reuses the name. Jobs use them as "Account resolution" describes. The upstream token is optional and is saved from an upstream token field inside the Maintenance form on the project's settings page, which shows only while packaging is on. Its forge is the one named by the field's buttons. `forge_tokens::save_guarded` does the lookup and then the same guarded write as the project token, so a save that outlives its project instance or its collaborator stores nothing. Changing the upstream forge and saving the Maintenance card clears the old upstream token, whose ciphertext is bound to the old forge. |
| Account resolution | `Accounts::resolve(project, requested_by)` picks the account when each forge or git operation of a job starts, so a token saved or cleared, or a switch changed, applies from the next operation with no restart. A request job runs as the stored token of its `requested_by` login when that login is a collaborator, has "Use my account" on for the project and has a token for the project's forge. Every other job runs as the project token. A job with the requester `factory` always does: Renovate discovery, Renovate jobs, and gap proposals before approval. `Store::approve_proposal` sets `requested_by` to the approving login, so an approved gap job follows the request rule from then on. An answer, approval or retry by another collaborator does not change `requested_by`. There is no fallback after resolution. With no project token the operation fails with "Project <name> has no project token. Save one on /settings/projects/<name>" and makes no forge call. A failed resolution or a refused token fails the job through `FactoryFailed`, or `AgentFailed` for an agent run, and the job page shows Retry. Retry resolves again, so it runs with a token saved since, and no other token is tried first. A transient error in a publish, watch or Renovate step still logs and tries again after the poll interval. Each executor request carries an `AccountSource`, and the executor calls `resolve` before every forge or authenticated git operation, so the push and the pull request open of one publish may run as different accounts when a token changes between them. The command that ran classifies a refusal: the runner marks an error with `REJECTED` when `gh` or `git` output holds HTTP 401, "Bad credentials" or git's authentication failure, and the executor turns that into "The forge rejected the project token of <name>" or "the GitHub token of <login>", with the page that replaces it. Agent failure text is never searched. The runner replaces the token and the authorization header with `<redacted>` in every `gh` and `git` error, so no job log or failure reason holds them. The worker writes the checkout's git configuration, so no command that reads it gets a credential. A clone runs where no checkout exists yet. A fetch or push runs in a bare repository the factory makes in a temporary directory, with `--git-dir`, hooks off and no credential helper, against the forge's URL with the header scoped to that host. The checkout hands the branch to that repository and takes the fetched base from it, each without a credential, so its proxy, certificate, `url.*` and `include` settings are never loaded with a token. `Git::prepare` takes a closure and calls it before the clone and again before the fetch, so a token saved between them reaches the fetch. A failed log fetch inside a CI failure report is noted in the report, except a refused credential, which fails the step like any other refusal. After a Renovate merge succeeds, the job records the merge before it reads the merged pull request, so a refusal on that read leaves Retry resuming the watch and not merging again. The `Account` comes from `Forge::account`, so its commit identity is the account's login and noreply address. `Resolved.ignore` holds the resolved login and the project token's login, read from the metadata tables, and `Forge::status` leaves out comments from those logins. After a push the job log reads "Pushed <branch> to <repo> as <login> (project account)" or "(requester's account)", with the login of the account the push ran as. With the secret store unavailable no token is readable, so no forge operation runs. A collaborator who is removed loses the switch, and their jobs move to the project token at the next operation. |
| One-time `GH_TOKEN` copy | The factory reads `GH_TOKEN` for this copy only. Jobs and onboarding do not use it, so an install with no `GH_TOKEN` works. At startup, after the toml import, with the secret store available and `GH_TOKEN` set, `forge_tokens::copy_gh_token` gives each `github` project with no project token that value as its project token. It looks the account up with `Forge::lookup_account` first and stores the token with the account's login and id. A project whose lookup fails or times out stores nothing, is named in a warning with the token removed from the text, and is tried again at the next start. The lookup runs once per start, bounded by `LOOKUP_TIMEOUT`, and the `gh` child is killed when it times out, so a stalled CLI cannot hold the start. The copy is recorded per project in `gh_token_copies (project)`. The marker is written in the same transaction as the token, whether it is a copy, a collaborator's save or a clear, and when the project already holds a token. A token cleared before the first successful pass therefore stays cleared across restarts. `Store::create_project` with an onboarding login writes the marker too, so a project onboarded later does not get the token of the factory account. The toml import passes no login and writes no marker, so imported projects get the copy. `Store::remove_project` deletes the marker, so a project onboarded under a reused name starts with none. Projects on another forge are skipped. With the secret store unavailable the factory logs one warning and copies nothing. The log names the project and the account login, never the token. |
| gh stdin | `GitHub::run` in `factory-runner` passes a body to gh on stdin for `pr create`, `pr edit`, `pr comment` and the approval `api` call. It closes the pipe and waits for gh in every case, even when the write fails. A non-zero exit returns `gh <cmd> <sub> failed: <stderr>`, so gh's own message survives. A zero exit ignores a `BrokenPipe` write error, because gh may exit without reading its stdin, and any other write error returns `writing to gh: ...`. An early return on the write error made the result depend on whether gh read its stdin and when it exited, and it lost the stderr of a gh that failed first, for example on a bad token. |
| Agent registry | `AgentRegistry` in `factory-server` maps each agent to what the server needs to run and present it: the credential, the worker image, the host config directory, the settings page URL, and the model aliases and effort levels the stage panel offers. It holds the `ClaudeToken` resolver, the `CodexLogin` coordinator and the secret store, and is built once at startup. For Claude the credential is that resolved token, the image is the `worker_image` setting from the Workers page, the host config directory and the stdout parser come from `factory-runner`'s `AgentBackend` (see "Agent runtime"), the settings page is `/settings/agents/claude`, the model aliases are fable, opus, sonnet and haiku, and the effort levels are the ones `factory-core` exposes. Codex carries the same: its credential is the stored `auth.json` the `CodexLogin` coordinator resolves, it runs in the same `worker_image` since one image carries both agents, its settings page is `/settings/agents/codex`, and its model aliases track the pinned CLI's `gpt-6` family. Copilot's credential is the GitHub token in its own secret store row, read afresh on each run, so a token saved on the settings page reaches the next run. It runs in the same `worker_image`, and its model suggestions are `claude-sonnet-5.5`, `claude-opus-5.5`, `gpt-6.2-sol` and `gemini-3.8-flash`. Its settings page is `/settings/agents/copilot`, which the sidebar links. The podman executor reads the credential, the image and the host config directory from the registry rather than naming an agent. A run whose agent resolves no credential fails before any checkout or container; Claude's reason is "no Claude token is set", Codex's is "no Codex login is set" and Copilot's is "no Copilot login is set". An unavailable secret store, or a Copilot row that will not decrypt, reads as no login. The stage panel renders the model chips, the datalist and the hint under the model field from `model_suggestions` of the stage's saved agent, so each agent offers only its own ids: Claude `fable`, `opus`, `sonnet` and `haiku`, Codex `gpt-6.1-sol` and `gpt-6.1-codex`, Copilot `claude-sonnet-5.5`, `claude-opus-5.5`, `gpt-6.2-sol` and `gemini-3.8-flash`. The hint names the agent's CLI. Job 47 showed why: with Copilot selected the panel still offered Claude's aliases, and a Claude alias saved on a Copilot stage would make a Copilot run fail. Any id can still be typed, and a save does not check it against the list. |
| Prompt boundary | The stage prompts stay Rust format strings in `factory-runner`'s `prompt.rs`, which interpolate the job's data and are covered by the prompt tests. Moving them to template files would add a loader, a path in the worker image and a template syntax, and every prompt would stay shared anyway, so the fix is at the boundary: `prompt.rs` names no agent. The parts that differ per agent come from the `AgentBackend` as a `PromptStyle`, next to the command line and parser that already sit behind the trait (see "Agent runtime"): the repository instructions file the prompt names, `CLAUDE.md` for Claude and `AGENTS.md` for Codex and Copilot, the review method a review run follows, the review skill for Claude and Copilot and the skill's path for Codex, and the schema the prompt carries when the agent's CLI has no output-schema flag. Claude and Codex pass the stage's schema to the CLI, so their `PromptStyle` carries none; Copilot has no such flag, so its `PromptStyle` carries an instruction that tells the agent to end with one message of only the JSON, says that text outside the JSON fails the run, and says a summary goes into the schema's fields, and `prompt.rs` appends the stage's schema after it. `Agent::rules_doc` in `factory-core` stays the one source of the instructions file name, which the `PromptStyle` and the podman executor's missing-`AGENTS.md` warning both read. A run with at least one active MCP server also gets one trailing paragraph that names the servers, tells the agent to load their tools before it starts, and covers gateway servers. A gateway such as Composio lists only a dozen meta tools that search a catalog and run what they find, so an agent that loaded only those tools could conclude that no tool exists for an app the gateway covers; the paragraph says the listed tools are then not all the server offers and tells the agent to ask the server's search tool before it decides no tool exists. The text is generic and names no vendor, because `job_prompt` gets only operator-chosen names, so matching a name or URL is a guess that misses other gateways, and the sentence is conditional, so it costs a plain server nothing. Claude Code keeps an MCP server's tools behind a search step and loads a tool's schema only when the model asks for it, so without the paragraph an agent never reaches a tool nothing names; the paragraph is what lets a later step use one. The scheduler passes the active server names into `job_prompt`, so the set tracks the run's config, and the wording is the same for every harness and stage because that set can change between runs. A run with no active server gets no MCP paragraph. Every run, for every agent and stage, also gets one fixed nix paragraph, built by `end_prompt` in `prompt.rs` before the schema instruction. It says nix is installed with flakes enabled and that a missing tool can come from nixpkgs, for example `nix shell nixpkgs#<package> -c <command>`, and that the repository's own instructions still decide how to build and test. The worker image has nix with flakes and every worker mounts the shared `/nix` volume, but an agent only learned of it from a repository's own instructions, so it could give up on a missing binary. The wording is identical for every agent, so it needs no `PromptStyle` field and `prompt.rs` still names no agent. It sits before the Copilot schema instruction, so a Copilot prompt still ends with the schema, or with the MCP paragraph, and the final JSON message is unaffected. |
| Contributor setup | This repository's own agent files are laid out for both Claude Code and Codex. `AGENTS.md` at the root holds the project instructions, worded for any coding agent, and `CLAUDE.md` is the single line `@AGENTS.md`. Claude Code reads `CLAUDE.md` and expands its `@path` imports, so the import pulls in `AGENTS.md`; Codex reads `AGENTS.md` into its developer message on its own. One file holds the text, so the two never drift. The `unslop` skill lives at `.agents/skills/unslop/SKILL.md`, the path Codex scans, and `.claude/skills/unslop` is a relative symlink to it, the path Claude Code scans, so both load the one skill. Before this a factory Codex run against this repository logged a missing `AGENTS.md` and could not load `unslop`. |
| Host | `moon.local` (`ssh moon@moon.local`): Ubuntu 26.04, x86_64, 8 cores, 7.2 GB RAM, 74 GB free disk, systemd linger on for user `moon`. Tailscale is up at `100.77.68.75`. |
| Factory process | A Rust binary in its own container, run as a Quadlet systemd user service. It starts worker containers through the user's `podman.socket`. |
| Factory stack | axum, SQLite, server-rendered pages with htmx, and server-sent events for live logs. No frontend build step. |
| Dashboard access | The factory listens on localhost. `tailscale serve` publishes it over HTTPS on the tailnet and passes the Tailscale login in request headers. No separate login. A login sees and acts on a project, and every job in it, only when it is one of the project's collaborators, see Project collaborators. `web.rs` reads this through two helpers: `visible_project` returns the named project when the login collaborates on it, and `visible_job` returns a job when the login collaborates on the job's project. A project the login may not see returns the same 404 as one that was never onboarded, and a job it may not see returns the same 404 as an unknown job, so neither leaks its existence through a different status or page. The board, the project picker, `/fragments/board`, `/fragments/stats`, `/fragments/workers`, `POST /jobs`, every `/jobs/{id}` route, and `/settings/projects/{project}`, its `/checks` and `/name` save routes, and its MCP pages and check all go through these helpers. The board's default project is the one in the `factory_project` cookie when the login collaborates on it, otherwise the first project the login collaborates on. A stale, foreign or malformed cookie falls back silently with no 404, see Remembered project. A login that collaborates on none sees "You are not a collaborator on any project." with a link to onboarding, and the worker and plan-usage tiles, which carry factory-wide data, render only once the login has a project. The board loads the login's projects with one `Store::projects_for` call, also when it checks the project cookie, and filters the already-loaded list in memory, so the checks add no query per job. The worker slots are account-wide, so a tile may hold a job in a project the viewer may not see; such a tile shows only that the slot is busy and for how long, not the job's id, project, stage or request, so the capacity count stays right without leaking the job. `/fragments/plan-usage` returns the same 404 for an explicitly named project the login may not see, and an empty tile for a login with no project of its own. The factory-wide settings pages are limited to factory admins, see Factory admins. The MCP server registry page names the login's own projects alone in its "Used by" card and its held-back-edit confirmation, so neither names a project the login may not see. The confirmation still counts every value the edit deletes, so its button states the full effect, and it reports the count in projects the login may not see without naming them. |
| GitHub identity | The factory has no account of its own. A job runs as the project's token or as its requester's own token, see "Account resolution". The account behind a token must be a **Write** collaborator on each target repository, not Admin, so a ruleset's Admin bypass does not apply to it. It should be a bot account, because the factory ignores pull request comments from the account a job runs as and from the project's account, and GitHub does not let an account approve its own pull request. Onboarding a project checks the repository as the onboarding login's own stored token for the forge, not as the bot, through the `GitHubRepos` trait: `GhRepos` runs `gh api` with the token of the `Account` each call is given, and tests pass a fake so none reaches the network. A login with no stored token gets a blocking error that links to `/settings/forges/github`, and the wizard makes no forge call. The dashboard reaches the checks through `Forges`, see "Forge interface". `check_repo` returns errors and warnings. An error blocks onboarding: a repo that is not `owner/name`, one that is missing or not visible to that account, a base branch that does not exist, no push access for that account, and squash merges turned off, which the factory relies on. A warning does not: the account holds Admin, the base branch has no protection or ruleset, the repo has no Actions workflow, and merged branches are not auto-deleted. GitHub answers HTTP 403 for the rules of a branch in a private repository on a free plan. That check then becomes a warning that names GitHub's answer, because it cannot tell whether the branch is protected. A 403 from any other call still means the checks could not run. The onboarding wizard calls them, and picks the checks by the forge selected in its form, see "Salsa and GitLab" for the Salsa ones. |
| Credentials | Only the factory holds the forge tokens that push branches and open pull requests, the project tokens and the personal tokens in its secret store. Workers get no credential for that identity. The one exception is a Copilot worker, which gets the stored Copilot login token in `COPILOT_GITHUB_TOKEN`, see "Copilot auth". That token belongs to a GitHub account on a Copilot plan. | Renovate pull request jobs | A Renovate job is a `Job` with `kind` `Renovate(RenovatePr)`, at its own `Stage::Renovate` with the request text set to the pull request title. A job stored before `kind` existed loads as `Request`. It skips clarify, spec, plan, implement and publish. The factory watches the pull request, and the core decides everything from what each watch reports. `Event::RenovateObserved` carries the head commit, the CI state (`NoChecks`, `Pending`, `Failed` with the log, or `Passed` with the diff and description when the job has no verdict for that head), the retry limits, the project's auto-merge flag and the project account's access (`RenovateAccess`: whether it may rerun CI, whether it may merge, and its login; a job stored before this loads with full access). Below it, the job reruns with no agent until the automatic reruns are used up, then runs `Task::AnalyzeFailure`. A transient verdict reruns and counts toward the total only. A repo is unique by forge plus repo, so the same path can be onboarded once per forge. `forge` joined the table after it shipped with `repo` unique alone. SQLite cannot change a constraint in place, so the store rebuilds a `projects` table without the column in one transaction and gives every existing row `github`. A row with a forge name no `ForgeKind` carries loads as `ProjectForge::Unknown`. That is an error for that project only: its board and settings page show the problem, its jobs fail with a message that names the forge, Renovate discovery skips it, and other projects are not affected. `Store::create_project` takes the `ForgeKind` and rejects a duplicate name or a duplicate forge plus repo, so the web onboarding wizard builds on it. The wizard has a forge selector, GitHub by default, as radio buttons that work without JavaScript. The repository placeholder follows the selected forge and the hint shows both forms. The selected forge decides the checker and the token the checks run with, and it is the forge the project is created with. An unknown forge name in the post is a blocking error. It takes the onboarding login and, in the same transaction, writes that login as the project's first collaborator, see Project collaborators. `Store::create_project_as` also sets that collaborator's "Use my account" switch, which onboarding turns on because its checks just showed that login's account can push; the project has no project token yet and its board shows the missing token notice; the toml import passes no login, so the collaborator migration seeds imported projects from their jobs instead. A project's models and its auto-merge and LLM-review flags stay in `project_models` and `project_settings`, so a project read from the `projects` table carries those at their defaults. Before this, projects were `projects/<name>/project.toml` files in this repository and a new one was a pull request. `import_tomls` makes the move once: on the first start of a database with no projects, it reads each `project.toml` under the `FACTORY_IMPORT_PROJECTS` directory (default `projects`), writes the `repo`, `base` and `checks` into the `projects` table, writes a `[models]` into `project_models` only when set and `auto_merge` or `llm_review` into `project_settings` only when one is on, then deletes the files. It is a no-op once the table has a project, so a rerun duplicates no row and keeps a later edit. A file that sets neither flag writes no `project_settings` row, so `Store::migrate_global_auto_merge` still applies the old global auto-merge to an imported project exactly as it did to the file. The `checks` command is set at onboarding and edited afterwards in the Local checks card on `/settings/projects/{project}`. The card is a form of its own that posts to `POST /settings/projects/{project}/checks` behind `visible_project`, so a login that is not a collaborator gets the same 404 as for an unknown project. It carries a CSRF token, because the value is a bash command the worker runs. The handler trims the value and stores `NULL` for an empty one, which means no local checks. `Store::save_project_checks` writes only `projects.checks` of that project. Any collaborator may edit it. The card and the onboarding field share one label and hint, so the wording cannot drift. The scheduler reads the project on every pass, so the next checks run of any job uses the new command, including jobs created earlier and a failed job retried into `verifying`. A checks run already in the worker keeps the command it started with. The command is not validated or test-run when saved, as at onboarding. The project page also has a Worker packages card, see Worker packages. |
| Worker packages | A project lists nixpkgs packages in the `project_packages` table, one JSON list per project, empty by default. Any collaborator edits it in the Worker packages card on `/settings/projects/{project}`, a form of its own with a CSRF token that posts to `POST /settings/projects/{project}/packages` behind `visible_project`, so a login that is not a collaborator gets the 404. The card has one textarea with one package per line, which works without JavaScript. An entry is a nixpkgs attribute path matching `[A-Za-z0-9_+-]+(\.[A-Za-z0-9_+-]+)*` of at most 128 bytes. A list holds at most 32 entries, a blank line is dropped and a duplicate collapses into its first place. A bad entry gives a 400 that names it and saves nothing, so `nixpkgs#foo` and `foo;rm -rf /` are refused. The scheduler reads the list on every agent and checks run, so a change reaches a job at its next run, and a run already in the worker keeps what it started with. With a non-empty list the runner puts a fixed bash script between the image and the run's command: `bash -c <script> factory-worker-packages <count> <package>... <command>`. The count, not a separator, ends the package list, so no package name can collide with the command. The script runs `nix build --no-link nixpkgs#<package>...` and exits with code 86 when that fails. It then runs `nix shell nixpkgs#<package>... --command <command>`, and the command writes a line to a deleted temporary file that the script holds open on a descriptor, so cleanup of temporary files by the command cannot erase the signal and nothing is left behind. The script exits 86 when the shell ends without that line, which is a setup failure after the build, and otherwise passes on the command's exit code. A command that exits 86 itself becomes 1, so 86 always means setup failed and a checks command that fails with 86 is still `ChecksFailed`. The package names are argv elements and never part of a shell string. A checks run of a project with packages runs `bash -c <command>` and not `bash -lc`, because the image's `/etc/profile` resets `PATH` and would drop the packages. With an empty list the `podman` arguments are the same as before. Packages resolve from the unpinned `nixpkgs` registry reference that the prompt already tells agents to use, so a version can change between runs, and they land in the shared `/nix` volume, so a later run reuses them. Other containers, such as the agent login containers, are not affected. A package set that cannot be built fails an agent run with a reason that starts "the worker packages (a, b) could not be installed" and ends with the tail of nix's error, and the job page's Retry works once the list is fixed. For a checks run it is a checks error, which the factory retries later, not `ChecksFailed`, so the report does not go to the agent as something to fix. Worker packages are how a project supplies what a stdio MCP server needs, see MCP stdio servers. |
| Project display name | A project has an optional display name, the nullable column `projects.display_name`. The migration is additive, so an existing project has none and shows its identifier. URLs, form fields, the `factory_project` cookie, table keys, secrets, forge tokens, job directories, logs, agent prompts, branch names, and commit and pull request text keep the identifier, so a save changes no keyed row and running jobs carry on. | Project collaborators | Each project has a set of collaborator logins, the only logins that may see and act on it. They live in the `project_collaborators` table in SQLite, one row per `(project, login)`: the project name, the login, the login that added it, and an added-at time. A login is the value `user()` returns, the `Tailscale-User-Login` header or `local` when it is missing. Onboarding a project writes the onboarding login as the first collaborator in the same transaction as the project row, so the person who onboarded a project can see it at once, see Project registry. `Store` carries the rest of the data model: `collaborators` lists a project's rows, `is_collaborator` tests one login, `projects_for` lists a login's projects, `add_collaborator` inserts a row and leaves an existing one unchanged, and `remove_collaborator` deletes a row but refuses the last one with `StoreError::LastCollaborator`, whose message is "A project needs at least one collaborator. Remove the project instead.", so a project is never left visible to nobody. A one-time migration at startup, `Store::migrate_project_collaborators`, seeds the projects that predate this table: each project with no collaborator rows gets one row for every distinct `requested_by` login in its jobs, added by `migration`. A project with no jobs gets no rows and is named in a warning log, because it is then visible to nobody until an admin adds a collaborator. The migration skips any project that already has a row, so it runs once per project and a later edit survives a restart, the same pattern as `Store::migrate_project_gates`. The access checks that read this table limit the board, the job routes and the project settings pages to a project's collaborators, see Dashboard access. A project's settings page carries a Collaborators card: it lists every collaborator with who added it and when, an "Add collaborator" field that takes a typed Tailscale login, and a Remove button on each row. Adding and removing both post to routes under `/settings/projects/{project}/collaborators`, each behind `visible_project`, so only a collaborator may change the set. A typed login is trimmed; an empty one, or one already listed, is refused on the page with a message and adds nothing, since the factory keeps no user list to check a login against and a duplicate would be a no-op. Any collaborator may add or remove any collaborator, itself included, while more than one remains, so a small team needs no owner role; roles are a later change. The row also holds `use_my_account`, the login's "Use my account" switch for the project, off by default, added to existing databases by an `ALTER TABLE` guarded by a pragma check. Removing a collaborator removes the switch, so a job that login requested moves to the project token at its next operation. The Forge account card on the project's settings page holds the project token, and the card holds the switch in a second form. Its save bars are not sticky, so the first one cannot cover the second form. Any collaborator saves or clears the project token. The routes `/settings/projects/{project}/forge-token`, `/forge-token/clear` and `/use-my-account` sit behind `visible_project` and a CSRF token. The switch handler writes only the row of `user()`, since the form names no login. When the switch is on and the login has no token for the project's forge, the card says so and links to `/settings/forges/<forge>`. While a project has no project token, its board and settings page show a notice that jobs without a personal account cannot run, linking to the card. Jobs do not read the switch or the tokens yet. The Remove button is left off when one collaborator is left, and a crafted POST that would remove the last one is refused with the `LastCollaborator` message, because a project with no collaborator is visible to nobody, so its sole collaborator removes the project instead. A login that removes itself can no longer see the project, so it is redirected to `/settings` rather than back to a page it may not read. The sole collaborator removes the project, see Project removal. |
| Project removal | A collaborator removes a project from the "Remove project" card at the bottom of its settings page. The card posts to `POST /settings/projects/{project}/remove` behind `visible_project`, and the removal goes ahead only when the typed name equals the name the page shows, the display name when set, else the project name, the same confirmation as deleting an MCP server, compared exactly, without trimming. A wrong name, including the identifier when a display name is set, redraws the page with "Nothing was removed." and changes nothing. `Store::remove_project` does the work in one transaction, so a failure leaves the project whole. It applies `Event::Cancel` to every job of the project that is not merged, failed or cancelled and writes the factory log line "Cancelled because the project was removed." The handler then wakes the scheduler, so `stop_unwanted` ends the container the way the Cancel button does. It deletes the project's rows in `projects`, `project_models`, `project_settings`, `project_gates`, `project_efforts`, `project_agents`, `project_mcp`, `project_mcp_tools`, `project_mcp_tool_refreshes`, `project_totals`, `project_collaborators` and `project_maintenance`, its MCP header values in `secrets`, and the `job_costs` rows and `cost` rows in `job_events` of its jobs. The cost history and the stored tokens go because the requester asked for them gone. A run that ends after the removal cannot bring the cost back: `remove_project` records the project's job ids in `cost_closed_jobs`, and `add_cost` and `add_session_cost` skip those jobs, so the write is refused inside the same database that holds the deletion, whatever the scheduler is doing. The job rows, their logs and `<data_dir>/jobs/<id>` stay until Job expiry deletes them at 30 days, and open pull requests on GitHub are left alone. With no collaborator left, nobody can see those jobs, and the scheduler already fails or skips a job whose project is unknown, so it needs no special case. Onboarding a name whose earlier project still has job rows deletes those jobs first, the way expiry does, so the new project's collaborators never see the old jobs. If one of them still has a scheduler task, onboarding is refused with "Try again in a minute.", because deleting a job under a running container would orphan it. `WorkerSlots` is the one registry of the scheduler's tasks: an entry per job for any task it spawns, a worker or a factory step, with the handle and an id. A task removes only its own entry when it ends, so a task that ends late cannot remove the entry of the task that replaced it, and the entry and whether the job has a task are one record, with no second marker that could disagree. For a job it stops, `stop_unwanted` keeps the entry, marked as stopping, until the task is gone and `executor.stop` has returned, so a stop in progress also blocks the deletion. The scheduler also holds a pass lock in `WorkerSlots` for each whole pass over the jobs, stops included, and the leftover cleanup takes the same lock. A pass therefore never works from a job list that is older than a deletion, a task is never spawned for a job the cleanup is about to delete, and the cleanup never sees a stop half done. A queued job that a removal cancelled after the pass read it is skipped, not treated as an error. One lock serializes the name check, the leftover cleanup and `create_project` across onboarding requests, so a second request for the same name sees the new project and deletes nothing. Success redirects to `/settings` with the notice "Removed project <name>." in the query string, which `/settings` passes on to the page it redirects to. |

| Project maintenance settings | A project has a "Renovate pull requests" switch and a "Packaging project" switch, both off by default, and five packaging fields: type (`snap`, `deb` or `other`), manifest files, build config files, the upstream repository and the upstream forge. They live in one row of the `project_maintenance` table, keyed by project, with the two path lists stored as JSON arrays. A project with no row reads both switches off, so existing projects need no migration. `Store::save_project_maintenance` writes the whole row, and turning packaging off clears the packaging fields. The Maintenance card on the project's settings page is its own form and posts to `POST /settings/projects/{project}/maintenance` behind `visible_project`. The page renders the packaging fields only while "Packaging project" is on, and leaves them out of the markup instead of hiding them with CSS. The fields first appear after an operator ticks the switch and saves. That save is refused for the missing manifest file, and the redraw shows the fields with the posted values and the switch still ticked. This needs no JavaScript. `Maintenance::check` holds the validation, so the handler and the tests share it. A save with packaging on is refused, with the message shown and the stored row unchanged, unless Renovate is on, at least one manifest file is given, and the upstream repository is valid for the upstream forge. `Maintenance::check` asks that forge's `valid_repo`: `owner/name` on GitHub and a path of two or more segments on Salsa. An unknown type or an unknown upstream forge is refused too. The two path lists come from textareas, one path per line, each trimmed and empty lines dropped. An empty build config list is valid. Packaging requires Renovate because the packaging analysis runs only after a merged Renovate pull request. Nothing acts on the switches yet. A save with Renovate on, whether or not packaging is on, also checks the project account, after `Maintenance::check` and before the write, on every such save. With no project token the save is refused and the message points at the Forge account card, because Renovate runs as the project account. With one, `Forge::access` reads what the account may do in the repository. Not visible is refused with the account named. Read saves with a warning that the factory cannot rerun failed CI and cannot merge Renovate pull requests, even with auto-merge on. Write and Admin save with no warning. A check that cannot run, such as an unreadable token or a failing forge call, saves and says the access was not checked. Re-checking on every save is simpler than tracking when the switch turned on, and it lets a granted Write clear the warning. A token the factory cannot read, because the secret store has no stored token for the project, is refused as missing, so account metadata alone never counts. The forge call is awaited between the access check and the write, so `Store::save_project_maintenance_guarded` writes in one transaction only while the project instance and the saving collaborator still exist and every token row the checks used still holds the sealed bytes they used, or is still absent when they found none. The Renovate check returns the sealed project token it used. `Accounts::upstream` returns the rows its credential came from with the same bytes, read in the one snapshot that opened the token, and the check uses that credential, so no gap separates the credential from its guard. The comparison is on bytes, so a replacement by another token of the same account is caught too, and so is a token saved or cleared while an anonymous check was in flight. Turning Renovate off builds no credential guard and needs no forge, so it works for a project on an unknown forge. Otherwise nothing is written and the page asks for the save again. The row also has a `renovate_author` column, added by ALTER, for the Renovate account. The card shows the "Renovate account" field only on a project whose forge is Salsa, because Salsa has no fixed Renovate account: self-hosted Renovate opens merge requests as whichever user owns its token. A Salsa save with Renovate on and the field empty is refused, and a name with a character outside letters, digits, `.`, `_` and `-` is refused. The handler holds both checks, since `Maintenance::check` does not see the forge. A GitHub project stores no author and shows no field. The Maintenance card also has an "Upstream forge" select, stored in `project_maintenance.upstream_forge` and read as the project's forge when NULL. The card has one upstream token field per forge, each with its status and its own Save and Clear buttons. A button's `formaction` names its forge, `.../upstream-token?forge=<forge>` or `.../upstream-token/clear?forge=<forge>`, and posts the card's draft. The handler parses that forge and answers 400 for an unknown value before it calls a forge or touches a token, and the select never decides the target, so the status shown and the action always match and a private upstream on another forge can be configured from scratch. They redraw the draft. A project keeps one upstream token, whose account row records its forge. Clearing one forge's token leaves a token stored for the other, and saving one replaces it. The "Check connection" button posts the card to `.../maintenance/check`, reads the upstream with the credential a job would use, shows which credential it used and whether the repository was readable, and stores nothing. A save with packaging on runs the same check. An unreadable upstream refuses the save with guidance to save an upstream token or correct the forge or path. A check that cannot run saves and says the upstream was not checked. |

| Agent effort | Each stage's agent run passes the effort level to the agent, so no run relies on the CLI's own default. Claude takes it as `claude --effort <level>`. Each agent carries its own levels and default in `factory-core`, because the CLIs disagree: Claude's `--effort` takes `low`, `medium`, `high`, `xhigh` and `max`, Codex's `model_reasoning_effort` takes `minimal`, `low`, `medium`, `high` and `xhigh`, and Copilot's `--effort` takes `low`, `medium`, `high`, `xhigh` and `max`. | Project agents | Each project chooses an agent for each of the clarify, spec, plan, implement and review stages, next to the stage's model and effort. The choice lives in the `project_agents` table in SQLite, one row per project with a column per stage, the way `project_efforts` does. A project with no row runs every stage on the default agent, `claude`. The store creates the table when a database that predates it opens, so an existing project reads `claude` for every stage. The store accepts only the id of an available agent, `claude`, `codex` or `copilot`: an unknown id returns an error and writes nothing. The settings save handler validates the agents before it writes the agents, efforts and models, so a rejected agent stores none of the three. The scheduler picks a run's agent from the same stage mapping as the model and the effort, so check fixes, CI fixes, rebases and review-comment runs use `implement`, and clarify answer runs use `clarify`. Each agent carries its own effort levels, so a stage's saved level is valid only against the agent it is saved with, and the save handler checks each effort against the same stage's agent, see Agent effort. The stage panel's agent control and the model and effort it offers for the selected agent, including the effort redraw when the agent switches, are covered in Settings layout and Agent effort. | Request attachments | The New request form posts multipart. A request carries at most 5 attachments of at most 10 MiB each, images and files counted together, and the request text may be at most 256 KiB. The handler checks each upload by its bytes, not by file name or declared type, in this order: the PNG, JPEG, GIF and WebP signatures are images; a `PK\x03\x04` or `PK\x05\x06` signature is a ZIP file; valid UTF-8 with no NUL byte, which allows a leading byte order mark, is a text file. Anything else, including a PDF, a UTF-16 file or a named zero-byte upload, gets a 400 that names the accepted types. A request over a limit, or one with attachments and no text, also gets a 400 and creates no job. An SVG file passes the text check and is stored and served as text, so the dashboard never renders it as an image. The factory saves each image as `<data_dir>/jobs/<id>/images/image-<n>.<ext>` and each file as `<data_dir>/jobs/<id>/files/file-<n>.<ext>`, where `<ext>` is `txt` or `zip`, under a name it generates, so an upload's file name never reaches the file system. The image names are recorded in a `job_images` table. Each file is recorded in a `job_files` table with its generated name and its original name, which is the upload's file name cut to its last path component and 255 characters, used only for display, the download name and the prompt. `factory-core`'s `Job` holds no attachment data, since it does no I/O. Job expiry deletes the `job_files` rows with the job, and its `files/` directory goes with `<data_dir>/jobs/<id>`. A small script, `static/paste-images.js`, attaches an image pasted into the request textarea to the file input, previews a picked image as a thumbnail and any other file as a document or archive icon with its name, each with a Remove button, and leaves the form working without the script. The job page shows the images next to the request and lists each file below as an inline-SVG icon tile, a document icon for a text file and an archive icon for a ZIP file, with the original name as the caption. An image is served from `GET /jobs/<id>/images/<name>` and a file from `GET /jobs/<id>/files/<name>`, each serving only a name its table lists for that job. A text file is served as `text/plain; charset=utf-8` and a ZIP file as `application/zip`, both with `X-Content-Type-Options: nosniff` and a `Content-Disposition: attachment` header whose download name is the original name, percent-encoded in a `filename*=UTF-8''…` parameter so it never enters the header unencoded. When a run starts a fresh session, the runner copies the images into the checkout under `.git/factory-images/` and the files under `.git/factory-files/`, which git does not track, so the checkout stays clean. It appends the image paths to the prompt and tells the agent to look at them, then lists each file with its worker path and original name; for a ZIP file it tells the agent to list the archive with `unzip -l` and unpack it with `unzip -d` under `.git/factory-files/` and not to copy its contents into the repository unless the request asks for that. The worker image installs `unzip` for this. The clarify run is the first such run. A run that resumes a session adds nothing, because the session already has them. While a job waits in `requested`, its text and attachments can still change; see "Request editing". |
| Request editing | A job waits in `requested` until a worker is free and its prerequisites have merged, shown on the board as queued, waiting or blocked. While it is in `requested`, whatever the board shows, the text and attachments stay editable and the request card shows an Edit link to `GET /jobs/<id>/edit`, a form that posts to `POST /jobs/<id>/edit` as multipart. Once the scheduler applies `Event::Start` and the job moves to `clarifying`, the request can no longer change: the GET redirects to the job page, the card drops the Edit link, and a POST from a stale page gets a 409. The edit form starts the textarea with the current text, shows each current image and file with a Remove checkbox that posts the attachment's stored name, and reuses `static/paste-images.js` for the file input. The POST applies the New request rules: the trimmed text must be non-empty and at most 256 KiB, each new upload is classified by its bytes and is at most 10 MiB, and the kept attachments plus the new ones are at most 5. A `remove` value that names no stored attachment, or any broken rule, gets a 400 and changes nothing. `factory-core` gains `Event::Edit { request }`, which applies only at `(Requested, Factory)`, replaces the request text, leaves every other field alone, and records an `edit` history row; in any other stage or turn it returns `Rejected::Unexpected`. The kept attachments keep their old order and come before the new uploads in upload order, and the factory renumbers images and files from 1, each type apart, as the New request handler does, so the name-sorted directory listing a run reads matches the table order. A kept file keeps its original name; a new one takes the upload's name by the usual rule. To keep the edit and the scheduler's `Event::Start` from racing, the handler writes the new attachment set to a `staging/` directory under the job, then in one store transaction, under the connection mutex that `Event::Start` also takes, checks the job is still `requested`, swaps the staged set in over the old one, replaces the `job_images` and `job_files` rows, and applies `Event::Edit`. So the edit either lands before Start, and the clarify run reads the new text and attachments, or it is rejected with a 409 and changes neither the store nor the files. A disk error before the commit restores the old set, returns a 500 and leaves the job queued, unlike `create_job`, which cancels a job whose attachments fail to save. An edit keeps the job's id, created-at time, project and gates, so it holds its place in the scheduler's oldest-first order. The timeline shows the edit as "You edited the request" in the created step. The edit form also carries the "Start after" picker of the New request form, built by the same helper, with the job's current prerequisites ticked and the other eligible jobs of the project unticked, so the requester can change the jobs it waits for while it waits. A current prerequisite that is no longer eligible, for example a cancelled one, stays listed and ticked with its state in brackets so it can be unticked. The job itself and any job that waits for it, directly or through others, are never offered, because they would form a cycle. Every current prerequisite, live or deleted, is a `keep` checkbox whose value is its `job_prerequisites` row id, ticked, labelled with its stored state: "merged" for a job deleted after it merged, "deleted before it merged" for one deleted otherwise. A new pick is an `after` box that posts a job id. The row id keeps a stale form from swapping a deleted prerequisite for a new job that reuses its id, and keeps two deleted rows with the same number apart. Saving replaces the whole set with the posted one in the same transaction as the text and attachment edit, under the same mutex: it deletes the rows whose id is not in `keep` and inserts each `after` id that is not already a live row. Posting none clears the set, and the job then starts when a worker is free. `Store::edit_request` takes the set as a `PrerequisiteEdit` and checks it before the directory swap, so a rejection changes neither the files nor the rows. It applies the `POST /jobs` rules to each `after` id, and also rejects the job's own id and any id from which a walk over live `job_prerequisites` rows reaches the edited job, a cycle. A `keep` id that is not a row of the job is rejected too. Each rejection is `StoreError::InvalidPrerequisite`, a 400 that changes nothing, and a value that is not a number is a 400. When the set changes it records a `prerequisites` history row whose detail is the new set, like "#12, #15", or "none", and the timeline shows it in the created step as "You changed the jobs this waits for". A POST after the job started is a 409 and leaves the set alone. Editing a job past `requested`, reordering attachments, and keeping earlier versions are out of scope. |
| Job expiry | The job loop deletes a merged, failed, cancelled or dismissed gap job once its `created_at` is more than 30 days old. The age counts from the request, not from the day the job finished. A dismissed failed job is still failed, so it expires at 30 days like any other failed job and keeps its directories until then, see Job dismiss. A dismissed gap job is at `Stage::Dismissed`, which `is_finished` counts, so it expires the same way. The factory deletes the job row, its rows in the other tables, and `<data_dir>/jobs/<id>`. A job that is not finished stays however old it is. Removing a project leaves its jobs for this expiry, see Project removal; re-onboarding the same name deletes them early. When one job fails to delete, the loop logs it and goes on with the others, and the next pass tries it again. A merged job loses its checkout and session well before this, see "Merged job cleanup"; the directories being gone already does not stop the full deletion at 30 days. |
| Request prerequisites | A request can wait for other jobs of its project. The New request form has a "Start after" fieldset inside the expanded part of the form, one checkbox `name="after" value=<id>` per eligible job, so it posts a repeated field and works without JavaScript. It is not shown when no job is eligible. `Job::can_be_prerequisite` decides what the form offers: any job that is not finished, and a failed job that can retry and is not dismissed. Renovate jobs and gap jobs at `proposed` are never offered. `POST /jobs` is looser, by `Job::accepts_as_prerequisite`, which refuses only a Renovate job and a job at `proposed`, because a job can merge, fail or be cancelled between the page load and the submit, and that must not reject the request. A merged prerequisite is accepted and counts as met, and a failed or cancelled one is accepted and shows as blocked. A repeated id counts once, and a non-numeric value is a 400. `Store::create_after` loads each id inside the transaction that inserts the job, and an id that names no job, a job of another project or a job that is not accepted returns `StoreError::InvalidPrerequisite`, a 400 with one message for all of them so nothing leaks about other projects. Nothing is created then. The ids go in the `job_prerequisites` table, one row per pair, with a unique index on (`job_id`, `prerequisite`) where `gone` is null. The row holds its own id because SQLite reuses the id of a deleted job: `jobs.id` is a plain `INTEGER PRIMARY KEY`, so deleting the newest job frees its id for the next one, and a row that only held the number would make a new job the prerequisite. `Store::delete_job` instead sets `gone` to `merged` or `unmerged` and `title` to the first request line on every live row that names the deleted job, and deletes the rows of the deleted job itself. The queries join `jobs` only on rows whose `gone` is null, so a reused id never takes the place of the job that was deleted. A prerequisite counts as met when it is at `merged`, or was deleted after it merged. It is blocked when it is cancelled, dismissed, failed (retryable or not) or was deleted before it merged, because none of those can merge until someone acts: retry the failed job, remove the dependency, or cancel the waiting job. Anything else is pending. `factory-core` folds the states into `Wait`: `Ready` when none is left, `Waiting` with the ids of the unmet ones, or `Blocked` when any of them is blocked. The factory never cancels or starts a blocked job by itself. If the prerequisite is retried and merges, the job starts as normal. The scheduler starts a requested job with `Store::start` instead of applying `Event::Start`. It reads the job and its prerequisites and applies `Start` in one transaction under the connection mutex, and returns `None` while any is unmet, so the job takes no worker slot and the loop goes on to the next job. The check and the start share the lock that a request edit takes, so an edit of the prerequisites lands before the start or gets a 409. The requester can change or clear the set while the job is in `requested`, on the edit page (see Request editing). A waiting job keeps its `created_at`, so the queue order and the 30-day expiry are as before, and it does not expire, because it is not finished. When the last prerequisite merges, the next pass with a free worker starts it, and it clones the base branch then, so it sees the merged changes. It does not build on an unmerged branch, which would need stacked pull requests. The board reads every job's wait in one query, `Store::waits`, and `status()` takes the wait: waiting is in Running with the badge "waiting", blocked is in You with the badge "blocked". Notifications use the same function, so a blocked job notifies as any job that enters Needs you, and there is no new kind. `Store::prerequisites` reads one job's rows for the job page, each with the prerequisite job, or `None` once it was deleted, and the same state the fold uses. The page folds them again with `Wait::fold`, so the card and the board agree. The status card of a requested job with unmet prerequisites replaces "Waiting for a free worker." with the prerequisites: a link to `/jobs/<id>`, the first request line (the stored title for a deleted one, shown as plain text with no link) and its stage label, or "deleted before it merged". A waiting card has the badge "waiting". A blocked card uses the needs-you look with the badge "blocked", says the job will not start until the blocked jobs merge or are removed from the list, and links to `/jobs/<id>/edit`. After the job starts, a "Queued after #12, #15" line with the same links stays on the page, because the prerequisite rows stay. It is its own region, `#job-queued-after`, below the status card, not part of the request card. The status card and that region are both in the job fragment, so the existing poll shows a prerequisite's failure and, when the job starts, swaps the prerequisite list from the status card into the history line. |
| Merged job cleanup | A merged job is final: no event moves it out of `Merged`, it has no next command, and Retry applies only to failed jobs, so nothing reads its checkout or session files again. On every job-loop pass, after expiry, the factory deletes `<data_dir>/jobs/<id>/work`, `<data_dir>/jobs/<id>/claude` and `<data_dir>/jobs/<id>/codex` for each merged job that still has any of them. `work/` is the git checkout the workers and checks run in, which holds build output such as cargo's `target/`; `claude/` is the Claude Code config directory with the session files `--resume` reads, and `codex/` is Codex's `CODEX_HOME` with its session rollout files. On moon the merged jobs' directories had grown to about 50 GB of the 74 GB free disk, which this frees. The check runs every pass, not only on the transition into `Merged`, so it also cleans jobs merged before this change and retries a deletion that failed. The pass skips a merged job while the scheduler still holds an unfinished task for it. A deletion error is logged with the job id and the loop goes on, the way expiry does, and a directory already gone counts as success. After the directories are gone the factory appends one line to the job log saying it removed the checkout and session files to free disk space, written only on the pass that deleted something, so a job does not collect the line on every pass. Everything else stays: the job row and its rows in the logs, events, costs, sessions, images, files and PR watermark tables, and the `images/` and `files/` directories the job page serves, so the page, its attachments and the board look the same as before. Failed and cancelled jobs keep their directories, because Retry resumes a failed job from them; a cancelled job could get the same treatment in a later change. |
| Capacity | At most 2 worker containers at a time. Each worker gets `--memory 3g --cpus 4`. A job waiting for you holds no worker, and neither does a request that waits for other jobs to merge, see Request prerequisites. The limit, image, memory and CPUs are settings stored in SQLite, read by the job loop on every pass, so a settings page can change them without a restart. The scheduler records which job holds which numbered slot, and since when, in a `WorkerSlots` handle it shares with the dashboard. A worker run takes the lowest free slot number when it starts and frees it when it ends or the job no longer wants it. Checks run in a worker and take a slot too. Factory steps such as a push or a pull request watch run in the factory process and take none. The board shows one tile per slot above the request bar, as many as the worker limit. A busy tile links to the job and shows its stage and how long it has held the slot. A job of another project shows that project's name, because the slots are shared by every project. An idle tile says idle. When the factory runs without podman workers, every tile is idle. |

The right one holds the timeline, which replaced the nine-step tracker under the title. In the two-column layout the timeline stays in view under the top bar as the left column scrolls, and scrolls on its own when it is taller than the window. Below 900px the columns stack, with the timeline between the status card and the request. The timeline reads the job history, see Job history. It lists the four planning steps, then a group for each planned pull request with its four steps, then merged. | Job cost | Each job has a running total of the API cost of its agent runs, in USD. It lives in the `job_costs` table in SQLite, one row per job, so a job from before the table existed has no row and reads 0. `Scheduler::record_run_cost` adds the cost after each run: a Claude run reports `total_cost_usd`, the cost of its whole session so far, which keeps counting across `--resume`. The `sessions` row keeps the last total in `cost_usd`, and the run adds the increase over it. A total below the stored one means Claude started the session over, so the run adds the whole total. A session from before the column existed has no stored total, so its next run adds its whole total once. Before this rule the factory added every total as it was, so a resumed session counted its earlier runs again: job 41 showed $20.90 for its ci-and-review stage, which cost $1.18. A run that reports no figure adds nothing. A Copilot run adds no cost row and no estimate, since Copilot bills in credits the factory does not price. `Scheduler::record_run_cost` writes one job log line per Copilot run, "Copilot runs are not counted in the cost", and a job that ran only on Copilot shows "–". A Codex run reports token counts and no dollar figure, so the factory estimates it from a price table, see below. A cancelled or failed job keeps its total. `format_cost` formats it as `$1.23`, for the log and the job page. The job page shows the total as a pill badge on the title row, right-aligned and vertically centred with the heading, out of the meta line. When any of the job's cost rows is an estimate the pill carries a `≈` and a title that says the total includes an estimate for Codex runs. A job with no recorded cost shows "–". The job board shows it on each card. The stats strip shows the project total, see Project totals. **Codex estimate.** The `codex_prices` table in SQLite holds one row per model id with three USD prices per million tokens: input, cached input and output. The table starts empty, and the Codex settings page adds, edits and deletes a row, so a price change needs no code change or deploy. A Codex run sums the `usage` of every `turn.completed` line. `cost::codex_cost` reads the row for the model the run passed and bills the uncached input, `input_tokens` minus `cached_input_tokens`, at the input price, the cached input at the cached price, and `output_tokens`, which already counts `reasoning_output_tokens`, at the output price. The estimate goes through `Store::add_cost` with its `cost` row in `job_events` marked `estimated`, so it counts in the job total and the project totals like a reported cost, and `Store::has_estimated_cost` tells the job page to flag the pill. When the run passed no model, or the model has no price row, the run adds no cost and the job log names the model; the run's token counts go to the log either way. A price change applies to runs after it, and recorded costs stay as they are. |
| Job history | The `job_events` table in SQLite keeps what happened to each job, one row per entry, oldest first by id. `Store::apply_in` writes a row in the same transaction as every event it applies, except an `Event::RenovateObserved` that leaves the job unchanged, which writes nothing so the timeline does not grow on each look, so the history and the stored job cannot disagree, and a rejected event writes nothing. A row has the time, the event name, and the stage, pull request index and turn the event left the job in. `Store::create` writes a `created` row, and `Store::add_cost` writes a `cost` row with the run's cost in USD against the stage the run ran in, because the scheduler adds the cost before it applies the run's event. `Store::record_mcp_tool_call` writes an `mcp-tool-call` row the same way, against the stage the job is in, for each MCP call the proxy forwards, see Job MCP tool calls. A failed agent or reviewer run and a CI rerun keep their reason in the row. The names come from `Stage::name`, `Turn::name` and `Event::name` in `factory-core`, such as `implementing`, `agent:fix-checks` and `review-approved`. They are stored, so renaming one breaks the history of stored jobs. A job from before the table has entries only from the table's first deploy on. Job expiry deletes a job's rows with the job. The job page timeline reads it. The fix events store as `fix-started`, `fix-ended`, `rebase-requested`, `rebase-skipped` and `rebase-failed`. |
| Project totals | The `project_totals` table in SQLite keeps one row per project with the total API cost, the number of jobs created and the number of jobs merged. The totals outlive the jobs: the expiry loop deletes a job and leaves them alone. Each counter changes when its event happens. A job counts as created when the store inserts it, so cancelled and failed jobs count as created and nothing more. A job counts as merged when it first reaches the Merged stage, once per job however many pull requests it had, and not when one of its pull requests merges. A job that fails or is cancelled after some pull requests merged is not merged. Cost adds the amount of each agent run, next to the job's own total in `job_costs`. Jobs from before the table existed are not counted, so the totals start at zero. `Store::project_totals` reads them, and a project with no row reads 0. The index page shows them on one line below the board, for the selected project: total API cost, jobs created, jobs merged, merge rate and average cost per merged job. `merge_fraction` computes the merge rate as merged divided by created, and returns 0.0 when nothing was created. The line shows it rounded to a whole percent. The average is total cost divided by merged, formatted with `format_cost`. Created and merged show "–" at zero. The merge rate shows "–" with no jobs created, and the average shows "–" with no merged job, so nothing divides by zero. Total cost shows `$0.00` at zero. |
| Job retry | A job that failed because it used up its 5 failed check or CI rounds, because its local checks could not run 5 times in a row, or because an agent run failed, can be resumed from its job page. The failure card shows a Retry button, which posts to `POST /jobs/{id}/retry` (an optional project, like approve). `Event::Retry` returns the job to the `verifying` or `ci-and-review` stage of the pull request it failed on, with a factory turn, and resets the failed-round count and the checks-error count, so the factory runs the checks or watches the pull request again and the agent gets 5 fresh rounds. A job whose checks could not run 5 times in a row ends in `failed` with the `verifying` retry target, and Retry reruns the project's current checks command with 5 fresh attempts. The failure card for this job also shows a sentence to revise the project's local checks command or retry, and a link to `/settings/projects/<name>` in the same tab. The page decides this from `Job::checks_could_not_run`, not from the reason text, so any other failure keeps the plain card. A job whose agent run failed, such as one stopped by the plan's 5-hour usage limit, keeps the stage and task of that run as its retry target, and `Event::Retry` runs the same task again in the same stage. The stage picks the session, so the run resumes the session that failed, in the same checkout, and keeps the failed-round count, because a failed agent run is not a failed round. When the run died mid-rebase, the checkout aborts the unfinished rebase before the next run, so the agent can start it again. A `Stage::Failed` keeps the retry target, so the core decides where a retry resumes. `Job::can_retry` reports whether a retry would resume the job, and the button and the endpoint both read it. A job stored before the target existed, such as jobs/10, carries none. The factory recognises it by its exact old reason, or for an agent failure by a reason that starts with "the agent run ended with", such as jobs/17 and jobs/20, and resumes at `ci-and-review` of its highest-numbered pull request. Watching that pull request finds the work left, or finds it merged and moves on to the next pull request. A legacy job with no pull request number is not retryable. A job closed unmerged, and a cancelled or merged job, reject `Retry`. Retry works on a dismissed failed job the same as on any failed job, see Job dismiss: it moves the job out of `Failed` and so clears the dismissal, and a later failure shows in the Failed section again. A stopped review retries too: a job in `ci-and-review` at `ReviewStopped` with a pull request number shows the Retry button, and where it resumes depends on why the review stopped, recorded on the ask as `ReviewStop`. A reviewer run that failed reruns the reviewer in its session; a review that hit the cap of 5 sends the last feedback to the implement session with 5 fresh rounds. A job stored in `ReviewStopped` before the field existed, such as jobs/28, retries as a reviewer failure. A stopped Renovate job retries too: `Event::Retry` at `Ask::Renovate` with the stopped state resets both rerun counts and reruns the failed CI runs, see Renovate pull request jobs. A ready or unsafe Renovate job has no Retry. A Renovate job whose agent run failed retries as any other failed agent run. The retry does not touch `created_at`, so the 30-day expiry still counts from the request. |

## Claude plan usage source

The board shows one account-wide tile with the Claude subscription limits: the 5-hour window, the weekly window and the Fable window. The factory runs Claude Code with the token from `claude setup-token`, see "Claude auth".

### The usage endpoint does not work with a setup token

The first version of the tile fetched `GET https://api.anthropic.com/api/oauth/usage?skip_spend=1` every 5 minutes with the factory's token. A spike on 2026-11-20 chose it as the endpoint the interactive `/usage` panel calls. Every authenticated call in the spike returned HTTP 429, so it never saw a 200 body. On moon every fetch returned 429 too, including the first one after a restart, so the tile never showed.

A `claude setup-token` token carries only the `user:inference` scope. The Agent SDK reference says such a token "doesn't qualify" for the `/usage` report "because it carries only the `user:inference` scope". Claude Code 2.1.330 checks that its token has the `user:profile` scope before it calls `/api/oauth/usage`, and makes no call when the scope is missing. So the endpoint is the source for a `claude login` token, not for ours. The 429 also carried `retry-after` of up to an hour, which the 5-minute poll ignored.

`claude -p "/usage"` is no source either. In print mode `/usage` resolves to the local session-cost command and prints this session's cost, not the plan limits.

### Decision: read the windows from worker runs

The API sends the plan windows in `anthropic-ratelimit-unified-*` response headers on every inference request, whatever the token's scopes. Claude Code reads them and, in `-p` stream-json mode, writes a `rate_limit_event` line:

```json
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":1795234800,"rateLimitType":"five_hour",
 "unifiedWindows":{"five_hour":{"utilization":0.77,"resetsAt":1795234800,"status":"allowed"},
                   "seven_day":{"utilization":0.33,"resetsAt":1795676400,"status":"allowed"}}}}
```

A run on moon with the factory's token wrote this line on 2026-11-21. `utilization` is the fraction of the window used and `resetsAt` is a Unix timestamp. `unifiedWindows` holds a `five_hour`, `seven_day` and `seven_day_overage_included` entry for each window the API reported. Claude Code labels `seven_day_overage_included` "Fable limit", so the tile shows it as Fable. An event from a Claude Code version without `unifiedWindows` reports one window, named by `rateLimitType`, with `utilization` and `resetsAt` at the top level, and the parser reads that shape too.

The runner's stream parser turns the line into `StreamItem::PlanUsage`, and `factory_runner::run` passes each report to a callback. The podman executor's callback writes it into the `PlanUsageCache` the dashboard reads. Each window in a report replaces the cached one, and a window the report leaves out keeps its last value. The factory makes no request of its own for plan usage, so it spends no tokens and meets no rate limit on it.

The numbers move only while a worker runs. Usage from interactive sessions on the same account shows up at the next run's report. The tile therefore shows the time of the last report, and a window whose reset time has passed reads as reset rather than show the old number. The tile has no per-model windows beyond Fable, because the event carries none.

Risk: `rate_limit_event` is part of Claude Code's stream-json output, which carries no stability promise. If the line changes shape the parser drops it, the cache keeps its last report, and the "as of" time shows how old that report is.

## Architecture

```text
moon.local (rootless podman, user moon)
├─ factory container (Quadlet user service)
│    orchestrator + dashboard + SQLite
│    holds the forge tokens in its secret store
│    talks to podman through podman.socket
│    polls GitHub for CI status and review comments, and lists Renovate pull requests
│    of projects that turned the switch on
│    holds the master key that decrypts per-project MCP header values
│    runs the MCP proxy on its own port, which adds a project's stored headers
└─ worker containers, one per job stage, started by the factory
     image: Claude Code, Codex, git, nix, unzip
     mounts: job workspace, the run's agent config directory, shared /nix store volume, cargo cache per project, factory agents directory (read-only)
     network: the shared factory podman network, to reach the MCP proxy but not the dashboard
     env: the run's agent credential and, when a remote server is active, the per-run MCP token
          Claude gets its token through --env, see Claude auth; Codex reads its auth.json from the mounted config directory, see Codex auth
          both agents get the MCP token through --env with no value and a proxy config written by the backend
     worker packages: a project's nixpkgs packages, put on PATH by a nix shell around the agent and checks command, built into the shared /nix volume
     stdio MCP servers: a child process of the agent inside the worker, started from the command in the agent's MCP config; it bypasses the proxy, carries no token and dies with the container
```

GitHub cannot reach `moon.local`, so the factory polls GitHub with `gh api` about once a minute instead of receiving webhooks.

## Recipe: playwright-mcp

The agent drives a browser against a dev server it starts in its own worker and saves screenshots under `/work`. The server is a stdio server, see MCP stdio servers, and the browser comes from a worker package, see Worker packages.

1. On the project page, add the worker package `playwright-mcp`. The nixpkgs package wraps a matching Chromium through `PLAYWRIGHT_BROWSERS_PATH`, so the project needs no `npx` download and no separate browser install. The first run takes longer while nix downloads it.
2. As a factory admin, add a stdio server with the command `playwright-mcp` and the base argument `--no-sandbox`. Chromium runs inside the rootless worker container, where its own sandbox cannot start.

## Job flow

Each job moves through these states. Each ✋ is an approval gate. A job has the gates its settings turned on when it was created.

```text
requested → clarifying → spec ✋ → plan ✋ → implementing → verifying → publish ✋ → pr-open → ci-and-review → merged
```

- **proposed.** A gap job starts here, in front of `requested`, and waits for approval with no worker and no agent run. Approve moves it to `requested` and makes the approver its requester. Dismiss ends it in `dismissed`. See Gap jobs.
- **requested.** The job waits here for a free worker, which the board shows as queued, and for every job in its prerequisites to reach `merged`, which the board shows as waiting, or as blocked when one of them cannot merge. A waiting job holds no worker and does not delay other jobs. While it waits, its requester can change the request text, the attachments and the jobs it waits for. `Event::Edit` replaces the text and applies only at `(requested, factory)`, so a job that has already started rejects it. The scheduler's `Start` copies the current text into the clarify task.
- **clarifying.** The agent reads the repository and asks questions. A headless run cannot wait for answers, so the run ends with its questions as structured output. The dashboard shows them, and the next run resumes the same session with your answers.
- **spec.** The agent writes the goal, scope, what is out of scope, and acceptance criteria. The run starts a new session. Its prompt holds the request and the answers to the clarifying questions.
- **plan.** The agent splits the work into pull requests. A large refactor gets its own pull request first, as maestro's `CONTRIBUTING.md` requires. The run starts a new session. Its prompt holds the request, the answers and the approved spec. Each planned pull request carries notes besides its title and summary: the files and functions to change, the tests to extend and the docs that apply. The implement run of each pull request starts a new session, and before notes existed each one explored the repository again for what the planning run had already found. The plan card shows the notes in a collapsed block under each summary, so you see them when you approve the plan. A plan stored before notes existed has none.
- **implementing.** One worker session per pull request. The prompt holds the request, the answers, the approved spec, the titles of all planned pull requests, and the summary and notes of this one. The prompt says the notes predate the earlier pull requests, so the agent checks them against the code. The worker commits in the job workspace and stops when the commits are ready.
- **verifying.** The factory runs the project's checks in the worker. Failures go back to the session. A run that ends in an error instead of a pass or a failure, because the command exited 125, 126 or 127, podman did not start or the git step before the checks failed, is a checks error. The factory logs it and runs the checks again after the poll interval, and after `MAX_FAILED_ROUNDS` (5) in a row the job ends in `failed` with the `verifying` retry target and a reason that holds the last error. Without the cap a wrong command looped for ever, because `bash -lc` itself exits 127 for a missing command and 126 for one that is not executable, and no agent run or question ever reached the user. The count is `checks_errors` in the job, so a restart keeps it. It is separate from the 5 failed rounds: checks errors do not use up the agent's rounds, and failed rounds do not count toward this cap. `ChecksPassed`, `ChecksFailed`, a new pull request and `Retry` reset it. The comment review once planned here is now part of the merge-time LLM review, see `ci-and-review, the LLM review pass`.
- **publish.** With the publish gate on, the job stays in verifying once the checks pass and the factory collects the branch's commits and diff stat from the checkout. The dashboard shows them with the pull request title and description. Approve moves the job to pr-open. Request changes sends your feedback to the pull request's session, then the checks run again and the job returns here. A revision does not count toward the 5 failed rounds. The factory pushes nothing before you approve.
- **pr-open.** The factory pushes the branch and opens the pull request as the job's account. Before the push, it asks GitHub for a merged pull request from the branch. You can merge a pull request while the factory is between a CI fix and its push, and GitHub then deletes the branch. The push would fail on every retry, because `--force-with-lease` expects the deleted branch. So when the branch has a merged pull request, the factory pushes nothing, records that pull request's number and applies `Merged`, and the job moves to the next pull request. When the branch has no commits after `origin/<base>`, the factory pushes nothing and applies `NothingToPublish`. This happens when an earlier pull request already made the change, as in job 42: its first pull request took in the second one's Containerfile change during review, the second implement run found nothing to commit, and `gh pr create` failed with "No commits between" every 60 seconds until the job was stuck. A pull request with no number is marked skipped, and the job moves to the next pull request, or to `merged` after the last one. The timeline and plan card show it as skipped. With the publish gate on, you see the empty commit list before you approve. A pull request that is already open fails the job instead, because pushing an empty branch would close it.
- **ci-and-review.** The factory polls CI and review comments, and feeds failures and your comments back into a resumed session until CI is green and you merge. When the pull request no longer merges cleanly, the factory fetches the newest base branch into the checkout, since workers have no GitHub credentials, and the agent rebases onto it. A conflict counts toward the job's limit of 5 failed rounds per pull request, so an agent that cannot resolve one stops.
- **ci-and-review, the LLM review pass.** When CI is green and the project has LLM review on, a reviewer runs before the factory merges. The scheduler applies `StartReview`, which moves the job to a review turn: a worker run in a `review` session of its own, separate from the implement session, with no GitHub token. It reads the branch diff from the checkout and ends with `approve`, or `changes` with feedback. Each pass is kept as a numbered `ReviewPass` with its verdict and feedback, for the job page. `approve` records the approval and returns the job to watching the pull request, so the factory merges when auto-merge is on or waits for you when it is off. `changes` sends the feedback to the implement session as a review-fix run, the same path as a human review comment; after the push CI runs and the reviewer runs again. The review session resumes across passes, so a later pass sees only the commits since the last one and reviews those. A push clears the recorded approval, so the reviewer reads each head afresh.

  The reviewer gets the decisions the branch rests on. The first pass on a pull request starts its prompt with the request, the requester's answers, the approved spec and the plan, with the pull request it reviews marked. A later pass resumes that session, so its prompt carries only the answers given since the last pass, with the feedback that pass asked for. Each `ReviewPass` records its pull request, the head it read and how many answers the job held, which is how the next pass finds the new answers. Both prompts tell the reviewer that the answers and the spec are decisions: it may say it disagrees with one, but not ask for a change that contradicts it. Job 41 showed why. The reviewer had only the diff, so it asked four times for a fallback that the spec ruled out and that the requester had turned down when the agent asked.

  `StartReview` carries the head commit CI passed on, read from `headRefOid`. When the last pass on the pull request asked for changes on that same head and the job holds no answer that pass did not see, the author added no commit and nothing new is known, so a new pass would read the same diff and give the same verdict. The job then stops at `ReviewStopped` with `ReviewStop::Unchanged` instead of running the reviewer, and spends no review round. The card asks you to merge on GitHub or retry. A new head or a new answer runs the reviewer as usual. The review-fix runs count toward a review cap of 5, held in `review_rounds` and separate from the 5 failed check and CI rounds, so a job can spend both on one pull request. At the cap, or when a reviewer run crashes, times out or returns no valid result, the review fails closed through `ReviewFailed`: the job does not merge and waits for you with the reason. While it waits, the factory keeps watching the pull request, but the watch is passive: `next_command` returns a `WatchPr` with `watch_only` set, and the watch reports only a merge or a close by you. It never merges the pull request, even with auto-merge on, and never restarts the reviewer. Merging it on GitHub moves the job on to the next pull request, or to `merged` for the last one. Closing it without merging fails the job. This is what frees a job stuck in review-stopped after you merge its pull request by hand. The review-stopped card also shows a Retry button, see `Retry a failed job`: a reviewer run that failed reruns the reviewer, and a review that hit its cap of 5 addresses the last feedback with 5 fresh rounds. The state machine is pure, so it models the pass with no I/O; the scheduler runs the worker and decides the merge.
- **Renovate pull request.** A Renovate job starts at `renovate` and never enters the stages above. The factory watches the pull request. It reruns failed CI up to the automatic reruns limit, then an agent analyses the failure and returns `transient` or `caused_by_update`. It stops and comments at the total reruns limit. When every check passed, an agent checks the diff and returns `safe` or `unsafe`. A safe update merges when the project's auto-merge is on and waits as ready to merge otherwise. A new head restarts triage. With Read access the project account cannot rerun CI or merge, so the factory skips the reruns and a safe update waits as ready to merge. A merge in a packaging project that changed a configured manifest file goes to `packaging`, where the factory gathers the manifest and the upstream changes and an agent lists the gaps. Each gap becomes a proposal job, and the job then ends in `merged`. Any other merge ends it in `merged` at once, and a close without a merge ends it in `cancelled`. See the Renovate pull request jobs and Packaging gap analysis rows. A stopped job can instead start a fix job in its own pull request. It waits while that job runs. When it merges, the factory asks Renovate to rebase, and the new head restarts triage. Any other ending of the fix job returns the job to the stopped wait.
- **Rerun on request.** When the agent runs a `FixCi` task and finds nothing to commit, such as after a flaky failure, it returns `rerun_ci` with a reason. The job moves to a factory turn that runs `Command::RerunCi`, which carries the reason for the log. This counts a failed round through `fail_round`, so the limit of 5 still applies and the fifth round fails the job. The `CiRerun` event returns the job to watching the pull request. The result is rejected in any other turn. The scheduler logs the reason, then calls `Executor::rerun`, which runs `GitHub::rerun_failed` with the factory's token. The worker still gets no GitHub token. When `gh` fails, the job stays in the rerun turn and the scheduler tries again after `poll_seconds`. After a successful rerun the scheduler applies `CiRerun` and holds the next watch for `poll_seconds`. `rerun_failed` already waits until GitHub stops reporting the old failure, so the next watch does not count it as a second round. When the head has no failed Actions run, the scheduler logs that and applies `CiRerun` anyway. The next watch then sees the failure again and asks the agent again, which counts another round, so the limit of 5 ends the loop.
- **Retry a failed job.** A job that used up its 5 failed check or CI rounds ends in `failed` with a retry target: the `verifying` or `ci-and-review` stage of the pull request it failed on. A job whose local checks could not run 5 times in a row ends in `failed` with the same `verifying` target, told apart by `Job::checks_could_not_run`, and its Retry resets the checks-error count too. Its failure card adds a sentence to revise the project's local checks command or retry, and a same-tab link to `/settings/projects/<name>`, chosen by that accessor and not by the reason text. A job whose agent run failed ends in `failed` with the stage and task of that run as its retry target. The failure card on the job page shows a Retry button, which posts to `POST /jobs/{id}/retry`. `Event::Retry` returns the job to that stage with a factory turn and resets the failed-round count, so the factory runs the checks or watches the pull request again and the agent gets 5 fresh rounds before it fails once more. For a failed agent run, `Event::Retry` runs the same task again in the same session and keeps the failed-round count. This covers a run stopped by the plan's usage limit, and a job whose project was not configured, which fails again if the project is still missing. `failed` is therefore no longer always terminal. `Job::can_retry` reports whether a retry would resume the job. A legacy job stored before the retry target existed carries none. The factory recognises it by its exact old reason, or by an agent failure reason that starts with "the agent run ended with", and resumes at `ci-and-review` of its highest-numbered pull request. A legacy job with no pull request number is not retryable. A job closed unmerged, and a cancelled or merged job, reject `Retry`, and their failure cards show no button. The retry leaves `created_at` alone, so the 30-day expiry is unchanged.

  A stopped review retries the same way, though its stage is not `failed`. A job in `ci-and-review` waiting at `ReviewStopped` with a pull request number is retryable, and the review-stopped card shows the same Retry button. Where it resumes depends on why the review stopped, recorded on the ask as `ReviewStop` so the retry never reads the reason text. When a reviewer run failed, or the review stopped because the head had not changed, `Event::Retry` returns to the `review` task in the same review session and leaves the review and failed round counts as they are. When the review hit its cap of 5, `Event::Retry` clears `review_rounds` and sends the last pass's feedback to the implement session as an `AddressReview` run, so the pull request gets 5 fresh review rounds. A job stored in `ReviewStopped` before the `ReviewStop` field existed, such as jobs/28, loads with the default and retries as a reviewer failure. A `ReviewStopped` ask with no pull request number is not retryable, and a `Retry` posted after the watch already moved the job on is rejected like any other stale retry.
- **Rerun after an edit.** When `open_pr` edits an existing pull request whose checks had failed, the factory reruns the failed runs on the head commit, so they read the new description. `GitHub::rerun_failed` lists the runs on the head with `gh run list --commit`, and runs `gh run rerun <id> --failed` for each one that failed, timed out or was cancelled. It uses the factory's token, so workers still have none. The case it covers is an agent run that edits the description and adds no commit. The push does nothing, so the old failed run is still the head's result. The factory reads the checks before the edit, and reruns after it. The rerun counts no round, because the round for the failing CI was counted when the agent was asked to fix it. Passing, pending and missing checks cause no rerun, and neither does creating the pull request. When the head has no failed Actions run, such as a failed check from outside Actions, `rerun_failed` returns `NothingToRerun`, and `open_pr` logs an error. When the rerun fails, `open_pr` logs the error and returns the pull request number, because the edit worked. GitHub keeps reporting the old failure for a moment after a rerun, and a watch in that moment would report it again and count a second round. So `rerun_failed` reads the pull request after the reruns until no check is failed, up to `settle_polls` reads `settle_interval` apart (10 reads, 3 seconds). The watch reads the same data, so it sees the new state.

The state machine is pure logic with no I/O, so it can be tested without podman or GitHub. Every step must be safe to retry, because a container or the factory can die in the middle of one.

## Running Claude Code in a worker

This is the Claude agent's implementation of the `AgentBackend` interface, see "Agent runtime". It holds every Claude-specific detail below: the `claude -p` command line, the `CLAUDE_CODE_OAUTH_TOKEN` credential, the `CLAUDE_CONFIG_DIR` config directory, the session-resume check, and the stream-json parser.

- One `claude -p` run per stage, with `--output-format stream-json` for the live log. The factory picks the session's UUID and passes it with `--session-id` on the first run, so it knows the ID even if it dies during the run. Later runs pass `--resume <session-id>`.
- **Fresh sessions.** The clarify, spec, plan and implement runs each start their own session, one for clarifying, one for the spec, one for the plan and one per planned pull request. Each prompt is self-contained, because the session has seen none of the earlier stages. The job stores the request, the answers, the approved spec and the plan for this. Only a gate revision, a check fix, a CI fix, a review fix or a rebase resumes the session of its own stage. Each stage can then use its own model, because no resumed session switches models. A job created before this rule has no stored answers and keeps one planning session for clarifying, spec and plan, so its spec and plan runs resume it with the short prompts.
- Every run ends with `--json-schema` structured output: an `outcome` and the questions, spec or plan that go with it. Each stage allows `questions` and one outcome of its own: `clarified`, `spec`, `plan` or `commits_ready`. A `FixCi` run may also end with `rerun_ci` and a required non-empty `reason`. The factory runs the rerun itself, so the worker needs no GitHub token for it. Any other run that returns it fails the job. Claude Code puts the output in `structured_output` on the final `result` line. A run without it, or with an outcome its stage does not allow, fails the job.
- The worker is started with `--rm`, so each job gets a Claude Code config directory on the host, mounted at `CLAUDE_CONFIG_DIR`. It keeps the session files that `--resume` reads.
- The factory resolves the Claude token when the run starts, see "Claude auth", and sets it in the podman process environment. The worker gets it with `--env CLAUDE_CODE_OAUTH_TOKEN` and no value, so podman passes the token through from its own environment and it never appears in the `podman` arguments, the job log or an error message. A token saved on the settings page reaches the next run this way, with no restart, while a run already going keeps the token it started with. With no token the run fails before any container starts with "no Claude token is set", and the job page's Retry runs the task again once a token is saved.
- Every run gets `--settings` with `attribution` emptied. Claude Code otherwise adds a `Co-Authored-By` trailer to each commit, a skill's rules do not stop it, and GitHub copies the branch's co-author trailers into the squash commit on the base branch. Before the project's checks, the factory also fails a branch whose commits credit an AI tool, and the agent rewords them.
- The factory's rules come in through `--plugin-dir` (skills and agents) and `--settings` (hooks). A headless run in an untrusted folder ignores a repository's `extraKnownMarketplaces` without any message, so the factory must not depend on the target repository's plugin settings.
- The target repository's own `CLAUDE.md` and project skills still load. maestro has its own `no-comments` and `open-pr` skills, so the factory's plugin namespaces its versions as `factory:no-comments` and `factory:open-pr`.
- Claude Code keeps an MCP server's tools behind its tool-search step and loads a tool's schema only when the model searches for it, such as `mcp__<server>__<tool>`. A run never reaches a tool nothing names, so a run with at least one active server gets a prompt paragraph that lists the servers and tells the agent to load their tools before it starts, see "Prompt boundary". A gateway server adds a second layer: its listed tools only search for and run other tools, and the app tools appear only when the agent searches by use case. The paragraph points the agent at the server's search tool for that. The paragraph is the same for Codex, where the load step costs nothing because Codex lists a server's own tools up front. A gateway's catalog stays hidden for Codex too, so the gateway sentences apply there.
- A stdio MCP server is a `"<name>": {"type": "stdio", "command": "...", "args": [...]}` entry in the MCP config JSON, next to the `http` entries. A run with a stdio server writes that JSON to `factory-mcp.json` in the config directory and passes its path to `--mcp-config`, see MCP stdio servers. Claude starts the process itself in `/work`. Its startup timeout is `MCP_TIMEOUT`, which defaults to 30 seconds. A run with a stdio server sets `"env": {"MCP_TIMEOUT": "120000"}` in the `--settings` JSON, which takes effect and needs no podman `--env`: checked on Claude Code 2.1.330, a server that never answered was marked `failed` in the `init` line after about 6 seconds with `MCP_TIMEOUT=1500` in settings and after about 33 seconds without it. A run with no stdio server passes the same `--settings` as before. A server that cannot start shows as `"status":"failed"` in the `init` line, which the runner reports as an unavailable server. Claude does not expand `${NAME}` in a command or argument, but the factory refuses `${` anyway, see MCP server registry.
- Claude Code hooks run under whatever shell the container has, without the nix devShell. Write hook scripts for plain bash and test them that way.

## Running Codex in a worker

The worker image carries Codex next to Claude Code, and the `AgentBackend` in `factory-runner` drives it with the `codex exec` CLI. Codex reports token counts and no dollar cost, so the factory estimates each run's cost from a price table an operator keeps on the Codex settings page (see Job cost). The Codex settings page, `/settings/agents/codex`, also enters the login (see Settings layout).

**The login and its refresh.** A Codex run uses the account-wide `auth.json` the `CodexLogin` coordinator resolves from the secret store (see "MCP secret storage"). The executor writes it into the run's `codex` config directory at mode 0600 before the worker starts, and after the worker exits it reads the file back, keeps it if Codex refreshed it, and deletes it, so a login sits in a job directory only while a run is in flight. Codex rewrites `auth.json` when it rotates the tokens, so the executor keeps the read-back file when it is a valid login whose `last_refresh` is newer than the stored one's, under a single lock so two runs that end together cannot write over each other. To stop two runs from rotating the same refresh token at once, a stored login is "due" for a refresh when its `last_refresh` is older than seven days or its access token's `exp` claim is within an hour; while it is due, one Codex run is in flight at a time and the others wait in the executor, holding their worker slots. A run with no stored login fails with "no Codex login is set" before any checkout or container, the way a Claude run fails with "no Claude token is set".

**Repository instructions.** Codex reads `AGENTS.md`, not `CLAUDE.md`, so the prompt builder names `AGENTS.md` in a Codex run's prompt, and a fresh Codex session in a repository with no `AGENTS.md` at its root writes one line to the job log, "This repository has no AGENTS.md, so Codex runs without its instructions.", and runs on. A target repository that turns Codex on adds its own `AGENTS.md`.

- **The command.** A new session runs `codex exec --json --dangerously-bypass-approvals-and-sandbox --output-schema <file> [--model <model>] -c model_reasoning_effort=<level> [MCP flags] <prompt>`, and a resumed one runs `codex exec resume <thread id>` with the same flags. `--json` writes JSON Lines for the live log. The container is the sandbox, as it is for Claude's `bypassPermissions`, so `--dangerously-bypass-approvals-and-sandbox` is safe. An empty model passes no `--model`. The effort is the run's agent level, see Agent effort.
- **Sessions.** Codex assigns the session id itself and reports it in `thread.started`, so the factory learns it from the stream and cannot pass it in advance the way it passes Claude's `--session-id`. The parser turns `thread.started` into an item the scheduler stores in the `sessions` table's agent-session-id column as soon as the line arrives, so a run that dies after that line can still resume. A resumed run uses `codex exec resume <thread id>` when the id is stored and a rollout file for it exists under `CODEX_HOME/sessions`, and otherwise starts a new session. Claude leaves the column empty, because it uses the factory's UUID.
- **Structured output.** Each run ends with `--output-schema`, which makes the final agent message match the schema. OpenAI's strict rules want every property in `required` and `additionalProperties: false` on every object, so a stage that may leave a field out marks it nullable and the outcome resolution reads a `null` as absent. The text of the last `agent_message` item goes through the same outcome resolution as Claude's `structured_output`, so a missing output or an outcome the stage does not allow fails the run the same way.
- **Config.** `CODEX_HOME=/codex` inside the worker, mounted from the job's `codex` directory on the host. The backend writes a `config.toml` there that sets `cli_auth_credentials_store = "file"` and no `project_doc_fallback_filenames`, so Codex keeps the login in the file rather than an OS keyring and reads a repository's `AGENTS.md` rather than its `CLAUDE.md`.
- **MCP.** Each active server becomes `-c mcp_servers.<name>.url="<proxy>/mcp/<name>"` and `-c mcp_servers.<name>.bearer_token_env_var="FACTORY_MCP_TOKEN"`, and the run token reaches the container through `--env FACTORY_MCP_TOKEN` with no value, so the token stays out of the `podman` arguments and the log. A stdio server becomes a `[mcp_servers.<name>]` table in the `config.toml` the runner writes into `CODEX_HOME`, with `command`, `args` and `startup_timeout_sec = 120`, and no `-c` override, because Codex's default startup timeout is 10 seconds and a first `npx` or `uvx` start downloads the package. Values are TOML basic strings, with the backslash, quote and control characters escaped, so a quote, backslash or space in an argument arrives unchanged. The pinned 0.165.0 binary accepted the same keys as `-c` overrides, including an argument that held `"`, `\` and a space. A run with only stdio servers passes no `FACTORY_MCP_TOKEN`. A run with no active server passes no MCP flags and no token. The proxy, its run tokens, the tool toggles and the `mcp-tool-call` rows work for a Codex run unchanged, because they sit on the factory side. A run with an active server also gets the shared prompt paragraph that names the servers, asks the agent to load their tools first and covers gateway servers, the same paragraph a Claude run gets, see "Prompt boundary".
- **Parser.** The Codex parser turns the JSON Lines into the same `AgentItem`s as Claude's stream parser. Agent messages, command executions with their exit code, file changes, MCP tool calls and errors become log lines in the same style, such as `tool mcp__<server>__<tool>` for an MCP call. It sums the `usage` of every `turn.completed` line for the cost estimate, see Job cost. A `turn.failed` carries its reason under `error.message` and a top-level `error` under `message`, and either without a final agent message fails the run with "the Codex run failed: <message>". A login Codex rejected mid-run surfaces as that failure, and the job page's Retry runs the task again once a new login is stored. A non-fatal item `error`, such as a startup warning, is a log line and does not fail the run.

- The image installs one pinned Codex release, set by the `CODEX_VERSION` build arg (`0.165.0`). It downloads the `codex-package-x86_64-unknown-linux-musl` tarball from the `rust-v<version>` GitHub release, unpacks it to `/opt/codex` and links `/opt/codex/bin/codex` as `/usr/local/bin/codex`. The build fails if `codex --version` does not report that version or `codex-code-mode-host` is missing. moon is x86_64, so the image pins that one asset rather than detect the architecture.
- The package, not the bare `codex-x86_64-unknown-linux-musl` asset, because Codex runs its shell and workspace tools through `codex-code-mode-host`, which it looks for in the directory of its resolved binary. The bare asset holds `codex` alone. With it, every Codex run logged "Code Mode is unavailable" as a non-fatal startup error and the agent could run no command, so a review reported that it could not read the diff. The package also carries `bwrap`, `rg` and about 50 MB of voice libraries a worker does not use; the image keeps the package whole so a later version's helpers arrive with it.
- The image creates `/codex`, owned by the worker user, the way it creates `/claude`. The Codex backend mounts the job's `codex` directory there as `CODEX_HOME`.
- The image links the bundled review skills to `/etc/codex/skills/factory`, a symlink to `/factory-agents/skills`. Codex reads skills from `/etc/codex/skills` and `~/.agents/skills`, so a review run finds `review` and `comment-review` there without the `--plugin-dir` flag Claude uses. `/etc/codex/skills/factory/review/SKILL.md` resolves through the symlink.

### Codex CLI facts (rust-v0.165.0)

These were checked by running the pinned `codex-x86_64-unknown-linux-musl` binary (`codex-cli 0.165.0`). A full run needs the ChatGPT login, which this build does not have, so the token-accounting facts are checked against the documentation and confirmed from an authenticated capture on moon in the backend pull request.

Confirmed against the binary:

- `codex exec` accepts `--json`, `--output-schema <FILE>`, `--dangerously-bypass-approvals-and-sandbox`, `-m/--model <MODEL>` and `-c key=value` overrides. `codex exec resume <SESSION_ID> [PROMPT]` takes a session UUID or a thread name.

- `--json` writes JSON Lines. The captured envelopes are in `crates/factory-runner/tests/fixtures/codex-exec-auth-failure.jsonl`: `{"type":"thread.started","thread_id":"<uuid>"}`, `{"type":"turn.started"}`, `{"type":"item.completed","item":{"id":"<id>","type":"error","message":"..."}}`, a top-level `{"type":"error","message":"..."}`, and `{"type":"turn.failed","error":{"message":"..."}}`. The run authenticated against `api.openai.com` with no login and ended at `turn.failed`, so the capture stops before the success-path lines.
- Codex assigns the session id and reports it in `thread.started.thread_id`, so the factory learns it from the stream and cannot pass it in advance, as the spec expected.
- `cli_auth_credentials_store = "file"` in `config.toml` is accepted, and `-c` overrides nested keys through dotted TOML paths.

Differences from the spec's expectations:

- The default model is `gpt-6.1-sol`, printed in the run header, not a `gpt-5-codex` id. The Codex model suggestions in the registry should track this CLI's `gpt-6` family.

The model's server rejects an unsupported level at request time, so the allowed levels cannot be read from the CLI. OpenAI's model page lists `low`, `medium` (default), `high`, `xhigh` and `max` for `gpt-6.1-sol`, and says `none` and `minimal` are not supported. This differs from the spec's expected `minimal, low, medium, high, xhigh`; the effort-levels pull request uses the model-supported set.
- `turn.failed` carries the reason under `error.message`, and `item.completed` wraps the item under `item`. The parser reads those paths.

Not confirmable without an authenticated run, deferred to the moon capture in the backend pull request:

- `turn.completed` and its `usage` fields, and whether `cached_input_tokens` is part of `input_tokens` and `reasoning_output_tokens` part of `output_tokens`. The unauthenticated run never reached `turn.completed`, so the cost formula stays unconfirmed.
- The success-path item types `agent_message`, `command_execution`, `file_change`, `mcp_tool_call`, `web_search` and `todo_list`.
- Whether the final message conforms to `--output-schema`.

Operational notes:

- Codex warns that it cannot find bubblewrap and uses a bundled copy. With `--dangerously-bypass-approvals-and-sandbox` the container is the sandbox, so bubblewrap is unused and the image does not install it.
- "Code Mode" fails closed when `codex-code-mode-host` is absent and emits an `error` item. It is not needed; the parser treats such a line as a non-fatal log line.

## Running Copilot in a worker

The worker image carries the GitHub Copilot CLI next to Claude Code and Codex, and the `AgentBackend` in `factory-runner` (`copilot.rs`) drives it with `copilot -p`. The event shapes and flags come from the pinned `1.0.114`; see "Copilot CLI facts" for how they were checked. A Copilot run records no dollar cost (option a, see Job cost), so it adds nothing to the job or project totals. The login is stored through the Copilot settings page, see "Copilot auth" and Settings layout, and the page has no price table.

**Repository instructions.** Copilot reads `AGENTS.md`, the shared standard, and also `CLAUDE.md`. The prompt builder names `AGENTS.md` in a Copilot run's prompt, as it does for Codex, and `Agent::rules_doc` returns `AGENTS.md`.

- **The command.** A new session runs `copilot -p <prompt> --output-format json --allow-all --no-ask-user --no-color --no-auto-update --disable-client-telemetry --disable-builtin-mcps --session-id <uuid> [--model <model>] --effort <level> [--additional-mcp-config <json>] --plugin-dir /factory-agents`, and a resumed one replaces `--session-id` with `--resume`. `--output-format json` writes JSON Lines for the live log. The container is the sandbox, as it is for Claude and Codex, so `--allow-all` grants every tool, path and URL and `--no-ask-user` denies nothing by waiting. `--no-auto-update` keeps the run on the baked-in release even when a newer one sits in the package cache, which `COPILOT_AUTO_UPDATE=false` in the image reinforces. An empty model passes no `--model`. The effort is the run's agent level, see Agent effort.
- **Sessions.** The factory picks the session UUID and passes it with `--session-id`, as it does for Claude, so it knows the id even if it dies during the run; the CLI accepts a v4 UUID for a new session. A resumed run passes `--resume <uuid>` when `COPILOT_HOME/session-state/<id>/` exists on the host, and otherwise starts a new session under the same id. The parser turns `session.start` into the session item, so the id is recorded the way Codex's thread id is.
- **Credential.** The CLI does not refresh the token, and the device-login token showed no expiry (see the "Copilot CLI facts" gate result), so the backend uses `Credential::Env("COPILOT_GITHUB_TOKEN")`, not the read-back file Codex needs. The factory sets the token in the podman process environment and the worker gets it with `--env COPILOT_GITHUB_TOKEN` and no value, so the token never appears in the `podman` arguments, the job log or an error message. `COPILOT_GITHUB_TOKEN` is first in the CLI's lookup order, so the stored login wins over any token baked into the image.
- **Config.** `COPILOT_HOME=/copilot` inside the worker, mounted from the job's `copilot` directory on the host. It keeps `session-state/<id>/` for a resumed run. It holds no login: the device flow's scratch directory is deleted once the token is in the secret store, and a worker gets the token through `COPILOT_GITHUB_TOKEN`.
- **Structured output.** The CLI has no output-schema flag, so the backend asks for the JSON in the prompt: the `PromptStyle` carries an instruction that tells the agent to end with one final message of only the JSON, gives the reason (text outside the JSON fails the run) and names where a summary goes (the schema's fields, or nowhere), and `prompt.rs` appends the stage's schema (see "Prompt boundary"). When the message ends with a fenced code block, the parser reads that last block as the JSON, whatever text comes before it. Text after the closing fence, or a message with no fenced block that is not JSON itself, fails the run, and the parser searches nowhere else. Copilot agents write a summary before the JSON despite the instruction, which already said "no sentence before it", so the prompt now gives the reason and a place for the summary. Failing a finished run over that wastes the run. A repair turn that asks for the JSON again was rejected because it costs another premium request, and brace-matching unfenced JSON is out of scope. The text of the last assistant message goes through the same outcome resolution as Claude's `structured_output`, so a missing output, invalid JSON, or an outcome the stage does not allow fails the run the way Codex's does.
- **MCP.** The built-in `github-mcp-server` would reach GitHub with the login token, so every run passes `--disable-builtin-mcps` and a worker gets no GitHub MCP tools. Each active factory server becomes one `http` entry in `--additional-mcp-config`, pointed at `<proxy>/mcp/<name>` with `Authorization: Bearer ${FACTORY_MCP_TOKEN}` and `"tools": ["*"]`. The CLI expands `${FACTORY_MCP_TOKEN}` from the environment, where the run sets it through `--env FACTORY_MCP_TOKEN` with no value, so the token stays out of the arguments and the log. A stdio server becomes `"<name>": {"type": "local", "command": "...", "args": [...], "tools": ["*"]}` in the same config. The SDK types, `MCPStdioServerConfig` in `copilot-sdk/types.d.ts`, accept `"local"` or `"stdio"` for `type`, and the factory writes `local`. Copilot has no startup timeout setting: the `timeout` field is in milliseconds for tool calls to the server, so a stdio server keeps the CLI's own startup behaviour. Copilot expands `${NAME}` in a command or argument from its environment and the other agents do not, which is why the registry and a project's extra arguments refuse `${`. A run with only stdio servers passes no `FACTORY_MCP_TOKEN`. A run with no active server passes no MCP flag. The run with an active server also gets the shared prompt paragraph that names the servers, asks for their tools to be loaded and covers gateway servers, the same one Claude and Codex get, see "Prompt boundary".
- **Review method.** Every run passes `--plugin-dir /factory-agents`, whether or not the factory mounts its own agents directory, because the image bakes a copy there. The flag always resolves, so the review-method wording names the skill rather than a path. The reviewed repository's own skills still load alongside it.
- **Parser.** The parser turns the JSON Lines into the same `AgentItem`s as the Claude and Codex parsers, skipping the `ephemeral` events such as the streaming deltas. A non-ephemeral `assistant.message` logs its `data.content`. Only a message with an empty `toolRequests` list is a final answer and resolves the result, so a run that fails after a message written before a tool call ends on the failure and not on that message; among final answers the last wins. `tool.execution_start` logs one line: an MCP call as `tool mcp__<server>__<tool>`, a shell command (the event's `shellToolInfo`) as an `exec` line, and a built-in file edit as an `edit` line; other tools, such as a read, log nothing, the way Codex drops a read step. A failed `tool.execution_complete` notes the failure without failing the run. `session.warning` logs its message. Copilot reports no fatal-error event in the stream and puts the human cause of a failed run on stderr, so the parser keys a failure off a non-zero `result.exitCode` with "the Copilot run failed: the CLI exited with code <n>", used only when no final message arrived. The result records `cost_usd: None`. `session.usage_checkpoint` logs the premium requests, the AI credits and the input, cache read, cache write and output token counts the CLI reports, and the final `result` line logs its premium request count. The backend's `start_log` hook writes one line before the run reads any output, noting that Copilot runs are not counted in the job cost, so a run killed before any output still carries it. None of this makes an estimate.
- The image creates `/copilot`, owned by the worker user, the way it creates `/claude` and `/codex`. The Copilot backend mounts the job's `copilot` directory there as `COPILOT_HOME`.

## Copilot CLI facts (1.0.114)

These are step 0 of the Copilot work, see the spec. The worker image now pins `@github/copilot@1.0.114` (`containers/worker/Containerfile`, `ARG COPILOT_VERSION`), installs it with Node 22 and fails the build if `copilot --version` disagrees. Most facts below come from running that same pinned package directly on a linux-x64 host, because podman and Node were not available here to build and run the worker image: the `@github/copilot-linux-x64` optional dependency is a self-contained QuickJS executable. The npm `@github/copilot` package is a loader that resolves `@github/copilot-<platform>-<arch>` and runs it, and the loader needs Node, which is why the image installs it. The authenticated device login, the stored token and an authenticated `-p` run were captured by an operator in a `node:22-slim` container with the same pinned CLI, since they need a GitHub account on a Copilot plan; those are marked as such below.

**Gate result: passes.** A completed `copilot login --device-code` leaves a usable token in the container. With `{"storeTokenPlaintext": true}` in `COPILOT_HOME/settings.json`, the login signs in and writes the token to `COPILOT_HOME/config.json` at mode 0600, in plaintext, with no keychain and no prompt. The file starts with two `//` comment lines, so it is not plain JSON and the coordinator drops them before parsing. The file holds an `authTokens` object keyed by `"https://github.com:<user>"` (and a `"…:<user>:github"` variant), each value `{ "token": "gho_…" }`, plus `loggedInUsers` and `lastLoggedInUser`. The stored token is an ordinary `gho_` OAuth token with scopes `codespace, gist, read:org, read:user, repo, write:plugin_gateway_connections` (from `X-OAuth-Scopes` on `GET /user`), no expiry and no refresh token, so it stays valid until revoked. Because it does not refresh, the backend uses `Credential::Env("COPILOT_GITHUB_TOKEN")` and the login coordinator reads the token once from `config.json` after the login. The `node:22-slim` capture also needed `ca-certificates`, or the login failed with "invalid proxy TLS configuration"; the worker image already installs it.

Confirmed against the binary (`GitHub Copilot CLI 1.0.114.`):

- `-p/--prompt <text>` runs non-interactive and exits. `--output-format json` writes JSONL, one object per line; `text` is the default. `--allow-all` equals `--allow-all-tools --allow-all-paths --allow-all-urls`. `--no-ask-user`, `--no-color`, `--disable-client-telemetry`, `--log-level` and `--disable-builtin-mcps` (which turns off `github-mcp-server` and `githubiq`) all exist.
- `--no-auto-update` disables the CLI download for this launch and makes it ignore a newer version already in the package cache. `COPILOT_AUTO_UPDATE=false` also disables the start-of-session plugin updates. The image sets the variable, and each run passes the flag.
- `--session-id <id>` sets the UUID for a new session or resumes an existing one, so the factory picks the id up front as it does for Claude's `--session-id`; `--resume`/`-r` also resumes. The id must be a valid UUID: `11111111-2222-3333-4444-555555555555` was refused as "not a valid UUID" for its variant bits, a v4 id worked, and the factory's v4 UUIDs qualify.
- `--model <id>` takes a model or `auto`; an empty value passes no flag. The effort flag is `--reasoning-effort <level>`, with `--effort` an accepted alias (`--effort bogus` errors "invalid value 'bogus' for '--reasoning-effort <level>'"). The CLI validates the level offline, unlike Codex, against `none, minimal, low, medium, high, xhigh, max`.
- `--additional-mcp-config <json|@file>` validates its JSON: a malformed value errors "Invalid JSON: expected ident", and `{"mcpServers":{"ctx":{"type":"http","url":"…/mcp/ctx","headers":{"Authorization":"Bearer ${FACTORY_MCP_TOKEN}"},"tools":["*"]}}}` is accepted, with `${VAR}` expansion in headers.
- `copilot --plugin-dir /work/agents skill list` lists the factory's `review` and `comment-review` under "Plugin skills", so a reviewer run loads the skill with `--plugin-dir /factory-agents` and names `review`, without a path reference. The flag goes before the subcommand.
- `--no-custom-instructions` turns off `AGENTS.md`, so `AGENTS.md` is the custom-instructions file the CLI reads.
- `COPILOT_HOME` sets the config and state directory, default `~/.copilot`. `session-state/<session-id>/` holds each local session's `events.jsonl`, so `session_for` resumes only when `COPILOT_HOME/session-state/<id>` exists. `COPILOT_CACHE_HOME` is a separate cache for downloaded CLI versions and is not under `COPILOT_HOME`.
- The token lookup order is `COPILOT_GITHUB_TOKEN` > `GH_TOKEN` > `GITHUB_TOKEN` > stored credentials. A fine-grained `github_pat_` with the "Copilot Requests" permission, an OAuth token from the Copilot CLI app, and an OAuth token from gh are supported; classic `ghp_` is not.
- The final record of a run is `{"type":"result",…,"exitCode":N,"usage":{…}}`. The unauthenticated failure capture, `crates/factory-runner/tests/fixtures/copilot-auth-failure.jsonl`, is one such line with `exitCode:1`. The human error ("No authentication information found.") goes to stderr, not into the JSONL, so a failed run yields a `result` with a non-zero `exitCode` and no `assistant.message`, and its reason is on stderr. There is no in-stream fatal-error event; the parser keys a failure off `result.exitCode` and the missing message. An invalid stored token fails the same shape, with "could not be validated … Bad credentials" on stderr.
- The authenticated run (operator capture, `crates/factory-runner/tests/fixtures/copilot-success.jsonl`, a `-p` prompt that replies `pong`) runs `session.start` (`data.sessionId`), then `user.message`, `assistant.turn_start`, streaming `assistant.message_start` and `assistant.message_delta` (`data.deltaContent`), the final `assistant.message` (`data.content`, `data.toolRequests`, `data.model`), `assistant.turn_end`, `session.usage_checkpoint`, and `result` (`exitCode:0`). The parser reads the last `assistant.message` `data.content` for the stage output and skips the `ephemeral:true` events. The ping run called no tools, so the `tool`-execution and `session.warning` event names are not exercised, see below.
- Usage lives in `session.usage_checkpoint`: `accountingSnapshot.modelMetrics.<model>.usage` has `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens` and `reasoningTokens`, with `totalNanoAiu` the AI credits and `totalPremiumRequests` the premium-request count. The final `result.usage` repeats `premiumRequests`, the durations and `codeChanges`. `--usage-output-file <file>` writes the same accounting as JSON. Job cost records none of it (option a), so the counts go to the job log only.
- The default model, from the authenticated run's `session.model_change`, is `claude-sonnet-5.5`, as the spec expected. (The `--help` examples instead show `gpt-5.6-sol`.) With no `--disable-builtin-mcps` the authenticated run auto-connected the built-in `github-mcp-server` with 18 tools; the factory's runs pass `--disable-builtin-mcps`, so a worker gets no GitHub MCP tools.
- `copilot login --device-code` prints "To authenticate, visit https://github.com/login/device and enter code 8F28-EA63", then "Waiting for authorization...". The code is alphanumeric, not digits, and the existing `is_code` parser accepts it: two groups of three to eight uppercase letters or digits. The output carries an OSC 52 clipboard escape, so the login coordinator strips ANSI and OSC as the Codex login does.
- The login container runs with `stdin` from `/dev/null` and piped output, with no pseudo-terminal, and the login still prints the prompt to the pipe and finishes. The login produced the lines "Failed to open browser" and "Failed to copy to clipboard" (no browser or clipboard in a container), which the page shows and ignores. A run of the pinned binary with piped output or under a pseudo-terminal reached the same clipboard step and wrote only `logs/` until the code was entered, so a pseudo-terminal is not needed.
- The login stores the token in the OS credential store, or in a plaintext config file under `COPILOT_HOME` when none is found. `copilot config` refuses to set `storeTokenPlaintext` ("cannot be changed with `copilot config`. Edit settings.json directly"), but writing `{"storeTokenPlaintext": true}` to `COPILOT_HOME/settings.json` reads back as `storeTokenPlaintext=true`. The coordinator writes that file before the login, and the operator capture confirmed the token then lands in `COPILOT_HOME/config.json` with no keychain and no prompt (see "Gate result").

Differences from the spec's expectations:

- The spec gave the effort flag as `--effort` (also `--reasoning-effort`); the canonical flag is `--reasoning-effort` and `--effort` is its alias. The spec's Copilot efforts `low, medium, high, xhigh, max` are a subset: the binary also accepts `none` and `minimal`, which the effort-levels work leaves out, with `medium` the default.
- The spec said the device code has the form `1234-5678`; the real code is alphanumeric, such as `8F28-EA63`. The existing parser accepts both.
- The spec expected a possible plaintext-storage prompt with no TTY. Instead `storeTokenPlaintext` in `settings.json` forces plaintext storage with no prompt.
- The spec and third-party parsers named `tool.execution_start`/`tool.execution_complete` for tool calls and `assistant.message_delta` with `data.content`. The authenticated capture shows the delta carries `data.deltaContent`, and its event names (`model.call_start`, `assistant.turn_start`) differ from the third-party list; the real tool-call event names are still unexercised, see below.

Confirmed from the pinned CLI's own SDK types, `copilot-sdk/generated/session-events.d.ts` in the `@github/copilot-linux-x64` package, since the `pong` capture ran no tools and an authenticated tool run needs a Copilot plan:

- A tool call emits `tool.execution_start` then `tool.execution_complete`. The start event carries `data.toolName`, `data.arguments`, and, for an MCP tool, `data.mcpServerName` and `data.mcpToolName`; a shell tool (`bash`) carries `data.shellToolInfo.displayCommand`. The complete event carries `data.success` and, on failure, `data.error.message`, keyed to the start by `data.toolCallId` but with no tool name of its own. The parser logs the start as an `exec`, `edit` or `mcp__<server>__<tool>` line and notes a failed complete; see "Running Copilot in a worker".
- `session.warning` carries `data.message`. The parser logs it.
- `session.mcp_server_status_changed` carries `data.serverName`, `data.status` (`connected`, `failed`, `needs-auth`, `pending`, `disabled`, `stopped` or `not_configured`) and, for a failure, `data.error`. `session.mcp_servers_loaded` lists `data.servers` with the same `name`, `status` and `error`. Both are marked `ephemeral`. The parser turns a `failed` status in either into an unavailable-server warning, without the error text. These are the SDK's shapes, not a captured run, so the manual check confirms that the `-p --output-format json` stream carries them.
- A stdio server entry is `{"type":"local","command":"…","args":[…],"tools":["*"]}`. `type` is `"local" | "stdio"` in the SDK types, `timeout` is the tool-call timeout in milliseconds, and there is no startup timeout field. A run with a stdio server passes `--additional-mcp-config @<path>`, which the help text documents for a file. The binary accepts `--additional-mcp-config` with such an entry, but an unauthenticated run stops before it starts the server.
- These shapes are the SDK's, not a captured run. The manual check on moon (acceptance criterion 10) is the first authenticated tool-using run; if a shape differs there, the parser and this section are corrected then.

## Layout

```text
crates/
  factory-core/      job state machine, pure, no I/O
  factory-server/    axum dashboard, SQLite, job loop, settings
  factory-runner/    podman workers, stream-json, git checkouts, gh
containers/
  factory/Containerfile
  worker/Containerfile
deploy/              Quadlet unit, deploy.sh and install.sh
e2e/                 Playwright browser tests, fake gh and podman, see Browser tests
```

`agents/` holds the factory's review skills: a `review` skill that judges a branch's diff before a merge and a `comment-review` skill that checks the comments the diff adds, with their `approve`/`changes` output schema in `agents/schemas/review.json`. Its `README.md` records which harness reads what. The worker image bundles the directory under `/factory-agents`. When the factory is configured with the agents directory (`FACTORY_AGENTS_DIR`), it mounts that directory there and a Claude reviewer run loads it with `--plugin-dir /factory-agents`; with the variable unset, the baked-in copy is present but a Claude run gets no `--plugin-dir` flag. The reviewed repository's own skills still load alongside it. The image also links the same skills to `/etc/codex/skills/factory`, where Codex reads them without a `--plugin-dir` flag, see "Running Codex in a worker". The image also carries Python and common shell tools so an agent can inspect a binary or parse JSON without a `nix shell` detour: `python3`, `jq`, `strings`, `file`, `xxd`, `hexdump`, `less`, `tree`, `fd`, `sqlite3`, `patch`, `make`, `zip`, `bzip2`, `zstd`, `bc`, `envsubst`, `lsof`, `ss`, `ip`, `dig`, `nc`, `rsync` and `shellcheck`. In the worker shell `grep` is a Claude Code wrapper around ugrep, which rejects some long regexes as too complex; `command grep` runs GNU grep.

Not built yet: the other factory skills (unslop, no-comments, open-pr, spec interview, and plan and split) and the live log over server-sent events. The comment review once listed for `verifying` is folded into the merge-time review above. The job page polls its fragment while a job is live, see Dashboard updates. `static/job-updates.js` keeps the log position across a swap: it saves in `sessionStorage` whether the reader was at the bottom or how far up they had scrolled, restores that on load, and re-applies it through an htmx swap hook. Server-sent events will replace the log poll with a live stream.

`open-pr` changes from maestro's version: the worker stops when its commits are ready, and the factory pushes and opens the pull request.

This repository follows the same standards as maestro: `CONTRIBUTING.md`, a check on pull request titles and descriptions, and prek hooks. Two gitleaks hooks guard against committed secrets: one scans staged changes, the other the current branch's history, which CI runs through `just lint`. `--redact` keeps values out of logs, and a known fixture goes into `.gitleaksignore` by fingerprint, never by directory. The repository has no ruleset on `main`. GitHub allows rulesets on a private repository only on a paid plan, and the factory stays private for now. Nothing on GitHub blocks a direct push or a merge with failing checks, so the reviewer merges only after CI passes. Merges are squash only, and GitHub deletes the branch after a merge.

The `Title and description` job reads the title and body with `gh pr view`, not from the event payload. The payload is a snapshot from when the event fired, so rerunning the job after an edit to the description checked the old text. `gh pr view` returns the current text. The job needs `pull-requests: read` for it.

## Lessons from building maestro's checks

- `grep -q` at the end of a pipeline under `set -o pipefail` can fail when it matches, because the writer gets SIGPIPE. Feed `grep -q` from a variable instead.
- macOS has bash 3.2 as `/bin/bash`. Hook scripts must work there.
- prek refuses to run when `prek.toml` is not staged.
- prek runs hooks without a `stages` setting at every stage, the `commit-msg` stage included. Set `default_stages` when adding hooks for other stages.
- A project setting in `.claude/settings.json` loads only when the session starts. A hook added mid-session does not fire until the next session.
