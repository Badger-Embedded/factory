# Factory design

The factory turns feature requests into pull requests. You describe a change in a dashboard. Claude Code agents clarify it with you, write a spec and a plan for you to approve, implement it in an isolated container, and open a pull request. You review and merge on GitHub.

The factory is separate from the projects it works on. Its skills, agents, hooks and per-project configuration live in this repository and are never committed to a target repository. A target repository keeps only its own rules, which bind people too: `CLAUDE.md`, `CONTRIBUTING.md`, CI and its GitHub ruleset. [maestro](https://github.com/Badger-Embedded/maestro) is the first project.

These decisions were made on 2026-11-19 while brainstorming in the maestro repository.

## Decisions

| Topic | Decision |
| --- | --- |
| Agent runtime | Agents run in rootless podman worker containers. Everything agent-specific sits behind one agent interface in `factory-runner`, the `AgentBackend` trait: the command after the image, the credential and config-directory environment variable names, the session-resume check, and the parser that turns the agent's stdout into the generic items the worker consumes. `worker.rs` keeps the generic `podman run` flags and names no one agent. Claude Code is the first agent and the only one that runs; see "Running Claude Code in a worker" for its implementation. Claude Managed Agents was considered and rejected in favor of local Claude Code on our own hardware. The worker image now also ships a pinned Codex CLI and the factory review skills, ahead of the `AgentBackend` that runs Codex; see "Running Codex in a worker". |
| Agent registry | `AgentRegistry` in `factory-server` maps each agent to what the server needs to run and present it: the credential, the worker image, the host config directory, the settings page URL, and the model aliases and effort levels the stage panel offers. It holds the `ClaudeToken` resolver and is built once at startup. For Claude the credential is that resolved token, the image is the `worker_image` setting from the Workers page, the host config directory and the stdout parser come from `factory-runner`'s `AgentBackend` (see "Agent runtime"), the settings page is `/settings/agents/claude`, the model aliases are fable, opus, sonnet and haiku, and the effort levels are the ones `factory-core` exposes. The podman executor reads the credential, the image and the host config directory from the registry rather than naming Claude, so no Claude-specific flag, env var or path lives in `podman.rs`. A run whose agent resolves no credential fails before any checkout or container; Claude's reason is "no Claude token is set". Codex is in the registry as the place the next agent goes: it has no credential, image or settings page, and its entry reports that it cannot run. |
| Host | `moon.local` (`ssh moon@moon.local`): Ubuntu 26.04, x86_64, 8 cores, 7.2 GB RAM, 74 GB free disk, systemd linger on for user `moon`. Tailscale is up at `100.77.68.75`. |
| Factory process | A Rust binary in its own container, run as a Quadlet systemd user service. It starts worker containers through the user's `podman.socket`. |
| Factory stack | axum, SQLite, server-rendered pages with htmx, and server-sent events for live logs. No frontend build step. |
| Dashboard access | The factory listens on localhost. `tailscale serve` publishes it over HTTPS on the tailnet and passes the Tailscale login in request headers. No separate login. |
| GitHub identity | The bot account `moonthebot`, logged in with `gh` on moon (scope `repo`). It must be a **Write** collaborator on each target repository, not Admin, so a ruleset's Admin bypass does not apply to it. Onboarding a project checks the repository against this as the bot, through the `GitHubRepos` trait: `GhRepos` runs `gh api`, and tests pass a fake so none reaches the network. `check_repo` returns errors and warnings. An error blocks onboarding: a repo that is not `owner/name`, one that is missing or not visible to the bot, a base branch that does not exist, no push access for the bot, and squash merges turned off, which the factory relies on. A warning does not: the bot holds Admin, the base branch has no protection or ruleset, the repo has no Actions workflow, and merged branches are not auto-deleted. GitHub answers HTTP 403 for the rules of a branch in a private repository on a free plan. That check then becomes a warning that names GitHub's answer, because it cannot tell whether the branch is protected. A 403 from any other call still means the checks could not run. Nothing calls the checks yet; the onboarding wizard is a later change. |
| Credentials | Only the factory holds the GitHub token. Workers get no GitHub credentials. |
| Claude auth | The subscription token from `claude setup-token`, held in the factory's encrypted secret store, the same store MCP header values use. An operator sets or replaces it from the settings page, so changing it needs no login to moon. The Claude agent page under Agents, at `/settings/agents/claude` with the heading "Claude", has the "Claude token" field. The token form posts to `/settings/agents/claude/token` and `/settings/agents/claude/token/clear`, and `/settings/claude` redirects to the agent page. It shows only whether a token is stored, never the value and not even in the input's `value` or the page source, the way an MCP header value's field does. A non-empty save replaces the token, after the factory trims surrounding whitespace and a trailing newline; an empty save keeps it; and a separate Clear button removes it. When the secret store is unavailable the field is disabled with a message and Clear still works, so a token stranded by a lost master key can still be removed. A saved token reaches the next worker run with no restart, because the `ClaudeToken` resolver reads it afresh. See "MCP secret storage" for the store. A `ClaudeToken` resolver reads the current token on each use: the stored token when the store is available, or `CLAUDE_CODE_OAUTH_TOKEN` from the environment when it is not, so a lost master key does not stop jobs while the old podman secret still passes the token in. At startup, when the store is available, holds no token, and the env var is set and not empty, the factory imports that value into the store and logs the import without the token, so the move off the podman secret needs no manual step on moon. Once a token is stored the env var is ignored. Workers get the resolved token to run Claude Code. Its usage limits are shared with interactive use. Switch to an API key if the factory hits them often. |
| MCP secret storage | Per-project header values for MCP servers are credentials, so the factory encrypts them at rest. Each value is sealed with XChaCha20-Poly1305 under a random per-value nonce, with the project, server and header name bound in as associated data, so a ciphertext copied into another row fails to decrypt. The ciphertext lives in the `secrets` table, keyed by project, server and header, separate from the server and per-project settings tables, so a later user system can add an owner column in a migration. The master key is 32 random bytes in the `factory-master-key` podman secret, held outside the database. `deploy/install.sh` generates it when it is missing, the same way it creates `gh-token`, so no step is manual, and it never regenerates the key on a later run. The Quadlet unit passes the key to the factory container alone. Workers never get it, so a stolen worker cannot read a credential, and a stolen database file or backup leaks nothing without the key. The key is excluded from database backups. Losing it makes every stored value unreadable, and each one must be entered again. When the key is missing or malformed the factory still starts and reports the secret store as unavailable, rather than refusing to run. Secret access goes through the `SecretStore` trait, with put, get and delete for MCP header values, and get, set and clear for the account-wide Claude token. The local encrypted backend is its only implementation now, and each row records its backend, so an external manager such as Vault can be added later without a schema change for existing rows. The Claude subscription token from `claude setup-token` is stored here too, sealed the same way but in one reserved row of the `secrets` table whose `server` is empty, which no MCP server name can be. So `delete from secrets where server = ?` for any MCP server, including one named `claude`, never touches it, and deleting or renaming such a server leaves the token in place. Its ciphertext binds a fixed domain tag rather than a project, server and header, so a ciphertext moved between the token row and an MCP header row fails to decrypt in either direction. |
| MCP server registry | An operator adds remote MCP servers on the MCP servers settings page and edits or deletes one on its own page, see Settings layout. The `mcp_servers` table holds one row per server: a unique `name`, an `https` `url`, and a JSON list of `headers`. A name is 1 to 32 characters of `a-z`, `0-9` and `-`, unique, because it keys the run's MCP config and is part of the proxy path. The URL must parse, use `https` and have a host. Each header name is a header a project may fill with a value; it must be a valid HTTP token and not one the factory sets itself or the streamable-HTTP transport owns: `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Mcp-Session-Id`, `MCP-Protocol-Version` and `Last-Event-ID`. Two header names that differ only in case collapse to the first spelling. The transport is streamable HTTP. stdio servers and the older SSE-only transport are out of scope. Deleting a server deletes every project's `project_mcp` row and every stored secret for it in one transaction. An edit that changes the URL's origin, its scheme, host or port, deletes every stored secret value for the server, so no dashboard user can repoint a server at their own host and collect another project's keys, and the server's page asks before it saves such an edit, see Settings layout. An edit that changes only the path keeps the values. Removing a header name deletes the stored values for that name alone. A rename is a remove plus an add: the old name's stored values are gone and each project enters a value under the new name. context7 at `https://mcp.context7.com/mcp` is the first server, added by hand through the form. |
| MCP project settings | Each project has a page per server, see Settings layout, with an enabled switch, a checkbox for each of the five stages, clarify, spec, plan, implement and review, the same five as the project models, and a write-only field for each header the server declares. The `project_mcp` table stores the enabled flag and the five stage flags, keyed by project and server. A project with no row reads off with no stage, so a newly added server and a newly onboarded project both start off. The save handler refuses an enabled server with no stage checked and returns a 400 that names the server. A header field shows only whether a value is stored, "set" or "not set", never the value and not even masked. An empty field leaves the stored value as it is, a typed value replaces it, and a "clear" checkbox deletes it. A header with no stored value is not sent, so a keyless server such as context7 needs none. The page posts to `POST /settings/projects/<project>/mcp/<server>`. The handler checks the whole form before any write, so a rejected submit leaves every table as it was. Saving one project's page for a server leaves other projects and other servers alone, and saving the project's own form leaves its MCP settings alone. The scheduler reads the registry and the project's settings on every run, the way it reads the models, so a change reaches a job in flight at its next run. |
| MCP header-name editing | The settings page edits a server's header names in one text box per name, on the add form and each server's edit form, not a textarea of names. An "Add header" button appends an empty row and each row has a "Remove" button, both run by an inline script. The boxes post a repeated `header` field that the add and edit handlers trim, dropping an empty row, so the form works without JavaScript too: the add form starts with one empty box, an edit form shows one box per stored name plus one empty box, you add one name per save and clear a box to drop its name. Each box's `pattern` allows only the HTTP token characters `mcp::normalize_headers` accepts, so a pasted `Authorization: x` is refused in the browser before the server validates it again, see MCP server registry for the validation and the propagation of an add, remove, rename or URL origin change to every project's stored values. A browser compiles a `pattern` as a RegExp with the `v` flag, where `-` and `|` are syntax inside a `[...]` class and must be escaped (as `\-` and `\|`), and an invalid pattern is silently ignored, so both the header-name and the server-name patterns escape them. Only the name goes in the box; the value is per project and encrypted, which the hints state, see MCP secret storage. |
| MCP proxy | The factory runs an HTTP proxy for MCP traffic on its own listener, `FACTORY_PROXY_LISTEN`, which the Quadlet unit sets to `0.0.0.0:8081`, separate from the dashboard on `127.0.0.1:8080`. The factory container and its workers share the `factory` podman network, which `install.sh` creates, so a worker reaches the proxy by the factory's container name at `FACTORY_PROXY_URL` (`http://factory:8081`), while the dashboard port, published only to the host loopback, stays out of a worker's reach. For each agent run with at least one active server the scheduler issues a run token through `RunTokens`: 256 random bits held only in the factory's memory, scoped to the job and the servers active for the run's stage. The scheduler revokes the token when the worker exits, whether the run succeeded, failed or was cancelled, and a factory restart drops every token. The worker gets `claude --mcp-config` with one `http` entry per active server, each pointing at `http://factory:8081/mcp/<server>` and carrying `Authorization: Bearer <run token>` as its only header. A run with no active server gets no MCP flags, so its arguments are unchanged, and check runs and every non-agent container get no config and no token. The proxy answers 401 to a missing, unknown or revoked token and 403 to a server outside the token's scope. For an authorized request it drops the worker's `Authorization` header, adds the project's stored headers, and forwards the method, path suffix, query, body and the protocol headers, `Content-Type`, `Accept`, `Mcp-Session-Id`, `MCP-Protocol-Version` and `Last-Event-ID`, to the server's URL. It streams a `text/event-stream` response without buffering it, except the event that answers a filtered `tools/list`, see MCP tool toggles, and supports the POST, GET and DELETE that streamable HTTP uses. It follows no redirect, so a 3xx cannot carry the headers to another host and is returned to the worker as it is. It uses a 10-second connect timeout and no total timeout, so a streaming response may stay open for the length of the run. The credential stays out of the worker because the worker runs with `bypassPermissions`: it could otherwise read the value from its config, arguments or environment, and a prompt injection in a repository or an MCP response could make it print or send the key. The proxy keeps the value on the factory side, so the worker holds only a run token the proxy swaps for the real headers. The proxy also reports each `tools/call` it forwards, which the factory records as an `mcp-tool-call` row, see Job MCP tool calls. |
| MCP unavailable servers | An enabled server that is unreachable when a run starts does not fail the run. The run goes on without the server's tools, as Claude Code does. Two paths report it. The runner reads the `mcp_servers` list in the stream-json `system`/`init` line and warns about each active server whose status is not `connected`. The proxy warns when it cannot reach the server, a connection times out, or the server answers 5xx. The scheduler also warns about a server it skipped because a stored header value would not decrypt, so a broken credential never lands in a worker's config. All three funnel through `McpWarnings`, which dedupes per run so a server is warned at most once, and writes the warning through `Store::record_mcp_unavailable`: a factory line to the job log that names the server and the reason, and an `mcp-unavailable` row in `job_events` with `<server>: <reason>` in its `detail`, written the way `add_cost` writes a cost row, so it changes neither the job's stage nor its turn. The reason names no credential. The job page timeline shows the row as a note under the step the run was in. |
| MCP connection check | A project's page for a server has a "Refresh connection" button that tests the server with that project's saved header values and refreshes the project's list of its tools, see MCP tool toggles. It posts to `POST /settings/projects/<project>/mcp/<server>/check` through htmx, which swaps the returned HTML fragment into a result area, so the page does not reload and unsaved input survives. The handler resolves the saved URL and the project's saved values through `StoreUpstreams`, the same resolver the proxy uses, so the check and a real run send the same headers. It ignores any form field posted with the request, so an unsaved value typed into the page is never sent, and the hint says to save first to check new ones. An unknown project or server gives 404. The check sends one JSON-RPC `initialize` POST, whose `clientInfo` carries the name `factory` and the crate version because the MCP schema requires both and a strict server such as Composio's rejects a request without `version`, with `Content-Type: application/json` and `Accept: application/json, text/event-stream` plus the project's values, follows no redirect like the proxy, uses the proxy's 10-second connect timeout, a 15-second total timeout, and reads at most 1 MiB of the body. Success is a 2xx reply, JSON or SSE, whose `result` carries a `protocolVersion`. The result names the server and version when the reply gives them. A 2xx reply with a JSON-RPC `error` shows the error's code and message, cut to 300 characters, with every header value the check sent replaced by `[redacted]`, since a server may echo the request. On success it sends a best-effort `DELETE` with any `Mcp-Session-Id` to end the session. The result messages cover a reachable MCP server, an unreachable host, a timeout, a 401 or 403 that points to the project's header values, another 3xx, 4xx or 5xx with a 3xx `Location`, a 2xx JSON-RPC error, and a 2xx that is not an MCP reply. A declared header with no stored value is named in the result, and the check runs without it. No header value reaches the fragment, a log line or an error. The result is not stored: reloading the page clears it. The HTTP part sits behind the `McpChecker` trait, held by the dashboard the way it holds `RepoChecker`, so a test uses a fake and the real `HttpMcpChecker` is tested against a local `http://` server. The "Add server" button runs no check, because the header values belong to projects and the add form has none; the per-project check is the one the requester chose. |
| MCP tool toggles | A project can turn off single tools of an MCP server it uses. Every tool is on by default, so the factory stores the tools that are off, and a project with none off behaves as before. The setting is per project and server and applies to all five stages, without a per-stage grid. A tool a server adds later starts on. The settings page marks it "new" so an operator sees it. The `project_mcp_tools` table holds the last tool list per project and server, keyed by project, server and tool name, with the tool's description, an `offered` flag, a `disabled` flag and the number of the refresh that first saw it. `project_mcp_tool_refreshes` counts each project and server's refreshes, so a tool is "new" when the latest refresh first saw it and is not the first one. The list is per project because a server may offer different tools for different credentials. "Refresh connection" fills the table, see MCP connection check: after a successful `initialize` it sends `notifications/initialized` and pages through `tools/list` by its cursor with the negotiated `MCP-Protocol-Version` and the `Mcp-Session-Id`. The same 15-second total timeout covers the whole exchange, and each reply is read up to 1 MiB. Only a complete list replaces the stored one. A tool missing from it keeps its row with `offered` cleared, so a turned-off tool stays off if the server offers it again, and the page lists it as "no longer offered". A failed list keeps the old rows and the result says the tools could not be listed. The refresh route returns the page's refresh area, the button, the result and the tool list, and htmx replaces that area, found from the button with `closest .mcp-refresh`. The swap drops unsaved changes to that list's checkboxes, and the hint says so. The list sits on the project's page for the server as one checkbox per stored tool, checked when on, with its description. Each shown tool posts a hidden `mcp.<server>.shown.<tool>` field and, when checked, `mcp.<server>.tool.<tool>`. A server name has no `.`, so the handler splits the tool name off after the prefix. The save handler turns off the shown tools left unchecked and turns on the checked ones. It leaves a tool the form did not show as it is, so a refresh between render and save turns nothing off by accident. The proxy enforces the setting, because a worker with `bypassPermissions` and a run token could call a tool with `curl` that a Claude Code flag only hid from the model. `StoreUpstreams` returns the server's turned-off tool names with its headers, read on each request, so a change reaches a run in flight at its next request. For a POST, the proxy parses the body it already buffers as JSON-RPC, rejecting duplicate keys so it and the server cannot read two different tool names. A `tools/call` whose `params.name` is off gets a JSON-RPC error that names the tool as turned off for the project, with the request's `id`, and the proxy forwards nothing. A batch array holding such a call gets a 403 and nothing is forwarded. When the server has a tool turned off, a POST body that does not parse gets a 400 rather than being forwarded. A `tools/list` reply is buffered up to 4 MiB and the turned-off tools are removed from `result.tools`, in a JSON body or in the SSE event carrying the response, with other SSE events passed through as they are. A reply over the cap or one that does not parse is relayed unchanged, and the call block still applies. A stream resumed by `Last-Event-ID` may replay an unfiltered list, and the call block applies there too. Every other request and response streams as before. Each blocked call goes through `McpWarnings`, deduped per run, server and tool, and `Store` writes a factory line to the job log and an `mcp-tool-blocked` row in `job_events` with `<server>: <tool>` in its `detail`, which the job page timeline shows as a note under the step. Deleting a server deletes its tool rows with its `project_mcp` rows. A rename loses them like the stored values. An edit that changes the URL's origin clears `offered` on every row and keeps each `disabled` flag until the next refresh. |
| Job MCP tool calls | Every MCP call a job makes passes through the proxy, so the proxy records it. After `screen` lets a request through, and before it forwards the body, the proxy finds every `tools/call` in the body, which is one for a single JSON-RPC object and several for a batch array, and reports each through its callback. This runs whether or not the project turned a tool off. `Store::record_mcp_tool_call` writes one `mcp-tool-call` row to `job_events` for each call, with `<server>: <tool>` in `detail` and the job's current stage, pull request and turn, the way a cost row is written, so it changes neither the stage nor the turn. It writes no job log line, because the agent's own `tool mcp__…` line already records the call, and it does not deduplicate: every call is a row. A refused call is recorded only as `mcp-tool-blocked`, never also as a call. With no tool turned off the reading is lenient: a body that is not JSON, or a `tools/call` with no string tool name, is forwarded unchanged and records nothing. The timeline adds no note for an `mcp-tool-call` row, and its step timing and cost are unchanged, because the row stores the stage the job is already in. Job expiry deletes the rows with the job. The job page shows these calls in its own "MCP tool calls" card, see Job page look. |
| Approval gates | Spec, plan and publish. Each project has its own gates, in a `project_gates` table in SQLite with one row per project and a column per gate. The factory-wide gates in the stored settings are the defaults: onboarding a project copies them into its row, and a later change to a default leaves existing projects alone. Spec and plan are on in the code default, publish is off. The settings page edits the defaults on the Default gates page and a project's gates on its pipeline, see Settings layout. A job copies its project's gates when it is created, so a later settings change does not touch existing jobs. Everything after the last gate runs without stopping, apart from questions the agent asks. The state machine stops at a gate only when the job has it. A job with the publish gate stops before the first push of each planned pull request and waits for approval. Later pushes to the same pull request, such as fixes for CI or review comments, are not gated. Gates were one global setting before. A one-time migration at startup gives every project with no `project_gates` row the current global gates, the way `Store::migrate_global_auto_merge` moved auto-merge, so each project keeps its earlier behaviour. You merge on GitHub, unless the project's auto-merge setting is on: then the factory squash-merges a pull request once every check passed and no review comment waits for the agent. Auto-merge is per project, see Project settings. A pull request with no checks reported yet is not merged, so a push is never merged before GitHub starts its CI. |
| Settings layout | The settings pages share a sidebar with four groups. Factory has Workers, Default gates and GitHub. Agents has one entry per registered agent, from the registry: Claude links to its page, and an agent that cannot run, such as Codex, is a disabled entry with no link and a "Not available yet" note. Integrations has MCP servers. Projects has one entry per project and a link to onboarding. Each entry is its own page with its own URL: `/settings/workers`, `/settings/gates`, `/settings/github`, `/settings/agents/claude`, `/settings/mcp`, `/settings/mcp/<server>`, `/settings/projects/<project>` and `/settings/projects/<project>/mcp/<server>`. `/settings` redirects to the first project, or to Workers when there is none. Each page has one form, and its Save button sits in a bar that stays at the bottom of the window. The Save button comes before a Delete or Clear button in the form, so Enter in a field saves. Once an input of the form changes, the bar reads "Unsaved changes." and leaving the page asks first. `static/settings-form.js` does both, and without it the forms save the same way. A save redraws the same page with a notice. Adding a server opens its page, and deleting one opens the MCP servers page. A project's page draws its settings as the path a job takes: clarify, spec, plan, implement, review and merge, with the spec, plan and publish gates between them. Each stage shows its model, its effort and the MCP servers on in it. The agent is set in the panel, not shown on the node. Selecting a stage, a gate or merge opens its panel under the pipeline. The selection is a `?stage=` query parameter, `clarify` to `review`, `gate-spec`, `gate-plan`, `gate-publish` or `merge`, and an unknown value opens clarify. It works without JavaScript, a link opens the same panel, and a save comes back to it. Every panel sits in the one form and only the selected one shows, so a save posts every field and a hidden panel's values are kept. `static/settings-pipeline.js` switches panels without a reload, keeps the address and the form's action on the open panel, and updates the nodes as the fields change. A stage panel sets the stage's agent, its model, its effort and a switch per MCP server for that stage. The agent control lists every registered agent above the model: Claude is a selectable radio, and an agent that cannot run, such as Codex, is a disabled radio marked "Not available yet". It preselects the stage's effective agent, Claude when the project saved none. The model suggestions and the effort radios come from the selected agent, and for Claude they are the aliases fable, opus, sonnet and haiku and the levels low, medium, high, xhigh and max, as before. The model is typed or picked from the aliases, and the effort is five radio buttons. A server's switch is on when the server runs in that stage. Saving with a switch on turns the server on in exactly the stages switched on. Saving with every switch off stops a running server and keeps its stages for the server's own page, and leaves a stopped server as it is. The review stage reads Off and is drawn dashed while LLM review is off, and its panel holds the LLM review switch. A gate panel shows the factory default, marks a gate that differs from it on the panel and with a dot on its diamond, and offers "Use the default". The merge panel holds auto-merge. A card under the pipeline sums up each MCP server for the project and links to its page. A project's MCP page holds the project's header values, the connection check, the five stage switches and the tool list with a filter, a count of the tools on, and buttons to turn every shown tool on or off. `static/mcp-tools.js` runs those controls, and without it they stay hidden. A server's page holds its URL and header names and lists the projects that use it. A save that renames or removes a header, or changes the URL's origin, and so deletes stored values, is held back: `Store::mcp_edit_deletes` lists the values it would delete without writing, and the page shows the posted URL and names with each project and header it deletes and a button that saves anyway. An edit that deletes nothing saves at once. Deleting a server is a form of its own, below the edit form, and needs the server's name typed into it. Any other name deletes nothing and redraws the page with the problem. |
| Notifications | The dashboard inbox only. |
| Job board | The index page is an inbox of the selected project's jobs in one column, sorted by what you must do. Each job's lane comes from one function that also decides its turn badge, from the same stage and turn rules, so they never disagree. The lanes are You, Agent, Factory, Failed and Done. A merged or cancelled job is in Done. A failed job is in Failed. A job that needs an answer or approval, or a review on GitHub, is in You. A job in review with auto-merge on is in Factory. The board shows four sections, top to bottom: Needs you for the You lane, Failed, Running for the Agent and Factory lanes together, and Done. Each section has a count and lists the newest job first. The new-request form above the sections is a one-line bar. It grows and shows the image picker once it has focus, text or a pasted image, using CSS `:focus-within` and `:has()` with no script. A section with no job does not render. When no job is live, the board says "Nothing needs you and no job is running." Done lists five jobs, and the older ones sit in a collapsed `<details>` element, so it works without JavaScript. Each job is a row: the id, the title, then a line with the turn badge, the steps, the detail, the requester and the cost. The title is the first line of the request, cut at 80 characters, with the full line in its `title` attribute. The steps are nine small segments for requested, clarifying, spec, plan, implementing, verifying, pr-open, ci-and-review and merged, marked done, current or to come. A job with several pull requests shows the steps of the one it is on. Only a live job shows them. The detail is the stage label for a live job, such as "implementing, PR 2 of 7", and the failure reason for a failed job. A merged or cancelled row has no detail, because its badge says so. | Request attachments | The New request form posts multipart. A request carries at most 5 attachments of at most 10 MiB each, images and files counted together, and the request text may be at most 256 KiB. The handler checks each upload by its bytes, not by file name or declared type, in this order: the PNG, JPEG, GIF and WebP signatures are images; a `PK\x03\x04` or `PK\x05\x06` signature is a ZIP file; valid UTF-8 with no NUL byte, which allows a leading byte order mark, is a text file. Anything else, including a PDF, a UTF-16 file or a named zero-byte upload, gets a 400 that names the accepted types. A request over a limit, or one with attachments and no text, also gets a 400 and creates no job. An SVG file passes the text check and is stored and served as text, so the dashboard never renders it as an image. The factory saves each image as `<data_dir>/jobs/<id>/images/image-<n>.<ext>` and each file as `<data_dir>/jobs/<id>/files/file-<n>.<ext>`, where `<ext>` is `txt` or `zip`, under a name it generates, so an upload's file name never reaches the file system. The image names are recorded in a `job_images` table. Each file is recorded in a `job_files` table with its generated name and its original name, which is the upload's file name cut to its last path component and 255 characters, used only for display, the download name and the prompt. `factory-core`'s `Job` holds no attachment data, since it does no I/O. Job expiry deletes the `job_files` rows with the job, and its `files/` directory goes with `<data_dir>/jobs/<id>`. A small script, `static/paste-images.js`, attaches an image pasted into the request textarea to the file input, previews a picked image as a thumbnail and any other file as a document or archive icon with its name, each with a Remove button, and leaves the form working without the script. The job page shows the images next to the request and lists each file below as an inline-SVG icon tile, a document icon for a text file and an archive icon for a ZIP file, with the original name as the caption. An image is served from `GET /jobs/<id>/images/<name>` and a file from `GET /jobs/<id>/files/<name>`, each serving only a name its table lists for that job. A text file is served as `text/plain; charset=utf-8` and a ZIP file as `application/zip`, both with `X-Content-Type-Options: nosniff` and a `Content-Disposition: attachment` header whose download name is the original name, percent-encoded in a `filename*=UTF-8''…` parameter so it never enters the header unencoded. When a run starts a fresh session, the runner copies the images into the checkout under `.git/factory-images/` and the files under `.git/factory-files/`, which git does not track, so the checkout stays clean. It appends the image paths to the prompt and tells the agent to look at them, then lists each file with its worker path and original name; for a ZIP file it tells the agent to list the archive with `unzip -l` and unpack it with `unzip -d` under `.git/factory-files/` and not to copy its contents into the repository unless the request asks for that. The worker image installs `unzip` for this. The clarify run is the first such run. A run that resumes a session adds nothing, because the session already has them. While a job waits in `requested`, its text and attachments can still change; see "Request editing". |
| Request editing | A job waits in `requested` until a worker is free, shown on the board as queued. While it is queued, the request card shows an Edit link to `GET /jobs/<id>/edit`, a form that posts to `POST /jobs/<id>/edit` as multipart. Once the scheduler applies `Event::Start` and the job moves to `clarifying`, the request can no longer change: the GET redirects to the job page, the card drops the Edit link, and a POST from a stale page gets a 409. The edit form starts the textarea with the current text, shows each current image and file with a Remove checkbox that posts the attachment's stored name, and reuses `static/paste-images.js` for the file input. The POST applies the New request rules: the trimmed text must be non-empty and at most 256 KiB, each new upload is classified by its bytes and is at most 10 MiB, and the kept attachments plus the new ones are at most 5. A `remove` value that names no stored attachment, or any broken rule, gets a 400 and changes nothing. `factory-core` gains `Event::Edit { request }`, which applies only at `(Requested, Factory)`, replaces the request text, leaves every other field alone, and records an `edit` history row; in any other stage or turn it returns `Rejected::Unexpected`. The kept attachments keep their old order and come before the new uploads in upload order, and the factory renumbers images and files from 1, each type apart, as the New request handler does, so the name-sorted directory listing a run reads matches the table order. A kept file keeps its original name; a new one takes the upload's name by the usual rule. To keep the edit and the scheduler's `Event::Start` from racing, the handler writes the new attachment set to a `staging/` directory under the job, then in one store transaction, under the connection mutex that `Event::Start` also takes, checks the job is still `requested`, swaps the staged set in over the old one, replaces the `job_images` and `job_files` rows, and applies `Event::Edit`. So the edit either lands before Start, and the clarify run reads the new text and attachments, or it is rejected with a 409 and changes neither the store nor the files. A disk error before the commit restores the old set, returns a 500 and leaves the job queued, unlike `create_job`, which cancels a job whose attachments fail to save. An edit keeps the job's id, created-at time, project and gates, so it holds its place in the scheduler's oldest-first order. | Job expiry | The job loop deletes a merged, failed or cancelled job once its `created_at` is more than 30 days old. The age counts from the request, not from the day the job finished. The factory deletes the job row, its rows in the other tables, and `<data_dir>/jobs/<id>`. A job that is not finished stays however old it is. When one job fails to delete, the loop logs it and goes on with the others, and the next pass tries it again. A merged job loses its checkout and session well before this, see "Merged job cleanup"; the directories being gone already does not stop the full deletion at 30 days. |
| Merged job cleanup | A merged job is final: no event moves it out of `Merged`, it has no next command, and Retry applies only to failed jobs, so nothing reads its checkout or session files again. On every job-loop pass, after expiry, the factory deletes `<data_dir>/jobs/<id>/work` and `<data_dir>/jobs/<id>/claude` for each merged job that still has either directory. `work/` is the git checkout the workers and checks run in, which holds build output such as cargo's `target/`; `claude/` is the Claude Code config directory with the session files `--resume` reads. On moon the merged jobs' directories had grown to about 50 GB of the 74 GB free disk, which this frees. The check runs every pass, not only on the transition into `Merged`, so it also cleans jobs merged before this change and retries a deletion that failed. The pass skips a merged job while the scheduler still holds an unfinished task for it. A deletion error is logged with the job id and the loop goes on, the way expiry does, and a directory already gone counts as success. After both directories are gone the factory appends one line to the job log saying it removed the checkout and session files to free disk space, written only on the pass that deleted something, so a job does not collect the line on every pass. The cancel form sits outside every swapped region. A fragment renders from the same data as its full page, so the two cannot disagree. A merged, failed or cancelled job carries no polling attribute, so its page does not poll; a page open when a job reaches one of those stages gets a fragment that swaps the poller for one with no trigger, which ends the loop. Server-sent events stay reserved for the live log, a separate item still to build. htmx is vendored as a static file the factory serves at `/htmx.min.js`, loaded with a deferred script tag in the page head. It does not come from a CDN, because the dashboard runs on a tailnet host that cannot reach one. |
| Dashboard time zone | SQLite stores every timestamp in UTC, as `CURRENT_TIMESTAMP` writes it, and the dashboard shows each one in the time zone of the browser that loads the page, because visitors work in different zones. The server has no time zone setting. Each rendered timestamp is wrapped in a `<time datetime="YYYY-MM-DDTHH:MM:SSZ" data-format="…">` element through one helper in `factory-server`: the `datetime` attribute carries the stored UTC time in ISO 8601 with a `Z`, and the element's text is the same UTC time the page showed before, labelled `UTC`, so a page with JavaScript off still shows a correct time. `data-format` is `datetime`, `time` or `time-seconds`, the three layouts the dashboard uses: a full date and time, `HH:MM`, and `HH:MM:SS`. The helper covers the job header `created_at`, the log line times, the timeline step, since, approval and note times, and the plan usage report and reset times. `static/local-time.js`, inlined on the board and the job page, rewrites each element to the browser's zone with `Intl.DateTimeFormat` in a fixed 24-hour layout, adds the short zone name to a full date and time, such as `CET` or `EST`, and sets the element's title to the full local time. It runs on load and on htmx's load event, so the 5-second fragment polls and out-of-band swaps are converted too, and it reads only the `datetime` attribute, so running it twice on one element changes nothing. Storage, the retention query `created_at < datetime('now', ?1)`, and every time sent to GitHub, a worker or the server log stay in UTC. |

## Claude plan usage source

The board shows one account-wide tile with the Claude subscription limits: the 5-hour window, the weekly window and the Fable window. The factory runs Claude Code with the token from `claude setup-token`, see "Claude auth".

### The usage endpoint does not work with a setup token

The first version of the tile fetched `GET https://api.anthropic.com/api/oauth/usage?skip_spend=1` every 5 minutes with the factory's token. A spike on 2026-11-20 chose it as the endpoint the interactive `/usage` panel calls. Every authenticated call in the spike returned HTTP 429, so it never saw a 200 body. On moon every fetch returned 429 too, including the first one after a restart, so the tile never showed.

A `claude setup-token` token carries only the `user:inference` scope. The Agent SDK reference says such a token "doesn't qualify" for the `/usage` report "because it carries only the `user:inference` scope". Claude Code 2.1.330 checks that its token has the `user:profile` scope before it calls `/api/oauth/usage`, and makes no call when the scope is missing. So the endpoint is the source for a `claude login` token, not for ours. The 429 also carried `retry-after` of up to an hour, which the 5-minute poll ignored.

`claude -p "/usage"` is no source either. In print mode `/usage` resolves to the local session-cost command and prints this session's cost, not the plan limits.

### Decision: read the windows from worker runs

The API sends the plan windows in `anthropic-ratelimit-unified-*` response headers on every inference request, whatever the token's scopes. Claude Code reads them and, in `-p` stream-json mode, writes a `rate_limit_event` line:

```json
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":1795234800,"rateLimitType":"five_hour",
 "unifiedWindows":{"five_hour":{"utilization":0.77,"resetsAt":1795234800,"status":"allowed"},
                   "seven_day":{"utilization":0.33,"resetsAt":1795676400,"status":"allowed"}}}}
```

A run on moon with the factory's token wrote this line on 2026-11-21. `utilization` is the fraction of the window used and `resetsAt` is a Unix timestamp. `unifiedWindows` holds a `five_hour`, `seven_day` and `seven_day_overage_included` entry for each window the API reported. Claude Code labels `seven_day_overage_included` "Fable limit", so the tile shows it as Fable. An event from a Claude Code version without `unifiedWindows` reports one window, named by `rateLimitType`, with `utilization` and `resetsAt` at the top level, and the parser reads that shape too.

The runner's stream parser turns the line into `StreamItem::PlanUsage`, and `factory_runner::run` passes each report to a callback. The podman executor's callback writes it into the `PlanUsageCache` the dashboard reads. Each window in a report replaces the cached one, and a window the report leaves out keeps its last value. The factory makes no request of its own for plan usage, so it spends no tokens and meets no rate limit on it.

The numbers move only while a worker runs. Usage from interactive sessions on the same account shows up at the next run's report. The tile therefore shows the time of the last report, and a window whose reset time has passed reads as reset rather than show the old number. The tile has no per-model windows beyond Fable, because the event carries none.

Risk: `rate_limit_event` is part of Claude Code's stream-json output, which carries no stability promise. If the line changes shape the parser drops it, the cache keeps its last report, and the "as of" time shows how old that report is.

## Job flow

Each job moves through these states. Each ✋ is an approval gate. A job has the gates its settings turned on when it was created.

```text
requested → clarifying → spec ✋ → plan ✋ → implementing → verifying → publish ✋ → pr-open → ci-and-review → merged
```

- **requested.** The job waits here for a free worker, which the board shows as queued. While it waits, its requester can change the request text. `Event::Edit` replaces the text and applies only at `(requested, factory)`, so a job that has already started rejects it. The scheduler's `Start` copies the current text into the clarify task.
- **clarifying.** The agent reads the repository and asks questions. A headless run cannot wait for answers, so the run ends with its questions as structured output. The dashboard shows them, and the next run resumes the same session with your answers.
- **spec.** The agent writes the goal, scope, what is out of scope, and acceptance criteria. The run starts a new session. Its prompt holds the request and the answers to the clarifying questions.
- **plan.** The agent splits the work into pull requests. A large refactor gets its own pull request first, as maestro's `CONTRIBUTING.md` requires. The run starts a new session. Its prompt holds the request, the answers and the approved spec.
- **implementing.** One worker session per pull request. The prompt holds the request, the answers, the approved spec, the titles of all planned pull requests and the summary of this one. The worker commits in the job workspace and stops when the commits are ready.
- **verifying.** The factory runs the project's checks in the worker. Failures go back to the session. The comment review once planned here is now part of the merge-time LLM review, see `ci-and-review, the LLM review pass`.
- **publish.** With the publish gate on, the job stays in verifying once the checks pass and the factory collects the branch's commits and diff stat from the checkout. The dashboard shows them with the pull request title and description. Approve moves the job to pr-open. Request changes sends your feedback to the pull request's session, then the checks run again and the job returns here. A revision does not count toward the 5 failed rounds. The factory pushes nothing before you approve.
- **pr-open.** The factory pushes the branch and opens the pull request as moonthebot. Before the push, it asks GitHub for a merged pull request from the branch. You can merge a pull request while the factory is between a CI fix and its push, and GitHub then deletes the branch. The push would fail on every retry, because `--force-with-lease` expects the deleted branch. So when the branch has a merged pull request, the factory pushes nothing, records that pull request's number and applies `Merged`, and the job moves to the next pull request.
- **ci-and-review.** The factory polls CI and review comments, and feeds failures and your comments back into a resumed session until CI is green and you merge. When the pull request no longer merges cleanly, the factory fetches the newest base branch into the checkout, since workers have no GitHub credentials, and the agent rebases onto it. A conflict counts toward the job's limit of 5 failed rounds per pull request, so an agent that cannot resolve one stops.
- **ci-and-review, the LLM review pass.** When CI is green and the project has LLM review on, a reviewer runs before the factory merges. The scheduler applies `StartReview`, which moves the job to a review turn: a worker run in a `review` session of its own, separate from the implement session, with no GitHub token. It reads the branch diff from the checkout and ends with `approve`, or `changes` with feedback. Each pass is kept as a numbered `ReviewPass` with its verdict and feedback, for the job page. `approve` records the approval and returns the job to watching the pull request, so the factory merges when auto-merge is on or waits for you when it is off. `changes` sends the feedback to the implement session as a review-fix run, the same path as a human review comment; after the push CI runs and the reviewer runs again. The review session resumes across passes, so a later pass sees only the commits since the last one and reviews those. A push clears the recorded approval, so the reviewer reads each head afresh. The review-fix runs count toward a review cap of 5, held in `review_rounds` and separate from the 5 failed check and CI rounds, so a job can spend both on one pull request. At the cap, or when a reviewer run crashes, times out or returns no valid result, the review fails closed through `ReviewFailed`: the job does not merge and waits for you with the reason. While it waits, the factory keeps watching the pull request, but the watch is passive: `next_command` returns a `WatchPr` with `watch_only` set, and the watch reports only a merge or a close by you. It never merges the pull request, even with auto-merge on, and never restarts the reviewer. Merging it on GitHub moves the job on to the next pull request, or to `merged` for the last one. Closing it without merging fails the job. This is what frees a job stuck in review-stopped after you merge its pull request by hand. The review-stopped card also shows a Retry button, see `Retry a failed job`: a reviewer run that failed reruns the reviewer, and a review that hit its cap of 5 addresses the last feedback with 5 fresh rounds. The state machine is pure, so it models the pass with no I/O; the scheduler runs the worker and decides the merge.
- **Rerun on request.** When the agent runs a `FixCi` task and finds nothing to commit, such as after a flaky failure, it returns `rerun_ci` with a reason. The job moves to a factory turn that runs `Command::RerunCi`, which carries the reason for the log. This counts a failed round through `fail_round`, so the limit of 5 still applies and the fifth round fails the job. The `CiRerun` event returns the job to watching the pull request. The result is rejected in any other turn. The scheduler logs the reason, then calls `Executor::rerun`, which runs `GitHub::rerun_failed` with the factory's token. The worker still gets no GitHub token. When `gh` fails, the job stays in the rerun turn and the scheduler tries again after `poll_seconds`. After a successful rerun the scheduler applies `CiRerun` and holds the next watch for `poll_seconds`. `rerun_failed` already waits until GitHub stops reporting the old failure, so the next watch does not count it as a second round. When the head has no failed Actions run, the scheduler logs that and applies `CiRerun` anyway. The next watch then sees the failure again and asks the agent again, which counts another round, so the limit of 5 ends the loop.
- **Retry a failed job.** A job that used up its 5 failed check or CI rounds ends in `failed` with a retry target: the `verifying` or `ci-and-review` stage of the pull request it failed on. A job whose agent run failed ends in `failed` with the stage and task of that run as its retry target. The failure card on the job page shows a Retry button, which posts to `POST /jobs/{id}/retry`. `Event::Retry` returns the job to that stage with a factory turn and resets the failed-round count, so the factory runs the checks or watches the pull request again and the agent gets 5 fresh rounds before it fails once more. For a failed agent run, `Event::Retry` runs the same task again in the same session and keeps the failed-round count. This covers a run stopped by the plan's usage limit, and a job whose project was not configured, which fails again if the project is still missing. `failed` is therefore no longer always terminal. `Job::can_retry` reports whether a retry would resume the job. A legacy job stored before the retry target existed carries none. The factory recognises it by its exact old reason, or by an agent failure reason that starts with "the agent run ended with", and resumes at `ci-and-review` of its highest-numbered pull request. A legacy job with no pull request number is not retryable. A job closed unmerged, and a cancelled or merged job, reject `Retry`, and their failure cards show no button. The retry leaves `created_at` alone, so the 30-day expiry is unchanged.

  A stopped review retries the same way, though its stage is not `failed`. A job in `ci-and-review` waiting at `ReviewStopped` with a pull request number is retryable, and the review-stopped card shows the same Retry button. Where it resumes depends on why the review stopped, recorded on the ask as `ReviewStop` so the retry never reads the reason text. When a reviewer run failed, `Event::Retry` returns to the `review` task in the same review session and leaves the review and failed round counts as they are. When the review hit its cap of 5, `Event::Retry` clears `review_rounds` and sends the last pass's feedback to the implement session as an `AddressReview` run, so the pull request gets 5 fresh review rounds. A job stored in `ReviewStopped` before the `ReviewStop` field existed, such as jobs/28, loads with the default and retries as a reviewer failure. A `ReviewStopped` ask with no pull request number is not retryable, and a `Retry` posted after the watch already moved the job on is rejected like any other stale retry.
- **Rerun after an edit.** When `open_pr` edits an existing pull request whose checks had failed, the factory reruns the failed runs on the head commit, so they read the new description. `GitHub::rerun_failed` lists the runs on the head with `gh run list --commit`, and runs `gh run rerun <id> --failed` for each one that failed, timed out or was cancelled. It uses the factory's token, so workers still have none. The case it covers is an agent run that edits the description and adds no commit. The push does nothing, so the old failed run is still the head's result. The factory reads the checks before the edit, and reruns after it. The rerun counts no round, because the round for the failing CI was counted when the agent was asked to fix it. Passing, pending and missing checks cause no rerun, and neither does creating the pull request. When the head has no failed Actions run, such as a failed check from outside Actions, `rerun_failed` returns `NothingToRerun`, and `open_pr` logs an error. When the rerun fails, `open_pr` logs the error and returns the pull request number, because the edit worked. GitHub keeps reporting the old failure for a moment after a rerun, and a watch in that moment would report it again and count a second round. So `rerun_failed` reads the pull request after the reruns until no check is failed, up to `settle_polls` reads `settle_interval` apart (10 reads, 3 seconds). The watch reads the same data, so it sees the new state.

The state machine is pure logic with no I/O, so it can be tested without podman or GitHub. Every step must be safe to retry, because a container or the factory can die in the middle of one.

## Running Claude Code in a worker

This is the Claude agent's implementation of the `AgentBackend` interface, see "Agent runtime". It holds every Claude-specific detail below: the `claude -p` command line, the `CLAUDE_CODE_OAUTH_TOKEN` credential, the `CLAUDE_CONFIG_DIR` config directory, the session-resume check, and the stream-json parser.

- One `claude -p` run per stage, with `--output-format stream-json` for the live log. The factory picks the session's UUID and passes it with `--session-id` on the first run, so it knows the ID even if it dies during the run. Later runs pass `--resume <session-id>`.
- **Fresh sessions.** The clarify, spec, plan and implement runs each start their own session, one for clarifying, one for the spec, one for the plan and one per planned pull request. Each prompt is self-contained, because the session has seen none of the earlier stages. The job stores the request, the answers, the approved spec and the plan for this. Only a gate revision, a check fix, a CI fix, a review fix or a rebase resumes the session of its own stage. Each stage can then use its own model, because no resumed session switches models. A job created before this rule has no stored answers and keeps one planning session for clarifying, spec and plan, so its spec and plan runs resume it with the short prompts.
- Every run ends with `--json-schema` structured output: an `outcome` and the questions, spec or plan that go with it. Each stage allows `questions` and one outcome of its own: `clarified`, `spec`, `plan` or `commits_ready`. A `FixCi` run may also end with `rerun_ci` and a required non-empty `reason`. The factory runs the rerun itself, so the worker needs no GitHub token for it. Any other run that returns it fails the job. Claude Code puts the output in `structured_output` on the final `result` line. A run without it, or with an outcome its stage does not allow, fails the job.
- The worker is started with `--rm`, so each job gets a Claude Code config directory on the host, mounted at `CLAUDE_CONFIG_DIR`. It keeps the session files that `--resume` reads.
- The factory resolves the Claude token when the run starts, see "Claude auth", and sets it in the podman process environment. The worker gets it with `--env CLAUDE_CODE_OAUTH_TOKEN` and no value, so podman passes the token through from its own environment and it never appears in the `podman` arguments, the job log or an error message. A token saved on the settings page reaches the next run this way, with no restart, while a run already going keeps the token it started with. With no token the run fails before any container starts with "no Claude token is set", and the job page's Retry runs the task again once a token is saved.
- Every run gets `--settings` with `attribution` emptied. Claude Code otherwise adds a `Co-Authored-By` trailer to each commit, a skill's rules do not stop it, and GitHub copies the branch's co-author trailers into the squash commit on the base branch. Before the project's checks, the factory also fails a branch whose commits credit an AI tool, and the agent rewords them.
- The factory's rules come in through `--plugin-dir` (skills and agents) and `--settings` (hooks). A headless run in an untrusted folder ignores a repository's `extraKnownMarketplaces` without any message, so the factory must not depend on the target repository's plugin settings.
- The target repository's own `CLAUDE.md` and project skills still load. maestro has its own `no-comments` and `open-pr` skills, so the factory's plugin namespaces its versions as `factory:no-comments` and `factory:open-pr`.
- Claude Code hooks run under whatever shell the container has, without the nix devShell. Write hook scripts for plain bash and test them that way.

## Running Codex in a worker

The worker image carries Codex next to Claude Code. The `AgentBackend` that drives it, the login storage, the settings page and the cost estimate land in later pull requests; this is the image groundwork and the facts the backend builds on.

- The image installs one pinned Codex release, set by the `CODEX_VERSION` build arg (`0.165.0`). It downloads the `codex-x86_64-unknown-linux-musl` tarball from the `rust-v<version>` GitHub release, installs the single binary as `/usr/local/bin/codex`, and fails the build if `codex --version` does not report that version. moon is x86_64, so the image pins that one asset rather than detect the architecture.
- The image creates `/codex`, owned by the worker user, the way it creates `/claude`. The Codex backend mounts the job's `codex` directory there as `CODEX_HOME`.
- The image links the bundled review skills to `/etc/codex/skills/factory`, a symlink to `/factory-plugin/skills`. Codex reads skills from `/etc/codex/skills` and `~/.agents/skills`, so a review run finds `review` and `comment-review` there without the `--plugin-dir` flag Claude uses. `/etc/codex/skills/factory/review/SKILL.md` resolves through the symlink.

### Codex CLI facts (rust-v0.165.0)

These were checked by running the pinned `codex-x86_64-unknown-linux-musl` binary (`codex-cli 0.165.0`). A full run needs the ChatGPT login, which this build does not have, so the token-accounting facts are checked against the documentation and confirmed from an authenticated capture on moon in the backend pull request.

Confirmed against the binary:

- `codex exec` accepts `--json`, `--output-schema <FILE>`, `--dangerously-bypass-approvals-and-sandbox`, `-m/--model <MODEL>` and `-c key=value` overrides. `codex exec resume <SESSION_ID> [PROMPT]` takes a session UUID or a thread name.
- `codex login --device-auth` exists for a machine with no browser. `codex login --with-access-token` reads a Business access token from stdin; it is out of scope for now.
- `--json` writes JSON Lines. The captured envelopes are in `crates/factory-runner/tests/fixtures/codex-exec-auth-failure.jsonl`: `{"type":"thread.started","thread_id":"<uuid>"}`, `{"type":"turn.started"}`, `{"type":"item.completed","item":{"id":"<id>","type":"error","message":"..."}}`, a top-level `{"type":"error","message":"..."}`, and `{"type":"turn.failed","error":{"message":"..."}}`. The run authenticated against `api.openai.com` with no login and ended at `turn.failed`, so the capture stops before the success-path lines.
- Codex assigns the session id and reports it in `thread.started.thread_id`, so the factory learns it from the stream and cannot pass it in advance, as the spec expected.
- `cli_auth_credentials_store = "file"` in `config.toml` is accepted, and `-c` overrides nested keys through dotted TOML paths.

Differences from the spec's expectations:

- The default model is `gpt-6.1-sol`, printed in the run header, not a `gpt-5-codex` id. The Codex model suggestions in the registry should track this CLI's `gpt-6` family.
- The CLI does not validate `model_reasoning_effort`: `-c model_reasoning_effort=bogus` was accepted and the run header printed `reasoning effort: bogus`. The model's server rejects an unsupported level at request time, so the allowed levels cannot be read from the CLI. OpenAI's model page lists `low`, `medium` (default), `high`, `xhigh` and `max` for `gpt-6.1-sol`, and says `none` and `minimal` are not supported. This differs from the spec's expected `minimal, low, medium, high, xhigh`; the effort-levels pull request uses the model-supported set.
- `turn.failed` carries the reason under `error.message`, and `item.completed` wraps the item under `item`. The parser reads those paths.

Not confirmable without an authenticated run, deferred to the moon capture in the backend pull request:

- `turn.completed` and its `usage` fields, and whether `cached_input_tokens` is part of `input_tokens` and `reasoning_output_tokens` part of `output_tokens`. The unauthenticated run never reached `turn.completed`, so the cost formula stays unconfirmed.
- The success-path item types `agent_message`, `command_execution`, `file_change`, `mcp_tool_call`, `web_search` and `todo_list`.
- Whether the final message conforms to `--output-schema`.

Operational notes:

- Codex warns that it cannot find bubblewrap and uses a bundled copy. With `--dangerously-bypass-approvals-and-sandbox` the container is the sandbox, so bubblewrap is unused and the image does not install it.
- "Code Mode" fails closed when `codex-code-mode-host` is absent and emits an `error` item. It is not needed; the parser treats such a line as a non-fatal log line.

## Lessons from building maestro's checks

- `grep -q` at the end of a pipeline under `set -o pipefail` can fail when it matches, because the writer gets SIGPIPE. Feed `grep -q` from a variable instead.
- macOS has bash 3.2 as `/bin/bash`. Hook scripts must work there.
- prek refuses to run when `prek.toml` is not staged.
- prek runs hooks without a `stages` setting at every stage, the `commit-msg` stage included. Set `default_stages` when adding hooks for other stages.
- A project setting in `.claude/settings.json` loads only when the session starts. A hook added mid-session does not fire until the next session.
